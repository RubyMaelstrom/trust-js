Implemented changes

Object.groupBy now indexes groups by key instead of rescanning every existing
group. Object/Map.groupBy consume the iterator and call the callback in the
specified order, including live changes to the input. Errors from callbacks
and property-key conversion close the iterator; opening/stepping errors do not.
Map uses one hash-table probe and offset links between groups, avoiding a
separate collision-bucket allocation per distinct hash. A deliberately colliding
undefined/Number pair exercises both head and older-group lookup.
Invocation-local guarded Callback entries amortize repeated callback/next calls
without losing proxy, bound-function, Realm, GC or exception behavior. Temporary
indexes are released before building the result. Object key ordering and Map
SameValueZero semantics are retained.

Literal replacement callbacks retain the original LStr rather than copying the
entire input for every match. ASCII callback offsets no longer rescan prefixes.
Unicode empty-pattern replacement no longer panics on a zero-width Rust window.
ASCII substring-view patterns receive a real ASCII check when a conservative
hint alone cannot decide whether they match.

Empty-separator split decodes only the requested UTF-16 prefix. Proven ASCII
strings and ASCII-owned views use an exact-length byte iterator, retaining full
split allocation efficiency. Surrogate halves, coercion order and split limits
are unchanged.

ARM64 numeric Math and isNaN call paths decline aliased receiver/callee owners
before mutation, allowing the checked path to release them correctly. Tests
cover repeated references and final-owner destruction with a separate sentinel.
The x86-64 call path already uses the checked helper.

Arrays can recover packed append/pop and numeric-read eligibility after a
transient far-index property is removed. Individual deletion scans at most 256
remaining named entries; larger maps stay conservative until a truncation
rebuild. All remaining canonical named indices keep packed growth disabled.
Failed numeric-mirror preparation is retried through its complete validator.
Descriptor, hole, prototype, partial-length-failure and cyclic-owner tests cover
the storage transition. No object/Props/JIT layout was changed.

JSON.stringify truncates string indentation to ten UTF-16 code units rather
than Unicode scalar values. It preserves a lone surrogate at that boundary
and canonicalizes output only when repeated indentation can join surrogate
halves. The ordinary no-gap serializer takes the existing path.

Final artifact memory and startup controls

The initial three-pair Math control had a peak-RSS gate (+9.87%); a seven-pair
repeat using the same executable-file pair retained that gate (+8.29%, nominal
95% ratio interval 1.0029..1.1350). These records were not discarded. The short

+2.020%, below the project median-loss threshold. Latency gates passed.

A separate seven-pair Math cohort created independent baseline/candidate tmpfs
files per pair, alternated creation order and verified every hash. Its RSS ratio
was 0.9975 (nominal 95% interval 0.9301..1.0111), with no gate. Controlled post-exec
RssAnon/RssFile/RssShmem and smaps measurements locate the large swings in anonymous

scopes. Native generated code is 208,656 vs 209,616 bytes. Opaque storage is still
excluded, so these observations are not an exact retained-heap proof. All original
RSS gates, independent-copy repeats and diagnostic reports are included in the
validation JSON. This is a measurement reproducibility investigation, not an RSS
waiver. The three-pair bootstrap intervals are descriptive controls and provide

A checked empty script completed in every seven-pair startup process. Wall-time

Ladybird comparison and remaining work

An agent cloned official Ladybird revision
 d8afe7ddba448c54ee9ded2c808c1a77d3791ca1
and audited its runtime/compiler, storage/GC, strings, regex, JSON and caching.
docs/ladybird-comparison-2026-10-14.txt retains the pinned source evidence and
standards references. The array-recovery and JSON-gap fixes came from this audit.
Ladybird was not built or timed: the normal shell build still needs additional
checkout trees and system dependencies. No measured Ladybird speed ratio is
claimed in this review.

The current Ladybird has a default optimizing Rust JIT and a generated native
bytecode interpreter. TRust already has numeric regions, direct calls, typed-array
fusion, caches, packed storage and an experimental whole-function optimizer.
Larger gaps are cross-control-flow guard reuse, range/bounds proofs, loop motion,
allocation elimination, optimizing inlining with multiple recovery frames,
cheap feedback and background compilation. Its embedded GC-cell assumptions
cannot be copied into TRust's Realm-independent shared code contract.

More bounded follow-up candidates are required-literal regexp rejection,
repeated JSON key/layout reuse, ordered-key caching with descriptor validation,
and efficient worst-case UTF-16 literal search. These remain unimplemented and
unmeasured; this session does not establish general superiority over Node or
Ladybird. See the detailed comparison for evidence and semantic constraints.

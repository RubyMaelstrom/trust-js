Strict large-caller inlining — application comparison, 30 September 2026
======================================================================

The old whole-body 320-source-operation allowance rejects small callees in
large callers. The solver lexer is an application target. This experiment
adds at most 64 callee source operations to strict ordinary callers above
320 and at most 4096 original operations. Explicit TRUST_JS_INLINE_BUDGET keeps
its previous diagnostic meaning. Callees retain the existing size, private
binding, closure-name, identity, receiver and operation allowlist proofs;
this expanded path additionally requires strict ordinary non-suspending
callees. The older small/sloppy inline path is unchanged. This experiment
does not establish that its pre-existing omitted frames are correct.

Expanded splices now bracket parameter binding and every source return with
logical call operations. An owned per-interpreter state stack pins each live
callee and temporarily clears/restores construction and new.target state.
FnFrame uses one existing padding byte to mark logical frames without
growing its 24-byte layout. ARM64 physical native pushes initialize that byte
with the existing strict-field store. Both native checked operations and VM
fallbacks implement entry/leave. Native/VM exception routing removes only
this activation's logical frames; an entry watermark protects reentrant
scripts, and physical FnFrame boundaries protect shared-context direct calls.
These bodies still exclude handlers, direct eval, closure creation, private
names, super, new.target and suspension needing an unremapped activation.

Logical calls contribute JS depth and GC cadence. Native execution-stack
checkpoints instead use physical depth. This distinction is necessary:
three inline frames per recurring physical call otherwise advance logical
depth by four and can miss all modulo-eight native-stack checkpoints. Saved
callee/new.target owners and state Vec capacity are included in retained
memory accounting. No strong GC graph edge or allocation identity is replaced
by an unowned pointer.

After both exclusive measurement sets ended, one instrumented diagnostic per binary/workload recorded 3,172,414 InlineEnter and 3,172,414 InlineLeave helper calls in the solver, plus 12,572 each in Djot. These counts show new helper traffic, not its causal time fraction. Solver generated native bytes were 59,435,336 baseline and 61,315,568 candidate in those diagnostics. Compile seconds were .43298 and .44147; a single instrumented observation does not establish a compilation regression. Both exact normalized outputs still match.

Decision: reject and restore all prototype production code and its new tests. The small primary changes do not establish a major benefit, and Djot system CPU crosses the regression gate. Entry/exit helpers and larger native output supply follow-up hypotheses, not measured remedies. The frame/owner/entry-watermark/physical-depth source remains archived for a future native context design. Existing small inlining is unchanged; the experiment supplies no new global correctness claim for it. No user exception to the regression policy was requested.
No installed or accepted release artifact is replaced. The workspace engine shell is restored to the pinned baseline after parking the prototype; subsequent source builds detect the restored sources.

# Phase 2 plan: baseline strengthening (2026-10-26; the owner's decisions of 2026-10-27)

Program: [docs/v8-chase-2026-10-15.txt](/big/Code/trust-js/docs/v8-chase-2026-10-15.txt).
Phase 1's plan and record, including its close-out:
[docs/v8-chase-p1-plan-2026-10-15.txt](/big/Code/trust-js/docs/v8-chase-p1-plan-2026-10-15.txt).
Citations are to the tree at the close-out (main after it merges); re-verify them when touching
code. This plan is the design record P2 needs before code, as P1's was.

## Goal

Make the existing tiers (the AST interpreter, the bytecode VM and the template JIT) and the
object model cheap enough, and make what they record complete enough, that Phase 3's
speculative optimizing tier (inlining, type speculation with deoptimization, escape analysis)
starts from a sound base; and close the gaps to Node/V8 that do not need speculation. The
program defines P2 as "call path (frame/argument costs), feedback completeness for the future
tier, builtin algorithmics (shift class), RegExp"; P1's closing record assigned P2 the object
layout costs its collector still carries. This plan covers both.

Acceptance surface, unchanged from the program's Decision 1: the Vue, React and Djot fixtures
and Speedometer 3.1 against Node/V8 on Crystal (ARM64), x64 on zombie secondary. New standing
comparisons from the close-out: full Octane 2, the Web Tooling Benchmark, ARES-6 and a call-path
microbenchmark set (the harness and suites are under target/claude-closeout; see "Measurement").

The yardstick is Node limited to its non-speculative tiers, Ignition and Sparkplug
(`--max-opt=1`). Node's lead on the fixtures does not depend on speculation: limited to
Sparkplug it runs them 3.4-3.8x faster than the close-out, against 2.9-3.9x in full (Node by
tier, below). Phase exit: each fixture within 2x of Node limited to Sparkplug, measured in the
same session (Decision 2).

What the numbers say:
- The close-out is the fastest of the three engines on every suite: Octane +6.9% over main
  (Splay +28%, RegExp +25%, SplayLatency +21%, EarleyBoyer +16%, PdfJS +10%; nothing slower
  than 0.3%), Web Tooling +31% with every tool faster, ARES-6's summary 2.8% lower (Babylon's
  steady state 13% lower; Basic 2-5% and Air's first iteration 1-4% slower), Djot -6%, TRust's
  replays 5-14% faster; the call microbenchmarks did not move (within 3%). Against the old
  engine it trails by more than 2% only on Splay (-15%), SplayLatency (-40%) and CodeLoad
  (-8%): major-collection pauses and the object layout (W2, W6).
- Node leads by 3-4x on the fixtures, 10x on ARES-6, 12x on Web Tooling and 3.4-34x on
  Octane's benchmarks. Limited to Sparkplug, it keeps all of its lead on the fixtures
  (3.4-3.8x) and leads by 4.2x on ARES-6 and 4.8x on Web Tooling, but by 1.8x on Octane's
  geomean, where the close-out is faster on Crypto (4.7x), NavierStokes (1.5x) and
  SplayLatency (1.4x) and level on Richards: most of Octane's gaps are speculation's (P3). The
  gaps Sparkplug-only Node keeps are this phase's; the largest: Web Tooling's coffeescript
  (23x) and source-map (11x), not yet attributed; the holey shift (17x) and spread calls (14x;
  W1, W3); RegExp (11x; Irregexp, W5); the other Web Tooling tools (2.8-6.7x); EarleyBoyer,
  Typescript, Gameboy and Box2D (2.1-3.5x). zlib's 22x does not move with the tier: V8 runs
  its asm.js module (zlib-data.js, "use asm") as WebAssembly.
- Memory: V8's sizing raises peak RSS where allocation is heavy: against main, Octane +10%,
  Web Tooling +41%, ARES-6 +56%, sustained allocation +45%, Octane through TRust +78%.
  Node's peaks are 3.7x (Octane), 3.4x (Web Tooling) and 1.6x (ARES-6) lower; its objects
  are smaller (W2). V8's cap of each limit at halfway to its heap maximum, which the
  close-out did not port, would bind only on Web Tooling: the close-out's largest live heap
  after a major collection (cells and their external payloads, TRUST_JS_GC_LOG; logs in
  final/gclog) is 1027 MB there, 458 MB on Octane and 39 MB on ARES-6, and the cap binds
  above ~585 MB (Decision 5).

### The code (survey of the close-out tree)

Call path.
- Generic entry (natives calling back, VM calls, uncached sites): `Interp::call`
  (interpreter.rs:12286) roots arguments, checks depth/stack/GC; `call_dispatch` (12491)
  probes the proxy side table and, once any class exists, the `class_info` hash map on every
  call (12593); bound functions concatenate a new Vec per call (12604); `call_user_inner`
  (15032) counts calls, compiles at threshold 8, runs `run_compiled_chunk` (13220).
- Prepared entries (sloppy `arguments` with non-simple parameters, eval/with, destructuring
  rest, unsafe defaults; bytecode.rs:6562-7115) allocate one var scope per call (three with
  parameter expressions), a `"this"` string when the body reads `this` (15235), and an
  arguments object or a boxed stash (15253, 15264).
- The VM's `Op::Call` ignores the call cache and re-enters the generic chain
  (bytecode.rs:17329-17364); rest parameters are `to_vec` + `make_array` (15361); an
  activation is built only when an inner function captures (bytecode.rs:3418), and
  `ActivationPlan::instantiate` clones every `(Rc<str>, Binding)` entry
  (bytecode_activation.rs:145-205).
- ARM64 JIT: a 4-way identity cache per site (bytecode.rs:1262; jit.rs:7340-7470) and a direct
  sequence (jit.rs:7596) that allocates nothing, but declines callees with an activation or
  any `arguments` slot (`CALL_IC_NEEDS_ENV`, bytecode.rs:1013), which is most framework code.
  Native calls from JIT pay depth/stack/GC checks, two interrupt polls and a host-callback swap
  (interpreter.rs:13841); ~30 intrinsics are inlined (bytecode.rs:1033-1084). Spread and
  args-array calls have no cache (bytecode.rs:16841-16880; spread.rs:129-190). x64 calls go
  through the `H_CALL` helper (jit_x64.rs:1227).
- Inlining is guarded bytecode splicing only (InlineGuard, bytecode.rs:17242; recompilation
  after 100 machine-code runs, budgets 320/384 source ops, an allowlist without closures,
  handlers, activations or `super`). The optional Cranelift tier was removed before P1
  (6b210624, 2026-10-15); docs from 2026-10-14 that cite `jit_optimizing*.rs` are history.
- Microbenchmarks (the call table): against Node limited to Sparkplug, its non-speculative
  baseline, the direct, method and closure calls take 1.5-1.9x as long, the constructor and
  recursion 2.1-2.2x, the argument shapes 3.2-4.4x, `call`/`apply` 3.7x, the getter 6.9x and
  spread 14x. Full Node inlines the method, `arguments`, rest and getter cases (about 1 ns an
  iteration).

Feedback.
- feedback.rs defines a versioned per-function schema (named/element loads and stores, call,
  construct, arithmetic, branch, loop, allocation; feedback.rs:46-187) with mono/poly/absent/
  generic states (373). Collection is opt-in (`TRUST_JS_FEEDBACK_PROFILE`, feedback.rs:28) and
  reroutes JIT templates through helpers (jit.rs:3940); nothing reads it in production (`read`
  is cfg(test), 1454); inlined or recompiled chunks write nothing (733-741). The schema file
  feedback.rs:3 names (FEEDBACK_SCHEMA.md) does not exist.
- What the tiers consume are their inline caches: the 4-way property IcState (up to 6
  prototype levels, bytecode.rs:87-139, baked into JIT probes jit.rs:5895-5946), call caches
  (whose way count the inliner reads), name/capture caches, creation caches, construct
  capacity hints, per-array mirror flags.
- A speculative tier would still lack: feedback that is on by default; comparison, `in`,
  `instanceof`, `typeof`, free-name, captured-variable, iteration and for-in sites; call-target
  identity, megamorphic state and per-way counts; elements kinds (packed/holey x int32/double/
  any); allocation-site records (boilerplate, kind transitions, survival, for pretenuring); a
  PC map through inlining; shapes as a proof (value.rs:5378, Pilot C unfinished); dependency
  records for invalidation.

Builtins (the "shift class").
- Packed elements are 16-byte `Property` words (10 inline, value.rs:5633; then a deque with
  front room, dense_deque.rs:15-25); holes are `Value::Empty`. Packed storage starts only at
  creation or a first write at index <= 256 on an empty array (value.rs:7836-7844); a farther
  write sets `has_far` (9120) and nothing converts a classic array back.
- push/pop are O(1) under the prototype protector (interpreter.rs:8353-8397); `shift` is O(1)
  for a packed, all-plain array (value.rs:8408), else an O(n) rotation, else the generic loop
  (builtins/mod.rs:6311) that formats a string key per index. unshift/splice/reverse need
  packed all-plain storage; indexOf/lastIndexOf/includes (6413), sort (6835) and copyWithin
  have no bulk path; partial fill sets per index by string key (6749). A delete writes Empty in
  place (9242) and fails every all-plain guard until refilled.
- Vue's cost is not storage: the fixture shifts `model.items` (benchmarks/fixtures/vue.js:41,
  54), a Vue `reactive()` Proxy, so the generic loop runs 50+ trap calls per shift, each with a
  freshly allocated key string (value.rs:1286). On the close-out, `shift` is ~47% of Vue's
  elapsed time (671 calls, ~275 us each; TRUST_JS_PERF_METRICS).

RegExp.
- A backtracking matcher over a flat instruction program with a heap stack (regex.rs:1-12,
  `run` ~5714); case folding at match time; literal and first-element fast paths (2376); a
  one-byte tier after 64 executions for capture-free, alternation-free programs (machine code
  only without anchors, and on AArch64 without classes; regex.rs:1129-1167). The close-out
  fixed that tier's anchors (/a^/ matched "a" after 64 runs).
- Prepared subjects: one hot ASCII entry plus an LRU of widened subjects (32 MiB / 8,192
  entries, interpreter.rs:3398); views of ASCII strings match as bytes since the close-out.
  Exec results share one pre-shaped layout per kind (close-out); each capture is still a fresh
  string copy (builtins/mod.rs ~2516).
- Fixed per-call costs: `regexps` hash lookups, a string-keyed `lastIndex`, ~20 guard lookups;
  every RegExp creation inserts into `gc_pin` and `regexps` (eval.rs:5477-5494), whose removal
  is now the largest per-minor-collection cost on Octane RegExp (~66 us of ~180 us). `match`
  with /g, `search` and `matchAll` build throwaway match arrays; no required-literal prefilter.

Object model and collector.
- The object cell is `RefCell<Object>` <= 192 B in the 192 B size class (value.rs:4069-4072):
  proto; `Props` with 4 inline 16-byte slots, a layout pointer, a u32 shape, a 2-word element
  sidecar, mirror flags, `has_far`, `elem_mode`, two slot memos; a 16-byte `Callable` that only
  functions need; an `Exotic`; a typed-array pointer; flag bytes. A fifth named property moves
  all fields to a spill block (inline_vec.rs:3-7). A 1-element array is a 192 B cell plus a
  ~256 B element block. V8's JSObject is 12 B plus 4 B per in-object field (pointer
  compression).
- Property layouts are GC cells holding `Vec<Rc<str>>` and run finalizers (value.rs:3185);
  environments (`Scope`, 128 B class) hold 40-byte `(Rc<str>, Binding)` entries and run
  `finalize_scope_cell` (value.rs:3621). Shape ids are process-wide; transitions per heap.
- The write barrier stores two bytes (card and page summary, gc_core.rs:110); a minor collection
  reads every carded page's summary (~0.4 ms per minor on Splay's ~480 MB heap). Generated code
  allocates only through helpers followed by a poll (jit.rs:1973-2003, 16982).
- Exotic state still lives in address-keyed side tables (proxies, promises, generators,
  `class_info`, mapped arguments, regexps, typed arrays; interpreter.rs:3423-3756).
- Heap sizing follows V8 since the close-out (`gc_pacing.rs`): dynamic growing factor 1.1-4,
  nursery 2-32 MiB, the memory reducer. Splay's heap peaks at twice P1's because of that
  factor; its live heap (~246 MB) is the layout's doing. Not ported: V8's cap of each limit
  at halfway between the live size and the heap maximum (heap-controller.cc,
  `BoundAllocationLimit`), since the engine has no maximum (V8's old generation may reach
  half of physical memory, clamped to 256 MB-4 GB on 64-bit desktop hosts, heap.cc
  `OldGenerationSizeFromPhysicalMemory`; Node reports a 4288 MB limit here). With a 4 GB
  maximum the cap binds only above ~585 MB live (4L > (L + 4 GB) / 2).

## Workstreams

W1. Builtins and Proxy-heavy paths (first: the largest single measured win)
- Index keys without allocation: the generic algorithms take numeric keys (interned index
  atoms or an index key variant) instead of formatting strings; Proxy trap calls pass them.
- Cheaper Proxy traps: a trap call from a builtin's generic loop without the full call chain's
  per-call checks (still observable-equivalent: the trap is a user function).
- Holey fast paths under the existing protector (holes stay holes), in-place deque splice
  (no whole-array copies, dense_deque.rs:227-236), bulk indexOf/lastIndexOf/includes, dense
  sort and fill; a census of generic-path hits on the acceptance set picks the rest.
- Exit: Vue's `shift` time cut by 10x; no builtin in the acceptance set spends more
  than 5% of a workload's time on a generic path that a fast path could take.

W2. Object model, second pass (layout and the collector's remaining costs)
- W2a Atoms: property keys and binding names interned per Agent heap (with a static table for
  the names compiled code embeds, since ASTs are shared across Agents), compared by identity;
  layouts and environments stop finalizing (the P1 record: a fifth of the sustained workload's
  minor collection time).
- W2b Per-chunk scope descriptors: environments index slots through a shared descriptor (V8's
  ScopeInfo, JSC's SymbolTable) instead of owning `(Rc<str>, Binding)` entries; eval/with and
  reflection keep a name path through the descriptor.
- W2c Elements as 8-byte words under a per-array "all plain" kind (the proof exists,
  value.rs:5640); a non-plain element moves the array to a dictionary representation (V8's
  elements kinds). Halves arrays; one load per JIT element read.
- W2d A slimmer cell: `Callable`, the typed-array pointer and mirror state move to kind-specific
  payloads, flags pack, only the overflow spills; then either the 128 B class or more inline
  slots at 192 B, chosen by allocation-site slack tracking (V8's).
- W2e Inline allocation in generated code: cursor take, byte charge and template copy, keeping
  the poll after allocation.
- W2f A chunk-level card summary (one more barrier store in both backends).
- W2g Exotic state into payload cells, as P1 did for Map and Set: proxies, promises, generators,
  `class_info`, RegExps (with W5), typed arrays.
- Exit: Splay's live heap halved; fixtures' peak RSS at or below the close-out's;
  the sustained workload's minor collection time down by the finalizer share; JIT dump checks
  unchanged apart from intended layout changes.

W3. Call path
- Measure first (TRUST_JS_JIT_CALLSTAT, DIAGNOSTICS.md) which direct-call misses dominate on
  the acceptance set; the code alone does not size them.
- The direct sequence's own cost: the bare call takes 41 ns an iteration against Sparkplug's
  22, though all but 872 of its 5,001,000 calls take the direct sequence
  (TRUST_JS_JIT_CALLSTAT); count what each call executes (the JIT dump) and trim it.
- A class-constructor bit on the function object instead of `class_info` probes on every call
  (interpreter.rs:12593, 14860, 15067).
- With W2b's descriptors: slot-indexed environments that the direct sequence or a lean helper
  builds, so functions with closures take the direct path.
- `arguments[i]`, `arguments.length` and rest length served from the caller's argument window
  (which the moved-frame entry already keeps alive, jit.rs:17937); mapped arguments as a slot
  map in the object.
- Call caches for the VM's `Op::Call` and `CallSpread`, and bound-function cache entries.
- A lighter native boundary for natives that cannot re-enter JS.
- Exit, against Node limited to Sparkplug on the call table: the direct, method,
  closure and constructor calls and recursion within 1.25x (today 1.5-2.2x); `arguments`,
  rest, `call`/`apply`, spread and the getter within 2x (today 3.2-14x); Vue/React elapsed
  improved by the measured call share.

W4. Feedback for the speculative tier
- Always-on value classes for arithmetic and comparison sites, written only on VM and miss
  paths; a production read API; the schema documented in the tree (tracked .txt).
- Call-target identity exported from CallSite; elements kinds from the mirror flags; a
  megamorphic state.
- Allocation-site records keyed by allocation PC, with survival counted at minor collections
  (boilerplates, slack tracking for W2d, and pretenuring: Splay-like workloads promote nearly
  everything they allocate).
- PCs of inlined and recompiled code mapped to their baseline sites.
- Finish Pilot C (descriptor classes as a proof) and add a dependency registry for
  invalidation.
- Exit: feedback on by default at <= 2% cost on the acceptance set; coverage (share
  of executed operations with usable feedback) reported as a standing metric and >= 95% on it.

W5. RegExp
- Slice-view captures; direct paths for `match` with /g, `search` and `matchAll` (no
  throwaway arrays); a protector bit replacing the per-call guard lookups; the compiled program
  and `lastIndex` in the RegExp's own payload (no `regexps`/`gc_pin` hashing per exec and
  creation, which also removes the largest per-minor cost left on Octane RegExp); case closure
  at compile time; required-literal and NEON prefilters.
- Then a native tier with captures and alternation on both backends, behind a differential
  gate against the interpreter (Decision 3; V8's Irregexp, which SpiderMonkey shares, and
  JavaScriptCore's YARR JIT compile RegExps to machine code); the measurements set the order.
- Exit: Octane RegExp and Djot's `exec` time each cut by 2x from the close-out.

W6. Collector scheduling
- V8's cap (Decision 5): each limit at most halfway between the live size and V8's heap
  maximum (half of physical memory, 256 MB-4 GB; heap-controller.cc `BoundAllocationLimit`,
  heap.cc `OldGenerationSizeFromPhysicalMemory`), for pacing only, without V8's out-of-memory
  failure at that maximum. Independent of the other workstreams.
- Incremental marking (Decision 4): a marking write barrier in the interpreter, the VM and both
  JIT backends, and major marking in slices interleaved with the program, as V8's incremental
  marking runs; after W2's layout work, so that P3's tier emits the barrier from its start.
  Concurrent marking stays a non-goal.
- Exit (proposed): the cap's limits match V8's rule in unit tests and lower Web Tooling's peak
  RSS, with no suite slower beyond noise; marking's exit is set in its design note, with
  SplayLatency at least the old engine's (6446) as the target.

W7. Strings (Decision 7)
- Store strings as code units at the browsers' two widths instead of UTF-8 with UTF-16 views
  built per string on demand, whose cliffs make Web Tooling's two largest gaps (see the stage
  record); fix the string deviations the survey found.
- Exit: in its design note.

### Step 0: a perf map for generated code (design, 2026-10-27)

`TRUST_JS_PERF_MAP=1` makes the engine append a line for each piece of code it generates to
`/tmp/perf-<pid>.map` in perf's JIT map format (`START SIZE name`, hexadecimal without `0x`),
which `perf report` reads for samples no binary resolves; V8's `--perf-basic-prof` writes the
same file. The lines come from the compile-time hook the gprofng registration uses
(jit_profiler.rs, called from `compile_profiled_with` for both backends) and from every other
place that makes executable code: the process-wide shared stubs (permanent), and the native
RegExp tier's byte and word programs (regex.rs). Names follow V8's: `JS:^<name>
<url>:<line>:<column>` for a chunk (`^` marks baseline code, as V8 marks Sparkplug's),
`<anonymous>` for a function without a name, the first local names when there is no script;
`Stub:<kind>` for a shared stub; `RegExp:/<source>/<flags>`. A chunk carries its label only
while the map is on: an `Option<Box<str>>` the bytecode compiler fills from the AST function's
name, script and start (`ScriptSource::line_column`), so the default path pays nothing. Freed
code is not unlisted, as perf's map format has no unload record (V8's map has the same limit;
a jitdump for `perf inject --jit` would lift it if address reuse confuses a profile). The file
opens on first use and takes one write per line under a process-wide lock, since Agents on
other threads compile too. Tests: a compiled function, a shared stub and a native RegExp each
add a line that parses and names them, and nothing is written with the switch off.
DIAGNOSTICS.md documents the switch beside `TRUST_JS_JIT_GPROFNG`, with the call-graph flags
(`perf record --call-graph fp --user-callchains`). Exit: `perf report` on the Vue fixture names
the generated code among its 30 hottest symbols, with no bare addresses.

Landed 2026-10-27 (d4e62452). The dumps differ from the base only in the displacement of the
three Chunk fields generated code reads, 16 bytes on for the label. Exit met: `perf report` on
the Vue fixture names generated code among its 30 hottest symbols with no bare address
(`JS:^<anonymous> .../vue.js:4:17983` 7.8%, `Stub:NameLoad` 4.7%, ...).

### W6a: V8's cap on the heap limit (design, 2026-10-27)

After a major collection V8 sets the old generation's limit to
max(min(max(size x factor, size + step) + young capacity, (size + maximum) / 2), minimum)
(heap-controller.cc, `MemoryController::BoundAllocationLimit`). The engine computes the inner
term today (gc_core.rs, `sweep_phase`: `size` is the cells held plus the payloads they own
outside the heap, which V8 keeps on its heap: Map and Set tables, internal slots, bound
arguments). The port adds the halfway bound with V8's maximum for the old generation on 64-bit
hosts (heap.cc, `OldGenerationSizeFromPhysicalMemory`): half of physical memory, clamped to
256 MB-4 GB, to be re-verified against V8's current source and cited at its revision as
gc_pacing.rs does. The physical memory comes from the operating system (sysconf on Linux,
`hw.memsize` on macOS, GlobalMemoryStatusEx on Windows); `TRUST_JS_GC_MAX_HEAP_BYTES=N`
overrides the maximum, as V8's `--max-old-space-size` does, for tests and diagnosis. Pacing
only (Decision 5): V8 fails with out-of-memory at its maximum and the engine does not, so the
bound never takes the limit below size + step + nursery, V8's own least room, and a heap past
the maximum keeps collecting at that room. The bound applies only with pacing on; fixed
budgets keep their rule. Tests: the limit below, at and above the point where the bound binds
(about 585 MB at factor 4 with a 4 GB maximum), past the maximum, and the override.
Exit (proposed, W6): the limits match V8's rule in unit tests; Web Tooling's peak RSS falls; no
suite slower beyond noise.

Landed 2026-10-27 (7495f76b). Two differences from V8 remain, both to be ported (Decision 9):
past the maximum V8's floor is `size + 8 MB` (its global limit, 8f876708cf), where the engine
keeps the note's `size + 8 MB + nursery`; and V8's MaxGrowingFactor allows a factor of 4 only for
a maximum of at least 2 GB (1.3 to 2.0 below), which the engine does not port (it differs on
hosts with less than 4 GB of memory or under a small override). Measured 2026-10-28 (Stage-exit
timing): no suite slower; Web Tooling's peak RSS waits for its runs.
Both ported 2026-10-27 (05b80239, V8 at 96c72ad4): the growing factor stops at
MaxGrowingFactor's (4 from a 2 GB maximum, 1.3 to 2 below), and within 16 MB of the maximum
and past it the budget is the size and 8 MB. With 4 GB of memory or more and no override, only
that floor changes. Validation: Test262 identical, the fixtures, the lib suite and the
downstream crates' suites.

### W1: builtins and Proxy paths (census and design, 2026-10-27)

Census: the close-out engine (target/claude-closeout/lto-final), user-mode instructions sampled
with call graphs on CPU 5; data, scripts and the microbenchmark in target/p2/w1-census.
- Vue: `shift` takes 34% of the fixture's time, 212 us a call against 66 us for Node limited to
  Sparkplug (3.2x; the fixture's own gap is 3.4x), where it is 36% of the time. The fixture's
  `reactive()` handlers are JavaScript: under `shift`, the `set` traps take 22% of the fixture's
  instructions and the element reads 7%, mostly Vue's handler code and the calls into it;
  formatting index keys takes 0.4%. The generic loop's own work does not dominate, so a 10x cut
  of `shift` (the plan's exit) is not W1's to make: it would be 3x faster than V8's.
- A Proxy microbenchmark (micro/proxy-shift.js: a 17-element array, one push and one shift an
  iteration, 53 trap operations a shift; ns an iteration, the least of 3 runs; trust-js /
  Sparkplug-only Node / Node): an ordinary packed array 290 / 190 / 145; classic (holey)
  storage 300 / 100 / 200; a Proxy without handlers 17,650 / 13,300 / 13,550; with handlers
  forwarding through Reflect 36,750 / 20,400 / 18,800; with handlers that use the target
  directly 17,500 / 9,050 / 8,500. V8's generic shift over a Proxy is slow too.
- Where a Proxy operation's time goes without handlers: a forwarded [[Set]] whose receiver is
  the proxy (OrdinarySetWithOwnDescriptor) turns the receiver's own descriptor into an object
  and back and builds a second descriptor object for [[DefineOwnProperty]]
  (`reflect_define_on_receiver`, `proxy_gopd_value`, `proxy_define_property`: about 25% of the
  micro's instructions, string-keyed reads of the descriptor fields included); the
  getOwnPropertyDescriptor, defineProperty, getPrototypeOf and ownKeys trap lookups bypass the
  trap caches; each element step re-probes the side tables (the proxy table among them: 6-8%);
  and each index is formatted into a heap String. With handlers, the calls into them (W3)
  dominate. Vue's handlers call `Reflect.set(target, key, value, receiver)` with the proxy as
  the receiver, which takes the same descriptor-object path (5% of the fixture).
- React and Djot spend no more than 4% in any builtin's generic path (React's largest is
  CreateDataPropertyOrThrow, 3.9%; Djot's RegExp work, about 8%, is W5's). Octane spends no more
  than 0.2% in any array builtin; its largest builtins are String.prototype.replace with a
  RegExp (8%, W5's) and Function.prototype.call (2.3%, W3's). Web Tooling (the whole suite): no
  array builtin above 1.1% (merge_sort 1.05%), the Proxy side-table probe 1.3%; its largest
  builtin cost is strings' UTF-16 views (9.4%, W7's).

Design:
1. Proxy [[GetOwnProperty]] and [[DefineOwnProperty]] pass Property Descriptor records
   (`Property`, `PartialDesc`) and make an object only to call a trap (FromPropertyDescriptor)
   or to read a trap's result (ToPropertyDescriptor), as ECMA-262 §10.5.5 and §10.5.6 do.
   OrdinarySetWithOwnDescriptor (§10.1.9.2 step 2.c-e) on a proxy receiver uses the records,
   and Object.defineProperty, Object.defineProperties and Reflect.defineProperty convert their
   attributes before the target's [[DefineOwnProperty]] runs (§20.1.2.4 step 3, ahead of the
   proxy's GetMethod of its trap).
2. Every trap's GetMethod goes through the trap caches (`proxy_get_trap`), all thirteen kinds.
3. Generic array loops format each index into one reused buffer instead of a String per
   element, and a key a trap receives comes from a per-Agent table of the strings of small
   indices (V8 answers NumberToString from its number-string cache).
4. Holey shift, unshift and splice: under the existing prototype protector, an Array with
   holes shifts in its storage, holes staying holes, without the generic loop (the call table's
   holey shift: 3,000 ns an iteration against Sparkplug-only Node's 172).
5. The plan's other W1 items (bulk indexOf, lastIndexOf and includes; dense sort and fill)
   wait for a workload that spends time there: none of the acceptance set or Octane does.
   Proxy target and handler move out of the side table with W2g, as planned.
Exit (revised with the owner's agreement, Decision 9; the plan's was Vue's `shift` cut by
10x): the Proxy microbenchmark without handlers at or below Sparkplug-only
Node's time and with Reflect-forwarding handlers within 1.5x of it (today 1.33x and 1.8x); the
holey shift within 2x of it (today 17x); Vue's `shift` time recorded before and after; no
builtin above 5% of a workload's time on a generic path a fast path could take (met on the
acceptance set and Octane today).

Landed 2026-10-27: items 1 and 2 (863c0939, which also fixed six observable deviations, each
checked against Node) and 4 (a683d988). Item 3 dropped: after items 1 and 2, index formatting is
under 1% of the Proxy microbenchmark (intern_key 0.8%), whose largest cost is now the Proxy side
table's probes (18%, W2g's). Under load (no-LTO, least of 3 runs, ns an iteration): without
handlers 27,900 to 9,900 (Sparkplug-only Node 13,750), with Reflect handlers 48,250 to 26,450
(20,350), with direct handlers 22,400 to 17,400 (9,150). Exit measured 2026-10-28 and met
(Stage-exit timing).

### W7: strings (census and design, 2026-10-27)

The owner's Decision 7 put strings in P2. ECMAScript strings are sequences of UTF-16 code units
(ECMA-262 §6.1.4). The engine stored UTF-8 (lstr.rs: a 16-byte header {frontier, len, cap} with
an ASCII hint in cap's top bit, then the bytes; a view {header, owner, offset} for slices of 256
bytes and more), with lone surrogates as plane-16 scalars (jstr.rs, "smuggling"). Indexing needed
a UTF-16 view, which `Interp::units_of` built per string on first use and kept in a 16 MB,
64-entry LRU keyed by the cell's address (`str_units`), beside a `Utf8Index` for slicing; RegExp
widened non-ASCII subjects to 32-bit elements in its own 32 MB LRU (`re_texts`). Every new string
started cold, so code that slices or grows non-ASCII text rebuilt a view a step: quadratic.

Census (no-LTO 7495f76b on Crystal, under load; data and scripts in target/p2/strings-census):
- Web Tooling, whole suite (the close-out): 9.4% of user instructions copy UTF-16 views
  (`units_of`: substr 3.3%, `.length` 3.3%, indexed reads 2.4%). Alone, with the perf map,
  coffeescript spends 63% of its instructions there (`.length` 27%, charCodeAt-style reads 20%,
  slice 17%) and source-map 56% (substr 43%, slice's index 12%): the two largest gaps
  Sparkplug-only Node keeps on the suite (23x and 11x).
- micro/strings.js, 14 patterns over 200 KB of ASCII, Latin-1, CJK and astral text, against
  Sparkplug-only Node: a lexer re-slicing per token (CoffeeScript's `@chunk = code[i..]`) 18x on
  ASCII and about 5,500x on the others (33 s against 6 ms); an anchored RegExp on each remaining
  chunk 4.8x and about 3,700-5,700x; a `+=` accumulator read as it grows 0.5x on ASCII and

  1bf7973e), the default sort ordered by code point, not code unit (fixed, 9b224edd), and object

What the browsers do (their source at V8 756afdd7, Firefox d9098b3e, WebKit 780058db, read
2026-10-27): all three store code units at one of two fixed widths, Latin-1 bytes or UTF-16
units, and none stores UTF-8 (Ladybird's LibJS moved from UTF-8 to UTF-16 in June 2026; the
engines that keep UTF-8, Duktape, JerryScript, XS, rescan or keep a few cached offsets). The rules
they share: a buffer's width is fixed at allocation, and a concatenation is one-byte only when
both operands are stored one-byte (V8 factory-base.cc, SpiderMonkey ConcatStrings); they narrow
only text they are copying anyway; the length lives in the header; a substring shares its
parent's buffer above a small cutoff (V8 SlicedString::kMinLength 13; SpiderMonkey above its
inline sizes) and a view never points at a view; anything needing contiguous text flattens
first. They defer concatenation into ropes (V8 ConsString from 13 units); SpiderMonkey instead
reuses the leftmost buffer when flattening, which is the engine's in-place append. Hashes are
over code units whatever the width (V8 caches one in the header).

Design:
1. Representation: a string cell holds one-byte or two-byte code units. The header keeps its 16
   bytes and offsets: `len` counts units, `cap` holds the capacity in units below the two-byte and
   ASCII-hint bits, and a view's `cap` stays the reserved marker. Lone surrogates are ordinary
   two-byte units; smuggling survives only in engine text, at the text boundary. The capacity
   limit is 2^30 - 2 units; the JS-visible limit stays MAX_STR_LEN (2^26 units).
2. Widths as the browsers choose them: text converts to one-byte when every unit fits;
   a concatenation or in-place append is one-byte when both sides are stored one-byte (a two-byte
   suffix on a one-byte buffer copies into a two-byte buffer, after which appends are in place
   again); short copies narrow. Views keep the owner's width, never point at views, and keep the
   engine's pinning rule (a slice of an owner above 1 MiB that covers less than half of it
   copies). The view cutoff stays 256 bytes of content and is measured against V8's 13 units in
   S3.
3. Equality compares units across widths (identity, then length, then memcmp at equal widths).
   Hashes run over code units, so equal strings hash equally at either width. Relational
   comparison and sorting are unit order.
4. Text access: `Deref<Target = str>`, `AsRef<str>` and `Borrow<str>` go. `as_ascii()` lends a
   one-byte string as `&str` without copying; `text()` returns engine text as a `Cow<str>`,
   copying only a two-byte string; algorithms read `units()`. Property keys (Rc<str> until
   W2a's atoms, which become internalized string cells) borrow ASCII text and convert the rest.
5. What goes away: the UTF-16 view cache (`str_units`), the `Utf8Index`, the surrogate join
   fix-ups of concatenation and repeat, and RegExp's UTF-8 decoding: subjects are one-byte bytes
   or two-byte units, widened to the matcher's 32-bit elements only for two-byte subjects until
   W5 reads units directly.
6. Generated code: with one-byte storage holding exactly what the ASCII hint marked, the
   templates (length, charCodeAt, equality, truthiness) and the dumps stay as they are through
   the storage change. S4 extends `.length` and charCodeAt to every flat string.
7. The embedding API: `as_engine_text()` returns `Cow<str>`, borrowed for an ASCII string (TRust
   uses it 37 times); `string_from_engine_text` converts to the right width (60 uses). TRust's
   port lands with S2's validation, through its handoff checks.
8. Ropes are not in this stage: the in-place append already keeps `s += x` linear (and faster
   than V8 on ASCII); a census of concatenation copies after S3 decides on V8-style cons strings.

Staging the widths: the engine's fast paths assume that a byte of a "known ASCII" string is its
code unit, and the generated code's string templates take a string's bytes only under the ASCII
hint. S2 therefore stores ASCII text one-byte and every other string two-byte, so one-byte
storage is exactly the hinted ASCII case those paths and templates already handle, and `text()`
of a one-byte string always borrows. Latin-1 one-byte storage, the browsers' width rule in full,
is S4, once the remaining byte-level paths read storage by width.

### W2a and W2b: atoms and scope descriptors (design, 2026-10-27; going ahead, Decision 9)

Census (the close-out's GC logs, target/claude-closeout/final/gclog, TRUST_JS_GC_LOG; means per
minor collection; a read-only survey of the tree supplied the inventory, its claims checked):

| | minors | mark + sweep + engine (ms) | finalize (ms) | cells finalized |

| ARES-6 | 6,823 | 12.6 | 4.05 (32%) | 17,429 environments, 2,866 property-map extras, 2,854 layouts |
| Web Tooling | 5,066 | 25.6 | 1.24 (5%) | 13,449 environments, 4,842 layouts, 794 extras |
| Octane (partial log) | 396 | 6.5 | 0.40 (6%) | 4,398 environments, 2,105 extras, 581 layouts |

Environments are 75-85% of the cells finalized. Three findings change the plan's framing:
- Compiled code belongs to one Agent heap: a Chunk records its heap (bytecode.rs `heap:
  HeapLifetime`), its constants are that heap's cells, and FunctionRuntime picks code by the
  active heap; only the AST is shared, and it holds names as text. Chunks and native code can
  therefore embed per-heap atoms. A static table still pays, for the roughly 540 distinct names
  the engine itself spells (builtins, `length`, `prototype`, the internal `%...%` bindings), as
  V8's read-only roots and SpiderMonkey's permanent atoms do.
- Atoms can live as long as their heap at first: ShapeTable's transitions already hold a strong
  key for every (parent, key, class) a heap has seen, for its whole life, and every structural
  removal mints a fresh shape, so delete/insert churn already grows that table (and walks the
  process-wide shape ids toward exhaustion); permanent atoms retain nothing new for property
  keys. Index keys, which do die today, will not be atoms. Collecting atoms, with weak
  transitions and dictionary maps for churn, is a later series (with W2d).
- W2a and W2b do not touch Splay's live heap (its objects share layouts and allocate few
  environments): that part of W2's exit belongs to W2c and W2d.

Design:
- Atom: a Copy handle to an immutable, exact-size flat string cell in the Agent heap (an LStr
  header with no spare room, at W7's widths), compared and hashed by address, read like any
  engine string. `Value::Str` can wrap it, so enumeration, JSON and Proxy traps stop
  allocating a string per key. Pointer atoms rather than u32 ids: the conservative stack scan
  sees them, and their text needs no table lookup.
- PropKey: one word, an atom or a tagged canonical array index (at most 2^32 - 2), as
  SpiderMonkey's jsid; one constructor canonicalizes, so identity equality is complete and
  classic arrays stop allocating key strings for indices above 63.
- Each Agent heap keeps an atom table beside its interned strings, with a seeded hash (key text
  comes from scripts): `atomize` for names that will be stored, `lookup` for reads (text with no
  atom names no property, as V8's LookupExisting). Atom cells are allocated old. The static
  names are a process-wide read-only table seeded into every heap's, so `names::LENGTH` is a
  constant; a static atom is never handed out as a heap Value and is never traced.
- Heap atoms live only in heap-bound holders (chunks, FunctionRuntime, GcState tables, cells),
  never in the AST, script sources, snapshots or process-wide caches; debug builds check that a
  looked-up atom is static or belongs to the active heap.
- Environments: binding names become atoms, the environment cell loses its drop glue (the large
  table moves into a storage block, an import becomes a small cell holding its environment and
  name) and stops finalizing. Then ScopeDesc, one immutable descriptor per compiled scope, owned
  by its chunk: ordered names, static flags (const, strict immutability, lexical at this level,
  import), the existing layout id the name caches and native guards use, and an index past 8
  bindings. An environment holds its descriptor and its binding values; a Binding without its
  name shrinks from 40 to 24 bytes and a one-binding environment from the 128-byte to the
  96-byte class. Creating one copies argument words instead of cloning names, the template W3's
  direct sequence needs. Sloppy direct eval, deletable eval bindings, the global declarative
  record and module imports copy on write to a private descriptor, as property layouts do.
  `with` keeps resolving through its object; eval's private-name scan, TDZ messages and memory
  accounting read names through the descriptor.
- Property layouts: keys become PropKeys in a traced storage block, the index an open-addressing
  table there, and layouts stop finalizing.
- Generated code: name compares become one word compare (the ARM64 key-checked arm and creation
  cache, references on both backends), and the binding and layout strides and offsets change.

Design (gains are shares of today's instructions):
1. Prefilters: at compile time, the longest literal every match contains and its offset range
   from the match start (re17: `"\/Qngr(` at 0-1); exec finds it with a NEON scan over bytes or
   units and tries only starts in range, and its absence ends the search. The first-element
   scan gets NEON too (byte equality, 128-entry ASCII tables). Octane 1.7-1.9x.
2. A RegExp protector: a realm proof, epoch-keyed like the array protectors, that
   %RegExp.prototype%'s `exec`, flag getters and symbol methods, %RegExp%[@@species] and the
   `constructor` link are the intrinsics. Value writes to those objects bump the epoch too
   (today only structural changes do: the objects are flagged, store caches decline them and the
   slow store path bumps). A receiver is fast when it has the realm's initial RegExp shape and
   prototype. String.prototype's methods then enter the RegExp algorithms directly and
   RegExpExec calls RegExpBuiltinExec without the Get of `exec`. Removes the guards, the @@method
   dispatch and the generic exec call: source-map 12%, Octane 7.8%, Djot 2.6%.
3. Payload and entry: `Exotic::RegExp(PayloadBox<..>)` holds the shared program (P1's Map/Set
   pattern; W2g's RegExp part). `lastIndex` stays an own data property at the initial shape's
   slot, read and written directly under 2's proof; the legacy statics keep the constructor
   cached; the matcher's scratch lives in the Interp, sized per program, capture slots reset
   through the undo log rather than filled per attempt, flags precomputed. Removes the
   `regexps`/`gc_pins` traffic, string-keyed `lastIndex` access and entry overhead: Octane 8%,
   Djot 5%, strings 20%, source-map 4.5%.
4. Subjects in place: the matcher reads one-byte storage as bytes and two-byte storage as units,
   decoding surrogate pairs in /u and /v as it steps, positions in units throughout; ReText, its
   32 MiB LRU and the unit-element maps go (W7's item 5). Strings 14%, Djot 2%, Octane 1.4%.
5. Captures from storage: captures, split pieces and replace arguments as slices of the subject
   at its width (views above V8's 13 units), with no Rust String or UTF-8 round trip. Octane
   2%, Djot 1%, strings 8%.
6. `match` with /g, `search` and `matchAll` without match arrays, on 2's proof: for
   completeness, after 2.
7. Case closure at compile time, with the native tier, which needs closed classes (`v`-mode
   class sets are already closed under `i`, 05e1f798).

- Sparkplug's call is a builtin call: `BaselineCompiler::BuildCall` (baseline-compiler.cc:1713-
  1729) calls `Call_ReceiverIs*_Baseline_Compact`, which loads the feedback vector from the
  caller's frame and runs `CollectCallFeedback` (ic-callable.tq:91-168: increment the call count,
  then return if the slot holds this target), then tail-calls `Call` and `CallFunction`
  (builtins-arm64.cc:2373-2450, 2944-3024) and `InvokeFunctionCode` (macro-assembler-arm64.cc:
  2884-2948), which pads missing arguments with undefined in place and jumps to the callee's
  dispatch-table entry. The callee pushes its frame (fp, lr, then in `BaselineOutOfLinePrologue`
  context, closure, argc, bytecode array, feedback cell and vector; builtins-arm64.cc:1147-1259)
  and makes one stack check against a limit that also signals interrupts (:1224-1233); the
  interrupt budget is charged at loop back-edges and returns, not at entry (baseline-compiler.cc:
  2638-2720, 2903-2911). new.target travels in x3, undefined for a call (macro-assembler-arm64.cc:
  2908); there is no frame stack beside the machine stack (frame-constants.h:744-785) and no
  ambient strictness. Maglev's `CallKnownJSFunction` skips `Call` and `CallFunction` altogether:
  it pads at the site and calls the dispatch entry (maglev-ir.cc:7434-7470).
- A function with context-allocated variables makes its own context: `CreateFunctionContext`
  (bytecode-generator.cc:8719-8744), in Sparkplug a call to `FastNewFunctionContextFunction`
  (constructor.tq:63-73): one new-space allocation of map, length, ScopeInfo, previous and the
  slots, filled with undefined (builtins-constructor-gen.cc:381-469); bytecode then copies the
  captured parameters (bytecode-generator.cc:8746-8770) and writes the TDZ hole at each
  declaration (:2139-2183). Slots are tagged words; modes and flags live in the ScopeInfo
  (scope-info.tq:101-108), which slot 0 of the context names (contexts.h:545-577).
- Builtins are machine code entered like JavaScript functions (TFJ/Torque): Map and WeakMap
  get/has/set, Array.isArray, Object.is, Reflect.get and has, String includes and substring,
  RegExp exec, parseInt and Number all are. Only C++ builtins (Reflect.set among these) pay a
  boundary: an adaptor and `CEntry`'s exit frame (builtins-internal-gen.cc:1337-1402,
  builtins-arm64.cc:4749-4926). WeakMap.get is one EphemeronHashTable probe by the key's stored
  identity hash, and a key without one returns undefined without creating it
  (builtins-collections-gen.cc:3036-3056, 2742-2760, 2828-2857). The embedder's boundary, API
  callbacks, is the heavier one (an exit frame and `FunctionCallbackInfo`, builtins-arm64.cc:
  5081-5232): the engine applies the equivalent of that boundary to its own builtins.
- A call slot holds a weak target, a FeedbackCell (closures of one literal) or the megamorphic
  sentinel, plus a call count and a SpeculationMode (feedback-vector.h:1115-1118;
  ic-callable.tq:22-50, 134-149). Maglev and TurboFan check the target and reduce known builtins:
  ArrayIsArray, ObjectIs, ReflectGet and Has, MapPrototypeGet, StringPrototypeIncludes,
  NumberParseInt (maglev-reducer-inl.h:1258-1299, 3152-3156; js-call-reducer.cc:5382-5815), and
  use count / invocation count as call frequency (feedback-vector.cc:1158-1167).

Design (gains are shares of today's instructions; per-call counts are the census's):
1. A cheaper direct call (ARM64), from 257 instructions beyond the body to about 140:
   a. The static gates (compiled entry, frame size, the global-body need, a sloppy callee's
      object receiver) fold into one ready bit at fill, and the sequence counts the callee's runs
      itself, so the inline-attempt warm-up gate goes: 30 to ~10.
   b. new.target and the construct flag live in the callee's record, as V8 passes new.target in
      a register; an ordinary call stores Undefined there and the sequence stops saving, clearing
      and restoring `Interp::constructing`/`new_target`; natives that read new.target take it from
      the boundary (2): 31 to ~4.
   c. The callee frame: save only the callee-saved registers the chunk uses, read strictness from
      the running chunk instead of an ambient `Interp::strict` set and restored by every
      prologue and epilogue, and find running code by walking the live frame records when code is
      reclaimed instead of counting residency per activation; one entry check: 59 to ~30.
   d. The finish stub checks one dirty bit that the slow paths set (pending tail call,
      materialized activation, `FnFrame` extra, operands left), not five fields; the callee
      context reads the chunk's constants instead of copying them; the record pool pops and
      pushes by index: 86 to ~45.
   Gains (117 instructions a direct call): React 9.4%, chai 1.7%, Djot 1.5%, Vue 1.3%; on the
   call table, the direct, method and closure cases' instructions an iteration fall to 1.13,
   1.10 and 1.23 times Sparkplug's, recursion to 1.48. Risks: code reclamation must see every
   running chunk (records, Rust entries, borrowed frames: the collector already registers each
   active context); every reader of `Interp::strict` and `new_target` moves. Dumps: every ARM64
   chunk's prologue and epilogue, every call site's sequence, the finish stub.
2. Natives without the full boundary (both backends, the helper):
   a. Native classes recorded at registration, not pointer lists: pure (Array.isArray, Object.is,
      Number.isNaN-style predicates, Math, the collection methods), primitive-pure (no author
      code when the receiver and arguments are primitives: parseInt, parseFloat, Number, String
      and Boolean called as functions, String.prototype's slice, substring, indexOf, includes,
      startsWith, charAt, trim and case mapping; Array.prototype.indexOf and includes on arrays
      the element protector covers; RegExp exec and test while W5's protector, 753d3aa2, holds),
      and the rest. The helper runs pure and primitive-pure natives on the operand window as the
      operand-only path does now; only natives that read new.target keep that clear. A native
      that usually runs no author code but may (Reflect.get, set and has through a getter or a
      Proxy) runs its fast path first and enters the boundary only on the path that calls out.
      Gains: Vue 3.8% (Array.isArray, Object.is, parseInt and Number 2.6%, Reflect 1.2%), chai
      5.2% (slice 3.0%, Array indexOf 1.1%, Reflect 0.9%), Djot 1.7%.
   b. The intrinsic helper's fallback takes the same light path for its pure intrinsics: chai
      ~2.8% (25.3M entries), Djot ~2.5% (276,060), Vue 0.4%.
   c. Templates, after the IC's identity proof (non-speculative, unlike Maglev's reductions):
      Array.isArray and Object.is in line (Vue ~1%), Math.min and max with three or four
      arguments (chai 1.9%), String.prototype.slice with one argument beside the existing
      two-argument intrinsic (chai ~1%), codePointAt on two-byte strings with W7's S4 (Djot
      ~0.3%).
   d. Natives' own algorithms, for their owners: WeakMap get and has as one probe in a payload
      (W2g's pattern; Vue 2.7%), Reflect.get, has and set sharing the property-get path (Vue
      3.7%, chai 2.7%; their key conversion changed with W2a's step 6, property keys as
      PropKeys, d3c66d56), dense indexOf (W1's deferred bulk indexOf now has a workload: chai
      4.3%), the string searcher's setup (Djot 0.5%).
   Risk: a misclassified native skipping the boundary while it can run author code; debug builds
   assert that nothing on the light path reaches `Interp::call`. No dump change apart from 2c,
   whose stubs gain arms.
3. The closure entry: a callee that needs an environment builds it in its prologue, as V8's do:
   allocate the cell its ScopeDesc sizes (a lean helper first, W2e's inline allocation later),
   link the closure's environment as parent, copy captured parameters from the argument slots,
   fill vars with Undefined and lexicals with the empty word, and install it as the frame's
   environment. W2b's descriptors make that a copy of words. Bindings become 8-byte slots (TDZ as
   the empty word; mutability and strictness in the descriptor; deletable eval bindings and
   imports in private descriptors, as W2b planned), aiming at the 64-byte class for one binding.

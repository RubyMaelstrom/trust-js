# Phase 2 plan: baseline strengthening (2026-10-26; the owner's decisions of 2026-10-27)

Program: [docs/v8-chase-2026-10-15.txt](/big/Code/trust-js/docs/v8-chase-2026-10-15.txt).
Phase 1's plan and record, including its close-out:
[docs/v8-chase-p1-plan-2026-10-15.txt](/big/Code/trust-js/docs/v8-chase-p1-plan-2026-10-15.txt).
Citations are to the tree at the close-out (main after it merges); re-verify them when touching
code. This plan is the design record P2 needs before code, as P1's was.

## Goal

Make the existing tiers (the AST interpreter, the bytecode VM and the template JIT) and the
object model cheap enough, and make what they record complete enough, that Phase 3's
speculative optimizing tier (inlining, type speculation with deoptimization, escape analysis)
starts from a sound base; and close the gaps to Node/V8 that do not need speculation. The
program defines P2 as "call path (frame/argument costs), feedback completeness for the future
tier, builtin algorithmics (shift class), RegExp"; P1's closing record assigned P2 the object
layout costs its collector still carries. This plan covers both.

Acceptance surface, unchanged from the program's Decision 1: the Vue, React and Djot fixtures
and Speedometer 3.1 against Node/V8 on Crystal (ARM64), x64 on zombie secondary. New standing
comparisons from the close-out: full Octane 2, the Web Tooling Benchmark, ARES-6 and a call-path
microbenchmark set (the harness and suites are under target/claude-closeout; see "Measurement").

The yardstick is Node limited to its non-speculative tiers, Ignition and Sparkplug
(`--max-opt=1`). Node's lead on the fixtures does not depend on speculation: limited to
Sparkplug it runs them 3.4-3.8x faster than the close-out, against 2.9-3.9x in full (Node by
tier, below). Phase exit: each fixture within 2x of Node limited to Sparkplug, measured in the
same session (Decision 2).

What the numbers say:
- The close-out is the fastest of the three engines on every suite: Octane +6.9% over main
  (Splay +28%, RegExp +25%, SplayLatency +21%, EarleyBoyer +16%, PdfJS +10%; nothing slower
  than 0.3%), Web Tooling +31% with every tool faster, ARES-6's summary 2.8% lower (Babylon's
  steady state 13% lower; Basic 2-5% and Air's first iteration 1-4% slower), Djot -6%, TRust's
  replays 5-14% faster; the call microbenchmarks did not move (within 3%). Against the old
  engine it trails by more than 2% only on Splay (-15%), SplayLatency (-40%) and CodeLoad
  (-8%): major-collection pauses and the object layout (W2, W6).
- Node leads by 3-4x on the fixtures, 10x on ARES-6, 12x on Web Tooling and 3.4-34x on
  Octane's benchmarks. Limited to Sparkplug, it keeps all of its lead on the fixtures
  (3.4-3.8x) and leads by 4.2x on ARES-6 and 4.8x on Web Tooling, but by 1.8x on Octane's
  geomean, where the close-out is faster on Crypto (4.7x), NavierStokes (1.5x) and
  SplayLatency (1.4x) and level on Richards: most of Octane's gaps are speculation's (P3). The
  gaps Sparkplug-only Node keeps are this phase's; the largest: Web Tooling's coffeescript
  (23x) and source-map (11x), not yet attributed; the holey shift (17x) and spread calls (14x;
  W1, W3); RegExp (11x; Irregexp, W5); the other Web Tooling tools (2.8-6.7x); EarleyBoyer,
  Typescript, Gameboy and Box2D (2.1-3.5x). zlib's 22x does not move with the tier: V8 runs
  its asm.js module (zlib-data.js, "use asm") as WebAssembly.
- Memory: V8's sizing raises peak RSS where allocation is heavy: against main, Octane +10%,
  Web Tooling +41%, ARES-6 +56%, sustained allocation +45%, Octane through TRust +78%.
  Node's peaks are 3.7x (Octane), 3.4x (Web Tooling) and 1.6x (ARES-6) lower; its objects
  are smaller (W2). V8's cap of each limit at halfway to its heap maximum, which the
  close-out did not port, would bind only on Web Tooling: the close-out's largest live heap
  after a major collection (cells and their external payloads, TRUST_JS_GC_LOG; logs in
  final/gclog) is 1027 MB there, 458 MB on Octane and 39 MB on ARES-6, and the cap binds
  above ~585 MB (Decision 5).

### The code (survey of the close-out tree)

Call path.
- Generic entry (natives calling back, VM calls, uncached sites): `Interp::call`
  (interpreter.rs:12286) roots arguments, checks depth/stack/GC; `call_dispatch` (12491)
  probes the proxy side table and, once any class exists, the `class_info` hash map on every
  call (12593); bound functions concatenate a new Vec per call (12604); `call_user_inner`
  (15032) counts calls, compiles at threshold 8, runs `run_compiled_chunk` (13220).
- Prepared entries (sloppy `arguments` with non-simple parameters, eval/with, destructuring
  rest, unsafe defaults; bytecode.rs:6562-7115) allocate one var scope per call (three with
  parameter expressions), a `"this"` string when the body reads `this` (15235), and an
  arguments object or a boxed stash (15253, 15264).
- The VM's `Op::Call` ignores the call cache and re-enters the generic chain
  (bytecode.rs:17329-17364); rest parameters are `to_vec` + `make_array` (15361); an
  activation is built only when an inner function captures (bytecode.rs:3418), and
  `ActivationPlan::instantiate` clones every `(Rc<str>, Binding)` entry
  (bytecode_activation.rs:145-205).
- ARM64 JIT: a 4-way identity cache per site (bytecode.rs:1262; jit.rs:7340-7470) and a direct
  sequence (jit.rs:7596) that allocates nothing, but declines callees with an activation or
  any `arguments` slot (`CALL_IC_NEEDS_ENV`, bytecode.rs:1013), which is most framework code.
  Native calls from JIT pay depth/stack/GC checks, two interrupt polls and a host-callback swap
  (interpreter.rs:13841); ~30 intrinsics are inlined (bytecode.rs:1033-1084). Spread and
  args-array calls have no cache (bytecode.rs:16841-16880; spread.rs:129-190). x64 calls go
  through the `H_CALL` helper (jit_x64.rs:1227).
- Inlining is guarded bytecode splicing only (InlineGuard, bytecode.rs:17242; recompilation
  after 100 machine-code runs, budgets 320/384 source ops, an allowlist without closures,
  handlers, activations or `super`). The optional Cranelift tier was removed before P1
  (6b210624, 2026-10-15); docs from 2026-10-14 that cite `jit_optimizing*.rs` are history.
- Microbenchmarks (the call table): against Node limited to Sparkplug, its non-speculative
  baseline, the direct, method and closure calls take 1.5-1.9x as long, the constructor and
  recursion 2.1-2.2x, the argument shapes 3.2-4.4x, `call`/`apply` 3.7x, the getter 6.9x and
  spread 14x. Full Node inlines the method, `arguments`, rest and getter cases (about 1 ns an
  iteration).

Feedback.
- feedback.rs defines a versioned per-function schema (named/element loads and stores, call,
  construct, arithmetic, branch, loop, allocation; feedback.rs:46-187) with mono/poly/absent/
  generic states (373). Collection is opt-in (`TRUST_JS_FEEDBACK_PROFILE`, feedback.rs:28) and
  reroutes JIT templates through helpers (jit.rs:3940); nothing reads it in production (`read`
  is cfg(test), 1454); inlined or recompiled chunks write nothing (733-741). The schema file
  feedback.rs:3 names (FEEDBACK_SCHEMA.md) does not exist.
- What the tiers consume are their inline caches: the 4-way property IcState (up to 6
  prototype levels, bytecode.rs:87-139, baked into JIT probes jit.rs:5895-5946), call caches
  (whose way count the inliner reads), name/capture caches, creation caches, construct
  capacity hints, per-array mirror flags.
- A speculative tier would still lack: feedback that is on by default; comparison, `in`,
  `instanceof`, `typeof`, free-name, captured-variable, iteration and for-in sites; call-target
  identity, megamorphic state and per-way counts; elements kinds (packed/holey x int32/double/
  any); allocation-site records (boilerplate, kind transitions, survival, for pretenuring); a
  PC map through inlining; shapes as a proof (value.rs:5378, Pilot C unfinished); dependency
  records for invalidation.

Builtins (the "shift class").
- Packed elements are 16-byte `Property` words (10 inline, value.rs:5633; then a deque with
  front room, dense_deque.rs:15-25); holes are `Value::Empty`. Packed storage starts only at
  creation or a first write at index <= 256 on an empty array (value.rs:7836-7844); a farther
  write sets `has_far` (9120) and nothing converts a classic array back.
- push/pop are O(1) under the prototype protector (interpreter.rs:8353-8397); `shift` is O(1)
  for a packed, all-plain array (value.rs:8408), else an O(n) rotation, else the generic loop
  (builtins/mod.rs:6311) that formats a string key per index. unshift/splice/reverse need
  packed all-plain storage; indexOf/lastIndexOf/includes (6413), sort (6835) and copyWithin
  have no bulk path; partial fill sets per index by string key (6749). A delete writes Empty in
  place (9242) and fails every all-plain guard until refilled.
- Vue's cost is not storage: the fixture shifts `model.items` (benchmarks/fixtures/vue.js:41,
  54), a Vue `reactive()` Proxy, so the generic loop runs 50+ trap calls per shift, each with a
  freshly allocated key string (value.rs:1286). On the close-out, `shift` is ~47% of Vue's
  elapsed time (671 calls, ~275 us each; TRUST_JS_PERF_METRICS).

RegExp.
- A backtracking matcher over a flat instruction program with a heap stack (regex.rs:1-12,
  `run` ~5714); case folding at match time; literal and first-element fast paths (2376); a
  one-byte tier after 64 executions for capture-free, alternation-free programs (machine code
  only without anchors, and on AArch64 without classes; regex.rs:1129-1167). The close-out
  fixed that tier's anchors (/a^/ matched "a" after 64 runs).
- Prepared subjects: one hot ASCII entry plus an LRU of widened subjects (32 MiB / 8,192
  entries, interpreter.rs:3398); views of ASCII strings match as bytes since the close-out.
  Exec results share one pre-shaped layout per kind (close-out); each capture is still a fresh
  string copy (builtins/mod.rs ~2516).
- Fixed per-call costs: `regexps` hash lookups, a string-keyed `lastIndex`, ~20 guard lookups;
  every RegExp creation inserts into `gc_pin` and `regexps` (eval.rs:5477-5494), whose removal
  is now the largest per-minor-collection cost on Octane RegExp (~66 us of ~180 us). `match`
  with /g, `search` and `matchAll` build throwaway match arrays; no required-literal prefilter.

Object model and collector.
- The object cell is `RefCell<Object>` <= 192 B in the 192 B size class (value.rs:4069-4072):
  proto; `Props` with 4 inline 16-byte slots, a layout pointer, a u32 shape, a 2-word element
  sidecar, mirror flags, `has_far`, `elem_mode`, two slot memos; a 16-byte `Callable` that only
  functions need; an `Exotic`; a typed-array pointer; flag bytes. A fifth named property moves
  all fields to a spill block (inline_vec.rs:3-7). A 1-element array is a 192 B cell plus a
  ~256 B element block. V8's JSObject is 12 B plus 4 B per in-object field (pointer
  compression).
- Property layouts are GC cells holding `Vec<Rc<str>>` and run finalizers (value.rs:3185);
  environments (`Scope`, 128 B class) hold 40-byte `(Rc<str>, Binding)` entries and run
  `finalize_scope_cell` (value.rs:3621). Shape ids are process-wide; transitions per heap.
- The write barrier stores two bytes (card and page summary, gc_core.rs:110); a minor collection
  reads every carded page's summary (~0.4 ms per minor on Splay's ~480 MB heap). Generated code
  allocates only through helpers followed by a poll (jit.rs:1973-2003, 16982).
- Exotic state still lives in address-keyed side tables (proxies, promises, generators,
  `class_info`, mapped arguments, regexps, typed arrays; interpreter.rs:3423-3756).
- Heap sizing follows V8 since the close-out (`gc_pacing.rs`): dynamic growing factor 1.1-4,
  nursery 2-32 MiB, the memory reducer. Splay's heap peaks at twice P1's because of that
  factor; its live heap (~246 MB) is the layout's doing. Not ported: V8's cap of each limit
  at halfway between the live size and the heap maximum (heap-controller.cc,
  `BoundAllocationLimit`), since the engine has no maximum (V8's old generation may reach
  half of physical memory, clamped to 256 MB-4 GB on 64-bit desktop hosts, heap.cc
  `OldGenerationSizeFromPhysicalMemory`; Node reports a 4288 MB limit here). With a 4 GB
  maximum the cap binds only above ~585 MB live (4L > (L + 4 GB) / 2).

## Workstreams

W1. Builtins and Proxy-heavy paths (first: the largest single measured win)
- Index keys without allocation: the generic algorithms take numeric keys (interned index
  atoms or an index key variant) instead of formatting strings; Proxy trap calls pass them.
- Cheaper Proxy traps: a trap call from a builtin's generic loop without the full call chain's
  per-call checks (still observable-equivalent: the trap is a user function).
- Holey fast paths under the existing protector (holes stay holes), in-place deque splice
  (no whole-array copies, dense_deque.rs:227-236), bulk indexOf/lastIndexOf/includes, dense
  sort and fill; a census of generic-path hits on the acceptance set picks the rest.
- Exit: Vue's `shift` time cut by 10x; no builtin in the acceptance set spends more
  than 5% of a workload's time on a generic path that a fast path could take.

W2. Object model, second pass (layout and the collector's remaining costs)
- W2a Atoms: property keys and binding names interned per Agent heap (with a static table for
  the names compiled code embeds, since ASTs are shared across Agents), compared by identity;
  layouts and environments stop finalizing (the P1 record: a fifth of the sustained workload's
  minor collection time).
- W2b Per-chunk scope descriptors: environments index slots through a shared descriptor (V8's
  ScopeInfo, JSC's SymbolTable) instead of owning `(Rc<str>, Binding)` entries; eval/with and
  reflection keep a name path through the descriptor.
- W2c Elements as 8-byte words under a per-array "all plain" kind (the proof exists,
  value.rs:5640); a non-plain element moves the array to a dictionary representation (V8's
  elements kinds). Halves arrays; one load per JIT element read.
- W2d A slimmer cell: `Callable`, the typed-array pointer and mirror state move to kind-specific
  payloads, flags pack, only the overflow spills; then either the 128 B class or more inline
  slots at 192 B, chosen by allocation-site slack tracking (V8's).
- W2e Inline allocation in generated code: cursor take, byte charge and template copy, keeping
  the poll after allocation.
- W2f A chunk-level card summary (one more barrier store in both backends).
- W2g Exotic state into payload cells, as P1 did for Map and Set: proxies, promises, generators,
  `class_info`, RegExps (with W5), typed arrays.
- Exit: Splay's live heap halved; fixtures' peak RSS at or below the close-out's;
  the sustained workload's minor collection time down by the finalizer share; JIT dump checks
  unchanged apart from intended layout changes.

W3. Call path
- Measure first (TRUST_JS_JIT_CALLSTAT, DIAGNOSTICS.md) which direct-call misses dominate on
  the acceptance set; the code alone does not size them.
- The direct sequence's own cost: the bare call takes 41 ns an iteration against Sparkplug's
  22, though all but 872 of its 5,001,000 calls take the direct sequence
  (TRUST_JS_JIT_CALLSTAT); count what each call executes (the JIT dump) and trim it.
- A class-constructor bit on the function object instead of `class_info` probes on every call
  (interpreter.rs:12593, 14860, 15067).
- With W2b's descriptors: slot-indexed environments that the direct sequence or a lean helper
  builds, so functions with closures take the direct path.
- `arguments[i]`, `arguments.length` and rest length served from the caller's argument window
  (which the moved-frame entry already keeps alive, jit.rs:17937); mapped arguments as a slot
  map in the object.
- Call caches for the VM's `Op::Call` and `CallSpread`, and bound-function cache entries.
- A lighter native boundary for natives that cannot re-enter JS.
- Exit, against Node limited to Sparkplug on the call table: the direct, method,
  closure and constructor calls and recursion within 1.25x (today 1.5-2.2x); `arguments`,
  rest, `call`/`apply`, spread and the getter within 2x (today 3.2-14x); Vue/React elapsed
  improved by the measured call share.

W4. Feedback for the speculative tier
- Always-on value classes for arithmetic and comparison sites, written only on VM and miss
  paths; a production read API; the schema documented in the tree (tracked .txt).
- Call-target identity exported from CallSite; elements kinds from the mirror flags; a
  megamorphic state.
- Allocation-site records keyed by allocation PC, with survival counted at minor collections
  (boilerplates, slack tracking for W2d, and pretenuring: Splay-like workloads promote nearly
  everything they allocate).
- PCs of inlined and recompiled code mapped to their baseline sites.
- Finish Pilot C (descriptor classes as a proof) and add a dependency registry for
  invalidation.
- Exit: feedback on by default at <= 2% cost on the acceptance set; coverage (share
  of executed operations with usable feedback) reported as a standing metric and >= 95% on it.

W5. RegExp
- Slice-view captures; direct paths for `match` with /g, `search` and `matchAll` (no
  throwaway arrays); a protector bit replacing the per-call guard lookups; the compiled program
  and `lastIndex` in the RegExp's own payload (no `regexps`/`gc_pin` hashing per exec and
  creation, which also removes the largest per-minor cost left on Octane RegExp); case closure
  at compile time; required-literal and NEON prefilters.
- Then a native tier with captures and alternation on both backends, behind a differential
  gate against the interpreter (Decision 3; V8's Irregexp, which SpiderMonkey shares, and
  JavaScriptCore's YARR JIT compile RegExps to machine code); the measurements set the order.
- Exit: Octane RegExp and Djot's `exec` time each cut by 2x from the close-out.

W6. Collector scheduling
- V8's cap (Decision 5): each limit at most halfway between the live size and V8's heap
  maximum (half of physical memory, 256 MB-4 GB; heap-controller.cc `BoundAllocationLimit`,
  heap.cc `OldGenerationSizeFromPhysicalMemory`), for pacing only, without V8's out-of-memory
  failure at that maximum. Independent of the other workstreams.
- Incremental marking (Decision 4): a marking write barrier in the interpreter, the VM and both
  JIT backends, and major marking in slices interleaved with the program, as V8's incremental
  marking runs; after W2's layout work, so that P3's tier emits the barrier from its start.
  Concurrent marking stays a non-goal.
- Exit (proposed): the cap's limits match V8's rule in unit tests and lower Web Tooling's peak
  RSS, with no suite slower beyond noise; marking's exit is set in its design note, with
  SplayLatency at least the old engine's (6446) as the target.

W7. Strings (Decision 7)
- Store strings as code units at the browsers' two widths instead of UTF-8 with UTF-16 views
  built per string on demand, whose cliffs make Web Tooling's two largest gaps (see the stage
  record); fix the string deviations the survey found.
- Exit: in its design note.

   (`perf record -e instructions:u --call-graph fp --user-callchains`); without that flag perf
   also asks for kernel call chains, which this setting refuses even for an event that
   excludes the kernel. Only kernel-side samples (page faults, the collector's mmap, madvise
   and munmap) would need paranoid <= 1. Generated code shows as bare addresses: the engine
   writes no perf map.
1. Branching: each commit series lands on main as soon as its gates pass, without a stage
   branch; stage exits are measured on main.
2. The exit numbers as proposed: the phase's (each fixture within 2x of Node limited to
   Sparkplug, measured in the same session) and each stage's (above). A stage's design note
   may revise its own numbers with the owner's agreement.

   interpreter-level stage, behind its differential gate; the measurements set the order.

   tier emits the barrier from its start. V8 marks incrementally and concurrently; the
   close-out pays full major pauses (Splay's are ~85 ms).

   memory, 256 MB-4 GB), for pacing only, without V8's out-of-memory failure at the maximum
   (W6). V8's sizing, adopted in the close-out, trades peak RSS for throughput on
   allocation-heavy workloads (against main: Octane +10%, Web Tooling +41% to 4.67 GB,
   ARES-6 +56%, sustained allocation +45%, Octane through TRust +78%). Of the standalone
   suites the cap binds only on Web Tooling (live heap up to 1027 MB); the other increases
   come with the growing factor and the nursery, and W2's smaller live heaps are the answer
   to them.
6. agent/jit-arith (403b7681) and agent/jit-calls (23050aaf) deleted on 2026-10-27, with the

8. Testing (2026-10-27): tests are a diagnostic tool, run in full at the end of a major phase or

9. After W7 (2026-10-27): W7 lands on both mains; W2a and W2b follow (their design draft
   goes ahead), with W5's interpreter-level stage alongside under its drafted exit (see W5's
   stage record); W1's revised exit is accepted; the heap cap ports V8's two remaining rules
   (the floor of size + 8 MB past the maximum, and MaxGrowingFactor).
10. After W2a and W2b (2026-10-27): W3's drafted exit is agreed: recursion within 1.6x of
    Sparkplug-only Node, the plan's other call-table bounds, and pinned instructions on main at
    the stage's end, React -8%, Vue -6%, Djot -4%, Web Tooling's chai -10%. W3 takes its item

    The exits of W1, W6a, W7, W5a and W2a/W2b are timed on a quiet machine before W3's builds.
    The merged stage worktrees, branches and build trees are deleted.
11. The function-entry poll (2026-10-28): V8's shape. The allocator raises the heap's due word
    when the live count passes the threshold, cancel and navigation requests set a word the
    poll reads, and a watchdog thread sets it when a deadline expires, so entries and loop
    back-edges test one word (12 instructions today, about 4). Collections still run at the
    next safepoint. Built, measured and gated as its own series.
12. The call probe's exhausted-epoch guard (2026-10-28) is dropped: the fill refuses u32::MAX,
    and debug builds assert it there.
13. W5b's exit (2026-10-28) is accepted as its design note drafted it; the note's census,
    design and exit move into this plan, and W5b's native tier continues.

    2.36 or later where they run.
15. The worktrees and branches of landed series are deleted (2026-10-28).
16. Constructions count toward their constructor's inline checkpoints, as calls do
    (2026-10-28).
17. Getters in code compiled before a read site's cache saw an accessor (2026-10-28): as V8's
    load builtin, SpiderMonkey's CacheIR stubs and JSC's data ICs do, the shared property stub
    takes the getter case at run time, with the site's getter call cache made lazily; no
    recompile, no growth at the sites.
18. The deadline watchdog (2026-10-28) follows Node's per-run thread, kept for bursts: the
    first armed deadline starts it, it serves the deadlines that follow, and it exits after a
    few seconds with none armed. A thread per deadline measured 36-90 us of the JS thread's time
    on Crystal, which TRust's URLPattern matching would pay on every match.
19. ShadowRealm code is interruptible by the host, as in V8 (2026-10-28): a ShadowRealm's
    interpreter shares its creator's interrupt handle, and an interruption passes through
    `evaluate` instead of becoming a TypeError.
20. W3 item 3's design (2026-10-28, on its design note's open questions):
    a. Step 1 first: a callee that needs an environment builds it in its prologue on today's
       representation; the representation change follows as its own series.
    b. The environment record keeps every binding in line, in a cell its scope descriptor sizes,
       as V8, SpiderMonkey and JSC do.
    c. Captured parameters: the helper copies them during step 1, and generated stores take over
       as soon as bindings are fixed slots.
    d. Every ARM64 call site passes the argument count (one instruction), as V8 does.
    e. `arguments` and rest arrays are elided when a compile-time proof shows every use is a
       length or element read (no run-time placeholder): a formal's index reads the parameter
       slot, an out-of-range read goes through the prototype. The exemplars leave this to their
       optimizing tiers; TRust JS has one native tier.
    f. Mapped arguments alias environment slots (step 6), as all three engines do; the side
       table goes.
    g. TDZ checks on a function's own captured lexicals are elided after the first in each
       basic block, as SpiderMonkey does; inner functions keep theirs.
    h. Derived constructors and instance elements are a series of their own, after item 1b's
       full form (new.target in the frame record).
21. Captured names resolve statically, as (hops, slot) with guards only under sloppy direct eval
    and `with` (2026-10-28): a new item after item 3's representation change.
22. Sloppy bodies with formals whose `arguments` the proof covers are elided in step 6, not step 1
    (2026-10-29): their exact mapped object, which a non-index key or a prototype getter can
    demand, must alias the parameters while the frame runs, so the parameters live in the
    environment, as V8 forces them into the context (src/ast/scopes.cc:2650-2690).
23. Immediates out of an instruction's range (2026-10-29): the ARM64 encoders accept any offset, as
    V8's, SpiderMonkey's and JSC's macro-assemblers do, instead of relying on each template's
    guard. The design follows an investigation of a scoped scratch-register allocator like V8's
    UseScratchRegisterScope (macro-assembler-arm64.h:2556-2640, over ip0 and ip1), and covers the
    JIT's and the RegExp tier's encoders. The design found reserves no register: see "Immediates
    out of an instruction's range" below.
24. W3 item 3's steps 2-3 (2026-10-29): their minor regressions are accepted as a step toward
    steps 4-6 (benchmarks/README.md's policy). Records made name by name cost arguments-mapped-call
    +2.1% and derived-construct +0.17% on ARM64 (x86-64 +2.0% and +0.96%); steps 4-5 bring them
    to +1.2% and -0.7%, and step 6 takes the mapped body off the prepared entry.

## Non-goals

Speculative optimization, inlining beyond today's guarded splicing, deoptimization (P3); moving
or compacting collection; concurrent marking;
startup snapshots (P4); Speedometer acceptance beyond the replays.

## Risks

- Atoms and scope descriptors (W2a/W2b) touch every name path, eval/with and reflection; the
  ShadowRealm and multi-Agent cases (shared ASTs) need the static name table to be sound.
- Element words (W2c) change the JIT's element templates on both backends; dump checks and
  difftest must hold, and the dictionary transition must be exactly specification-equivalent.
- Always-on feedback (W4) must not tax the baseline beyond its budget; measure per stage.
- A native RegExp tier (W5) is a second code generator; it lands only behind a differential
  gate against the interpreter on Test262's RegExp suites plus a fuzzed corpus.
- Strings (W7) touch every string path, the embedding API (TRust's port) and RegExp's subjects;
  Test262, the fixtures, difftest and a differential test against Node over generated non-ASCII
  programs guard them.
- Incremental marking (W6) puts a barrier on every pointer store in the interpreter, the VM and
  both JIT backends; it lands behind GC stress with marking forced into small slices, and
  TRUST_JS_GC_VERIFY.

### Step 0: a perf map for generated code (design, 2026-10-27)

`TRUST_JS_PERF_MAP=1` makes the engine append a line for each piece of code it generates to
`/tmp/perf-<pid>.map` in perf's JIT map format (`START SIZE name`, hexadecimal without `0x`),
which `perf report` reads for samples no binary resolves; V8's `--perf-basic-prof` writes the
same file. The lines come from the compile-time hook the gprofng registration uses
(jit_profiler.rs, called from `compile_profiled_with` for both backends) and from every other
place that makes executable code: the process-wide shared stubs (permanent), and the native
RegExp tier's byte and word programs (regex.rs). Names follow V8's: `JS:^<name>
<url>:<line>:<column>` for a chunk (`^` marks baseline code, as V8 marks Sparkplug's),
`<anonymous>` for a function without a name, the first local names when there is no script;
`Stub:<kind>` for a shared stub; `RegExp:/<source>/<flags>`. A chunk carries its label only
while the map is on: an `Option<Box<str>>` the bytecode compiler fills from the AST function's
name, script and start (`ScriptSource::line_column`), so the default path pays nothing. Freed
code is not unlisted, as perf's map format has no unload record (V8's map has the same limit;
a jitdump for `perf inject --jit` would lift it if address reuse confuses a profile). The file
opens on first use and takes one write per line under a process-wide lock, since Agents on
other threads compile too. Tests: a compiled function, a shared stub and a native RegExp each
add a line that parses and names them, and nothing is written with the switch off.
DIAGNOSTICS.md documents the switch beside `TRUST_JS_JIT_GPROFNG`, with the call-graph flags
(`perf record --call-graph fp --user-callchains`). Exit: `perf report` on the Vue fixture names
the generated code among its 30 hottest symbols, with no bare addresses.

Landed 2026-10-27 (d4e62452). The dumps differ from the base only in the displacement of the
three Chunk fields generated code reads, 16 bytes on for the label. Exit met: `perf report` on
the Vue fixture names generated code among its 30 hottest symbols with no bare address
(`JS:^<anonymous> .../vue.js:4:17983` 7.8%, `Stub:NameLoad` 4.7%, ...).

### W6a: V8's cap on the heap limit (design, 2026-10-27)

After a major collection V8 sets the old generation's limit to
max(min(max(size x factor, size + step) + young capacity, (size + maximum) / 2), minimum)
(heap-controller.cc, `MemoryController::BoundAllocationLimit`). The engine computes the inner
term today (gc_core.rs, `sweep_phase`: `size` is the cells held plus the payloads they own
outside the heap, which V8 keeps on its heap: Map and Set tables, internal slots, bound
arguments). The port adds the halfway bound with V8's maximum for the old generation on 64-bit
hosts (heap.cc, `OldGenerationSizeFromPhysicalMemory`): half of physical memory, clamped to
256 MB-4 GB, to be re-verified against V8's current source and cited at its revision as
gc_pacing.rs does. The physical memory comes from the operating system (sysconf on Linux,
`hw.memsize` on macOS, GlobalMemoryStatusEx on Windows); `TRUST_JS_GC_MAX_HEAP_BYTES=N`
overrides the maximum, as V8's `--max-old-space-size` does, for tests and diagnosis. Pacing
only (Decision 5): V8 fails with out-of-memory at its maximum and the engine does not, so the
bound never takes the limit below size + step + nursery, V8's own least room, and a heap past
the maximum keeps collecting at that room. The bound applies only with pacing on; fixed
budgets keep their rule. Tests: the limit below, at and above the point where the bound binds
(about 585 MB at factor 4 with a 4 GB maximum), past the maximum, and the override.
Exit (proposed, W6): the limits match V8's rule in unit tests; Web Tooling's peak RSS falls; no
suite slower beyond noise.

Landed 2026-10-27 (7495f76b). Two differences from V8 remain, both to be ported (Decision 9):
past the maximum V8's floor is `size + 8 MB` (its global limit, 8f876708cf), where the engine
keeps the note's `size + 8 MB + nursery`; and V8's MaxGrowingFactor allows a factor of 4 only for
a maximum of at least 2 GB (1.3 to 2.0 below), which the engine does not port (it differs on
hosts with less than 4 GB of memory or under a small override). Measured 2026-10-28 (Stage-exit
timing): no suite slower; Web Tooling's peak RSS waits for its runs.
Both ported 2026-10-27 (05b80239, V8 at 96c72ad4): the growing factor stops at
MaxGrowingFactor's (4 from a 2 GB maximum, 1.3 to 2 below), and within 16 MB of the maximum
and past it the budget is the size and 8 MB. With 4 GB of memory or more and no override, only
that floor changes. Validation: Test262 identical, the fixtures, the lib suite and the
downstream crates' suites.

### W1: builtins and Proxy paths (census and design, 2026-10-27)

Census: the close-out engine (target/claude-closeout/lto-final), user-mode instructions sampled
with call graphs on CPU 5; data, scripts and the microbenchmark in target/p2/w1-census.
- Vue: `shift` takes 34% of the fixture's time, 212 us a call against 66 us for Node limited to
  Sparkplug (3.2x; the fixture's own gap is 3.4x), where it is 36% of the time. The fixture's
  `reactive()` handlers are JavaScript: under `shift`, the `set` traps take 22% of the fixture's
  instructions and the element reads 7%, mostly Vue's handler code and the calls into it;
  formatting index keys takes 0.4%. The generic loop's own work does not dominate, so a 10x cut
  of `shift` (the plan's exit) is not W1's to make: it would be 3x faster than V8's.
- A Proxy microbenchmark (micro/proxy-shift.js: a 17-element array, one push and one shift an
  iteration, 53 trap operations a shift; ns an iteration, the least of 3 runs; trust-js /
  Sparkplug-only Node / Node): an ordinary packed array 290 / 190 / 145; classic (holey)
  storage 300 / 100 / 200; a Proxy without handlers 17,650 / 13,300 / 13,550; with handlers
  forwarding through Reflect 36,750 / 20,400 / 18,800; with handlers that use the target
  directly 17,500 / 9,050 / 8,500. V8's generic shift over a Proxy is slow too.
- Where a Proxy operation's time goes without handlers: a forwarded [[Set]] whose receiver is
  the proxy (OrdinarySetWithOwnDescriptor) turns the receiver's own descriptor into an object
  and back and builds a second descriptor object for [[DefineOwnProperty]]
  (`reflect_define_on_receiver`, `proxy_gopd_value`, `proxy_define_property`: about 25% of the
  micro's instructions, string-keyed reads of the descriptor fields included); the
  getOwnPropertyDescriptor, defineProperty, getPrototypeOf and ownKeys trap lookups bypass the
  trap caches; each element step re-probes the side tables (the proxy table among them: 6-8%);
  and each index is formatted into a heap String. With handlers, the calls into them (W3)
  dominate. Vue's handlers call `Reflect.set(target, key, value, receiver)` with the proxy as
  the receiver, which takes the same descriptor-object path (5% of the fixture).
- React and Djot spend no more than 4% in any builtin's generic path (React's largest is
  CreateDataPropertyOrThrow, 3.9%; Djot's RegExp work, about 8%, is W5's). Octane spends no more
  than 0.2% in any array builtin; its largest builtins are String.prototype.replace with a
  RegExp (8%, W5's) and Function.prototype.call (2.3%, W3's). Web Tooling (the whole suite): no
  array builtin above 1.1% (merge_sort 1.05%), the Proxy side-table probe 1.3%; its largest

Design:
1. Proxy [[GetOwnProperty]] and [[DefineOwnProperty]] pass Property Descriptor records
   (`Property`, `PartialDesc`) and make an object only to call a trap (FromPropertyDescriptor)
   or to read a trap's result (ToPropertyDescriptor), as ECMA-262 §10.5.5 and §10.5.6 do.

   attributes before the target's [[DefineOwnProperty]] runs (§20.1.2.4 step 3, ahead of the
   proxy's GetMethod of its trap).
2. Every trap's GetMethod goes through the trap caches (`proxy_get_trap`), all thirteen kinds.
3. Generic array loops format each index into one reused buffer instead of a String per
   element, and a key a trap receives comes from a per-Agent table of the strings of small
   indices (V8 answers NumberToString from its number-string cache).
4. Holey shift, unshift and splice: under the existing prototype protector, an Array with
   holes shifts in its storage, holes staying holes, without the generic loop (the call table's

5. The plan's other W1 items (bulk indexOf, lastIndexOf and includes; dense sort and fill)
   wait for a workload that spends time there: none of the acceptance set or Octane does.
   Proxy target and handler move out of the side table with W2g, as planned.

### W7: strings (census and design, 2026-10-27)

The owner's Decision 7 put strings in P2. ECMAScript strings are sequences of UTF-16 code units
(ECMA-262 §6.1.4). The engine stored UTF-8 (lstr.rs: a 16-byte header {frontier, len, cap} with
an ASCII hint in cap's top bit, then the bytes; a view {header, owner, offset} for slices of 256
bytes and more), with lone surrogates as plane-16 scalars (jstr.rs, "smuggling"). Indexing needed
a UTF-16 view, which `Interp::units_of` built per string on first use and kept in a 16 MB,
64-entry LRU keyed by the cell's address (`str_units`), beside a `Utf8Index` for slicing; RegExp
widened non-ASCII subjects to 32-bit elements in its own 32 MB LRU (`re_texts`). Every new string
started cold, so code that slices or grows non-ASCII text rebuilt a view a step: quadratic.

Census (no-LTO 7495f76b on Crystal, under load; data and scripts in target/p2/strings-census):
- Web Tooling, whole suite (the close-out): 9.4% of user instructions copy UTF-16 views
  (`units_of`: substr 3.3%, `.length` 3.3%, indexed reads 2.4%). Alone, with the perf map,
  coffeescript spends 63% of its instructions there (`.length` 27%, charCodeAt-style reads 20%,
  slice 17%) and source-map 56% (substr 43%, slice's index 12%): the two largest gaps
  Sparkplug-only Node keeps on the suite (23x and 11x).
- micro/strings.js, 14 patterns over 200 KB of ASCII, Latin-1, CJK and astral text, against
  Sparkplug-only Node: a lexer re-slicing per token (CoffeeScript's `@chunk = code[i..]`) 18x on
  ASCII and about 5,500x on the others (33 s against 6 ms); an anchored RegExp on each remaining
  chunk 4.8x and about 3,700-5,700x; a `+=` accumulator read as it grows 0.5x on ASCII and
  12-90x on the others; prepending (no ropes) 12-37x; split/join 6-12x; Map and property keys
  5-6x; a sticky RegExp lexer 5-7x; the rest 1.6-4.4x.
- The survey found three deviations: a string's own index properties were parsed with Rust's
  integer parser ("abc"["01"] was "b"; a read past the end skipped String.prototype; fixed,
  1bf7973e), the default sort ordered by code point, not code unit (fixed, 9b224edd), and object
  spread and rest of a string walk code points, not units (`{...'a😀b'}` has three keys, not
  four; fixed, b2dfe9bb).

What the browsers do (their source at V8 756afdd7, Firefox d9098b3e, WebKit 780058db, read
2026-10-27): all three store code units at one of two fixed widths, Latin-1 bytes or UTF-16
units, and none stores UTF-8 (Ladybird's LibJS moved from UTF-8 to UTF-16 in June 2026; the
engines that keep UTF-8, Duktape, JerryScript, XS, rescan or keep a few cached offsets). The rules
they share: a buffer's width is fixed at allocation, and a concatenation is one-byte only when
both operands are stored one-byte (V8 factory-base.cc, SpiderMonkey ConcatStrings); they narrow
only text they are copying anyway; the length lives in the header; a substring shares its
parent's buffer above a small cutoff (V8 SlicedString::kMinLength 13; SpiderMonkey above its
inline sizes) and a view never points at a view; anything needing contiguous text flattens
first. They defer concatenation into ropes (V8 ConsString from 13 units); SpiderMonkey instead
reuses the leftmost buffer when flattening, which is the engine's in-place append. Hashes are
over code units whatever the width (V8 caches one in the header).

Design:
1. Representation: a string cell holds one-byte or two-byte code units. The header keeps its 16
   bytes and offsets: `len` counts units, `cap` holds the capacity in units below the two-byte and
   ASCII-hint bits, and a view's `cap` stays the reserved marker. Lone surrogates are ordinary
   two-byte units; smuggling survives only in engine text, at the text boundary. The capacity
   limit is 2^30 - 2 units; the JS-visible limit stays MAX_STR_LEN (2^26 units).
2. Widths as the browsers choose them: text converts to one-byte when every unit fits;
   a concatenation or in-place append is one-byte when both sides are stored one-byte (a two-byte
   suffix on a one-byte buffer copies into a two-byte buffer, after which appends are in place
   again); short copies narrow. Views keep the owner's width, never point at views, and keep the
   engine's pinning rule (a slice of an owner above 1 MiB that covers less than half of it
   copies). The view cutoff stays 256 bytes of content and is measured against V8's 13 units in
   S3.
3. Equality compares units across widths (identity, then length, then memcmp at equal widths).
   Hashes run over code units, so equal strings hash equally at either width. Relational
   comparison and sorting are unit order.
4. Text access: `Deref<Target = str>`, `AsRef<str>` and `Borrow<str>` go. `as_ascii()` lends a
   one-byte string as `&str` without copying; `text()` returns engine text as a `Cow<str>`,
   copying only a two-byte string; algorithms read `units()`. Property keys (Rc<str> until
   W2a's atoms, which become internalized string cells) borrow ASCII text and convert the rest.
5. What goes away: the UTF-16 view cache (`str_units`), the `Utf8Index`, the surrogate join
   fix-ups of concatenation and repeat, and RegExp's UTF-8 decoding: subjects are one-byte bytes
   or two-byte units, widened to the matcher's 32-bit elements only for two-byte subjects until
   W5 reads units directly.
6. Generated code: with one-byte storage holding exactly what the ASCII hint marked, the
   templates (length, charCodeAt, equality, truthiness) and the dumps stay as they are through
   the storage change. S4 extends `.length` and charCodeAt to every flat string.
7. The embedding API: `as_engine_text()` returns `Cow<str>`, borrowed for an ASCII string (TRust
   uses it 37 times); `string_from_engine_text` converts to the right width (60 uses). TRust's
   port lands with S2's validation, through its handoff checks.
8. Ropes are not in this stage: the in-place append already keeps `s += x` linear (and faster
   than V8 on ASCII); a census of concatenation copies after S3 decides on V8-style cons strings.

Staging the widths: the engine's fast paths assume that a byte of a "known ASCII" string is its
code unit, and the generated code's string templates take a string's bytes only under the ASCII
hint. S2 therefore stores ASCII text one-byte and every other string two-byte, so one-byte
storage is exactly the hinted ASCII case those paths and templates already handle, and `text()`
of a one-byte string always borrows. Latin-1 one-byte storage, the browsers' width rule in full,
is S4, once the remaining byte-level paths read storage by width.

Order:

### W2a and W2b: atoms and scope descriptors (design, 2026-10-27; going ahead, Decision 9)

Census (the close-out's GC logs, target/claude-closeout/final/gclog, TRUST_JS_GC_LOG; means per
minor collection; a read-only survey of the tree supplied the inventory, its claims checked):

| | minors | mark + sweep + engine (ms) | finalize (ms) | cells finalized |
| --- | --- | --- | --- | --- |
| ARES-6 | 6,823 | 12.6 | 4.05 (32%) | 17,429 environments, 2,866 property-map extras, 2,854 layouts |
| Web Tooling | 5,066 | 25.6 | 1.24 (5%) | 13,449 environments, 4,842 layouts, 794 extras |
| Octane (partial log) | 396 | 6.5 | 0.40 (6%) | 4,398 environments, 2,105 extras, 581 layouts |

Environments are 75-85% of the cells finalized. Three findings change the plan's framing:
- Compiled code belongs to one Agent heap: a Chunk records its heap (bytecode.rs `heap:
  HeapLifetime`), its constants are that heap's cells, and FunctionRuntime picks code by the
  active heap; only the AST is shared, and it holds names as text. Chunks and native code can
  therefore embed per-heap atoms. A static table still pays, for the roughly 540 distinct names
  the engine itself spells (builtins, `length`, `prototype`, the internal `%...%` bindings), as
  V8's read-only roots and SpiderMonkey's permanent atoms do.
- Atoms can live as long as their heap at first: ShapeTable's transitions already hold a strong
  key for every (parent, key, class) a heap has seen, for its whole life, and every structural
  removal mints a fresh shape, so delete/insert churn already grows that table (and walks the
  process-wide shape ids toward exhaustion); permanent atoms retain nothing new for property
  keys. Index keys, which do die today, will not be atoms. Collecting atoms, with weak
  transitions and dictionary maps for churn, is a later series (with W2d).
- W2a and W2b do not touch Splay's live heap (its objects share layouts and allocate few
  environments): that part of W2's exit belongs to W2c and W2d.

Design:
- Atom: a Copy handle to an immutable, exact-size flat string cell in the Agent heap (an LStr
  header with no spare room, at W7's widths), compared and hashed by address, read like any
  engine string. `Value::Str` can wrap it, so enumeration, JSON and Proxy traps stop
  allocating a string per key. Pointer atoms rather than u32 ids: the conservative stack scan
  sees them, and their text needs no table lookup.
- PropKey: one word, an atom or a tagged canonical array index (at most 2^32 - 2), as
  SpiderMonkey's jsid; one constructor canonicalizes, so identity equality is complete and
  classic arrays stop allocating key strings for indices above 63.
- Each Agent heap keeps an atom table beside its interned strings, with a seeded hash (key text
  comes from scripts): `atomize` for names that will be stored, `lookup` for reads (text with no
  atom names no property, as V8's LookupExisting). Atom cells are allocated old. The static
  names are a process-wide read-only table seeded into every heap's, so `names::LENGTH` is a
  constant; a static atom is never handed out as a heap Value and is never traced.
- Heap atoms live only in heap-bound holders (chunks, FunctionRuntime, GcState tables, cells),
  never in the AST, script sources, snapshots or process-wide caches; debug builds check that a
  looked-up atom is static or belongs to the active heap.
- Environments: binding names become atoms, the environment cell loses its drop glue (the large
  table moves into a storage block, an import becomes a small cell holding its environment and
  name) and stops finalizing. Then ScopeDesc, one immutable descriptor per compiled scope, owned
  by its chunk: ordered names, static flags (const, strict immutability, lexical at this level,
  import), the existing layout id the name caches and native guards use, and an index past 8
  bindings. An environment holds its descriptor and its binding values; a Binding without its
  name shrinks from 40 to 24 bytes and a one-binding environment from the 128-byte to the
  96-byte class. Creating one copies argument words instead of cloning names, the template W3's
  direct sequence needs. Sloppy direct eval, deletable eval bindings, the global declarative
  record and module imports copy on write to a private descriptor, as property layouts do.
  `with` keeps resolving through its object; eval's private-name scan, TDZ messages and memory
  accounting read names through the descriptor.
- Property layouts: keys become PropKeys in a traced storage block, the index an open-addressing
  table there, and layouts stop finalizing.
- Generated code: name compares become one word compare (the ARM64 key-checked arm and creation
  cache, references on both backends), and the binding and layout strides and offsets change.

Order, each commit series behaviour-preserving (Test262 identical) and separately gated:
1. A census in TRUST_JS_GC_LOG: finalize time by cell kind, and the atom count and bytes.
2. Atoms, PropKey, the per-heap table and the static names, without users yet.
3. Binding names as atoms (entries padded to their current 40 bytes, so the code dumps stay
   identical).
4. Environments without drop glue; `fin:environment` reaches 0.
5. ScopeDesc and the smaller Binding (code dumps change in the binding stride and offset only).
6. Property keys as PropKeys; layouts stop finalizing (code dumps change: the creation cache, the
   key-checked arm, the layout stride).
7. References and the stub cache by atom; hot builtin paths through static atoms.
Atom collection, weak transitions and dictionary maps follow with W2d. 8-byte binding slots (TDZ
as the empty word, a one-binding environment in the 64-byte class) are deferred to W3, which
decides the environment layout its direct sequence builds.

Exit (as drafted, within W2's; going ahead, Decision 9): `fin:environment` and
`fin:property_layout` reach 0 on the
sustained workload, the fixtures, ARES-6 and Web Tooling; minor-collection time falls by the
measured finalize share; one-binding environments sit in the 96-byte class; no suite slower
beyond noise. Splay's live heap stays W2c/W2d's.

- Octane's RegExp is mostly one pattern: re17, `/(^|[^\\])"\\\/Qngr\((-?[0-9]+)\)\\\/"/g`, replaced
  over 2,257-unit two-byte strings 780 times a run (48.8% of instructions). Its first element
  admits nearly every position, so the matcher starts at each: 158 us a replace, the same on an
  ASCII copy, against at most 2.5 us in Node at either tier. Skipping the replace when its
  required literal is absent (a JavaScript what-if; same checksum) takes a run from 284 to 166 ms.
- Elsewhere fixed per-operation costs dominate. A Djot operation costs ~4,000 instructions (1,250
  matching; Sparkplug-only Node ~180 in all); a source-map one ~8,500, over a third of it guards
  (`normalize` runs `match` and `split` 2.2M times each, creating its `/\/+/` each time, and
  `test` 1.8M).
- Costs the plan's list misses: the matcher's entry and per-attempt resets (Octane 3.7% beyond
  re17, Djot 2.6%, strings 9%); two-byte subject preparation (strings 14%: the prepared-text
  LRU, widening, unit-element binary searches); replace output built as UTF-8 and canonicalized
  (Octane 3.2%; gone with W7's d1ad3c45); match arrays and `d` indices (Djot 2.4%, strings
  18%; W2c/W2d).
- Little or nothing measured: `match` with /g, `search`, `matchAll` (Octane's 2,255 and
  coffeescript's 1,040 global matches are all there are, among 1.36M and 2.6M operations), case
  folding at match time (at most 0.11%), compilation (0.5%), the collector's `regexps`/`gc_pins`
  sweeps (0.2%).

Design (gains are shares of today's instructions):
1. Prefilters: at compile time, the longest literal every match contains and its offset range
   from the match start (re17: `"\/Qngr(` at 0-1); exec finds it with a NEON scan over bytes or
   units and tries only starts in range, and its absence ends the search. The first-element
   scan gets NEON too (byte equality, 128-entry ASCII tables). Octane 1.7-1.9x.
2. A RegExp protector: a realm proof, epoch-keyed like the array protectors, that
   %RegExp.prototype%'s `exec`, flag getters and symbol methods, %RegExp%[@@species] and the
   `constructor` link are the intrinsics. Value writes to those objects bump the epoch too
   (today only structural changes do: the objects are flagged, store caches decline them and the
   slow store path bumps). A receiver is fast when it has the realm's initial RegExp shape and
   prototype. String.prototype's methods then enter the RegExp algorithms directly and
   RegExpExec calls RegExpBuiltinExec without the Get of `exec`. Removes the guards, the @@method
   dispatch and the generic exec call: source-map 12%, Octane 7.8%, Djot 2.6%.
3. Payload and entry: `Exotic::RegExp(PayloadBox<..>)` holds the shared program (P1's Map/Set
   pattern; W2g's RegExp part). `lastIndex` stays an own data property at the initial shape's
   slot, read and written directly under 2's proof; the legacy statics keep the constructor
   cached; the matcher's scratch lives in the Interp, sized per program, capture slots reset
   through the undo log rather than filled per attempt, flags precomputed. Removes the
   `regexps`/`gc_pins` traffic, string-keyed `lastIndex` access and entry overhead: Octane 8%,
   Djot 5%, strings 20%, source-map 4.5%.
4. Subjects in place: the matcher reads one-byte storage as bytes and two-byte storage as units,
   decoding surrogate pairs in /u and /v as it steps, positions in units throughout; ReText, its
   32 MiB LRU and the unit-element maps go (W7's item 5). Strings 14%, Djot 2%, Octane 1.4%.
5. Captures from storage: captures, split pieces and replace arguments as slices of the subject
   at its width (views above V8's 13 units), with no Rust String or UTF-8 round trip. Octane
   2%, Djot 1%, strings 8%.
6. `match` with /g, `search` and `matchAll` without match arrays, on 2's proof: for
   completeness, after 2.
7. Case closure at compile time, with the native tier, which needs closed classes (`v`-mode
   class sets are already closed under `i`, 05e1f798).

What the native tier does today (regex.rs at c9610dfa):
- A program tiers up after 64 executions (`REGEXP_TIER_UP_THRESHOLD`, :23; `note_execution`,
  :2695) once a one-byte subject has been seen, never under `i`, `s`, `u` or `v`. One-byte
  storage is ASCII until W7's step S4, and two-byte subjects stay on the matcher: in-place units
  can exceed 0xFF.
- `OneByteNativeProgram::compile` (:1000-1076) takes a program whose body is either one terminal
  `Many` of a one-byte Char, Any or a Class with its 256-entry LUT, run by a Rust loop
  (`find_terminal_one_byte_many`, :1184), or a straight line of such Chars, Anys, Classes and
  non-multiline `^`/`$` with at least one non-literal. Captures, alternation, any other
  quantifier, lookaround, backreferences and `\b` decline it.
- Machine code (`OneByteNativeCode::compile`, :415-470): at most 256 ops, no assertions on
  either backend, and no Class on AArch64 (:1058-1076); the rest runs the ops through a Rust loop
  (`find_interpreted`, :1114). Emitters: x86-64 :586-711, AArch64 :890-992, with their own small
  assemblers, unix only. The candidate loop calls `regexp_native_poll` (:395) at every start
  position (`call rax` :627, `blr x16` :920): a call and `RuntimeInterrupt::current_reason` per
  candidate, where V8 compares the stack pointer at each backtrack.
- In the census the tier was Djot's "native code" (1.6%), almost all of it `find_interpreted`:
  on AArch64 Djot's class programs never reach machine code.
- The AArch64 "release-build termination fault" (the plan's regex.rs:1156 at 56c28010, now
  :1058) was most likely a bug fixed since, by reading. 51fbed49 (2026-09-06) added the emitters
  and, in the same commit, the class decline. Its AArch64 loop branched on the flags right after
  `blr x16` (`b.ne interrupted`, no compare): AAPCS64 leaves NZCV undefined across a call, and
  the poll returned `u8`, whose upper bits w0 does not define. When the flags happened to read
  "not equal", the code added 1 to w0 and returned status 1, "match", with the output still the
  `{0, 0}` the caller initialized: a false empty match at 0. A global replace or exec loop then
  never advances (an empty match at 0 sets `lastIndex` to 0, AdvanceStringIndex moves it to 1,
  and the next exec matches at 0 again), which is "termination lost on a no-match tail" in
  release, where the poll's flags differ from debug's. The same false empty match is the
  "anchored no-match into a false empty match" behind the assertion decline (jQuery's
  vendor-property test). 5967822c (2026-09-10) compares w0 after the call (:921) and returns
  `u32` (:395), with comments naming both causes; the x86-64 loop has tested `al` after its call
  from the start, so that path was sound. The declines were not revisited. Still fragile: `sticky`
  arrives as a `u8` in w3 and the code compares all of w22. Crystal check: a release build of
  c9610dfa with both declines removed, run under the generated harness (regex_native_generated.rs),
  Test262's RegExp suites with `TRUST_JS_REGEXP_TIER_UP_AT=1`, and global replaces over subjects
  whose tails do not match; then the same build with the compare at :921 removed, which should
  reproduce the fault.

What V8 does (c8b709085e21):
- Single tier by default: a pattern is compiled to native code at its first execution
  (`regexp_tier_up` with `regexp_tier_up_ticks` 0, flag-definitions.h:3512-3539;
  `EnsureCompiledIrregexp`, regexp.cc:837-893), separately for one-byte (Latin-1) and two-byte
  subjects (`CreateNativeMacroAssembler`, regexp.cc:1009-1030). The bytecode interpreter
  (regexp-bytecode-generator.cc, regexp-interpreter.cc) serves jitless and a nonzero tick count;
  even then a subject of 1,000 units or more, or global execution, tiers up at once (regexp.cc:
  1283-1310; js-regexp.h:162). Patterns longer than `kMaxOptimizedPatternLength` compile without
  optimizations; more than 65,536 registers is an error (regexp.cc:1366-1402,
  regexp-macro-assembler.h:37). `--regexp-assemble-from-bytecode` (off by default; flag-
  definitions.h:3544-3546) builds native code from the bytecode one instruction at a time
  (regexp-code-generator.h:19-80), the shape proposed for item 3 below.
- Compilation: the AST becomes a node graph wrapped in capture 0, behind a lazy `.*?` loop unless
  anchored or sticky (`PreprocessRegExp`, regexp-compiler.cc:6469-6512); one pass analyzes it and
  `Assemble` emits through a macro assembler with a native backend per architecture and the
  bytecode generator as another (regexp.cc:1363-1495). A pattern anchored at its end with a
  bounded length starts from the end (`SetCurrentPositionFromEnd`, regexp.cc:1466-1475); global
  execution loops inside the generated code (GLOBAL, GLOBAL_NO_ZERO_LENGTH_CHECK,
  GLOBAL_UNICODE, regexp.cc:1477-1485, regexp-macro-assembler.h:386-391).
- Captures are registers, two per group: on ARM64 the first 16 live in x0-x7, two 32-bit positions
  per register, the rest in the frame (regexp-macro-assembler-arm64.h:202-205, :226-281); w24 holds
  the "unset" value for clearing (:264). Changes are deferred along a Trace, the path being
  generated (regexp-compiler.h:292-505); at a choice point `Trace::Flush` pushes the old value of
  each affected register (RESTORE), or notes it for clearing (CLEAR) or for nothing (IGNORE), and
  emits undo code reached by backtracking: pop or clear, then backtrack on
  (regexp-compiler.cc:511-527, 611-650, 706-880). Loop iterations clear their captures with
  `ActionNode::ClearCaptures` (:981).
- Alternation: a ChoiceNode tries its alternatives in order. Quick checks load up to four
  characters and compare them under a mask to skip alternatives that cannot start here
  (`GetQuickCheckDetails`, :2095; `EmitQuickCheck`, :1965); the unanchored search skips ahead
  with a Boyer-Moore lookahead or SIMD scans (`EmitOptimizedUnanchoredSearch`, :4621;
  `BoyerMooreLookahead::EmitSkipInstructions`, :3976; `SkipUntil*`,
  regexp-macro-assembler-arm64.cc:655-1268), and disjoint alternatives dispatch on one masked
  compare (`regexp_masked_dispatch`, :5393).
- Loops: fixed-length greedy loops step back without pushing a record per iteration
  (`SpecialLoopState`, regexp-compiler.h:507-520). A loop whose retries are futile drops its
  backtracking (`AtomicLoopKind`, regexp-nodes.h:238-252): its continuation is `$` then accept
  (kAtEnd), always succeeds at the greedy extent, as `\D*` after `\d*` in `/(\d*)(\D*)/`
  (kTotal), starts with `\b` over a word-character body (kBoundary), or starts with characters
  disjoint from the body's (kDisjoint).
- The backtrack stack is per isolate, 32-bit slots, 1 KB static, then grown on the heap up to 64
  MB (regexp-stack.h:62-127). Generated code pushes code offsets, positions and saved registers,
  checks a limit kept 32 slots short of the end after its pushes (`CheckStackLimit`,
  regexp-macro-assembler-arm64.cc:2303-2307; `PushBacktrack`, :1946-1960) and calls out to grow
  it. Every backtrack also compares sp with the JS stack limit, which interrupt requests lower
  (`EmitBacktrack`, :195-219; `CheckPreemption`, :2293-2300). An optional backtrack limit counts
  backtracks and fails, or falls back to the experimental linear-time engine, which is off by
  default (`SetBacktrackAndExperimentalFallback`, regexp.cc:1060-1077; flag-definitions.h:
  3622-3630).
- Case independence is compiled in. Classes under `i` gain their case equivalents
  (`TextNode::MakeCaseIndependent`, regexp-compiler.cc:2902-2922; `CharacterRange::
  AddCaseEquivalents`, regexp-compiler-tonode.cc:1743, from ICU's case closure minus the
  characters ECMA-262's Canonicalize keeps apart, special-case.h:20-60), under `iu`/`iv` by simple
  case folding (`AddUnicodeCaseEquivalents`, regexp-compiler-tonode.cc:512-540). A character
  becomes its one to four equivalents (`GetCaseIndependentLetters`, regexp-compiler.cc:1575), and
  two that differ in one bit match under a mask in one compare (`ShortCutEmitCharacterPair`,
  :1077-1103; `EmitAtomLetter`, :1685).

Design (gains are shares of the W5 census's instructions, 56c28010 no-LTO, from the plan's W5b
paragraph: the backtracking interpreter and class tests are about 9% of Octane's, coffeescript
3.6%, strings.js 14%, source-map 2.8%, and in the census Djot 1.5% besides 1.6% in the one-byte
tier; coverage from the table above; native code assumed to remove 75-85% of the matcher work it
covers, counted after item 1's):
1. The matcher's futile retries (Rust only, both tiers, no dump change):
   a. Atomic loops, as V8's four kinds: a greedy `Many` whose continuation is non-multiline `$`
      and then the match, always succeeds at the greedy extent, starts with `\b` over a
      word-character body, or starts with a set disjoint from the loop's takes no Greedy
      record, so it never retries shorter runs. coffeescript's `\s+$`
      (kAtEnd), source-map's `[\w+\-.]+` before `:` (kDisjoint), Octane's `\s*$`, `(\d*)(\D*)`
      (kTotal) and `\b\w+\b` (kBoundary).
   b. Restart past a failed atomic loop: when such a loop, first in the program, ran to `e` and the
      continuation failed, no start inside its run can match (the run from there ends at `e` too,
      and the continuation sees the same `e`), so the scan resumes at `e`. coffeescript's restarts
      inside every whitespace run: O(k) for a run of k blanks instead of O(k^2).
   c. First-element filters for assertion-led programs: a multiline `$` admits line terminators
      and the end, `\s*$` the loop's set and the end, an alternative led by `^` position 0 and,
      under `m`, line starts. coffeescript's `/$/m` (2.06M attempts), Octane's trim (1.0M).
   Gains: coffeescript ~2.3% (`clean` from 2,150 us a call toward Sparkplug-only Node's 375),
   source-map ~1% (its URL pattern's retries), Octane ~1%. Risk: a misclassified loop drops a
   match that a retry would have found; each kind is a proof over the program, tested against
   the matcher with the analysis forced off (a switch per item, as W5a's).
2. Case closure at compile time (W5's item 7, Rust only): under `i`, every Class closes over
   ECMA-262's case relation: Canonicalize's for legacy patterns (simple uppercasing, never
   folding non-ASCII onto ASCII, §22.2.2.7.3), simple case folding for `u` (regex_fold.rs's
   FOLD_CANON and orbits); `v`-mode sets are closed already (05e1f798, `ClassSet::
   close_over_case`, :7337). A Char becomes its equivalence set, compiled as a Char, a two-member
   mask, or a small Class. Matching then tests membership with no folding (`CharClass::matches`'
   orbit loops, :1878-1921, go for compiled classes), the 256-entry LUTs serve `i` patterns, and
   the prefilter and first-element filter scan for case-closed sets: Octane's cookie readers get
   a real prefilter. Backreferences under `i` keep runtime Canonicalize. Gains: case folding at
   match time was at most 0.11% in the census; the value is the filters (Octane's 22% of
   attempts) and 3b. Risk: Canonicalize's exceptions (ß, ẞ, the Kelvin sign, and characters
   whose uppercase is ASCII); a test over every BMP code point compares the closed sets with
   `canonicalize_legacy` and `fold_canon`, as V8 generates special-case.cc.
3. The native tier: compile the matcher's `Inst` program itself, one template per instruction,
   for each subject width (V8's assemble-from-bytecode shape). `Matcher::run` stays the reference
   and the fallback for everything a program uses that the tier does not.
   a. Core, both backends: Char, Any, Class (one-byte LUT; two-byte LUT below 256, else ranges
      searched inline for a few, by helper for more), Save with W5c's undo rules (records above
      the floor, one first-write record per slot at the root floor, 46c93827), Split with the
      first-instruction tests `branch_may_match` makes resolved at compile time, Jmp, the match,
      `^`/`$`/`\b` with their flags resolved statically, greedy and lazy Many (records and retry
      stubs; 1a's atomic loops without), SetMark and CheckProgress, ClearCaps with its snapshot;
      one-byte and two-byte subjects. The candidate loop runs in the generated code with the
      first-element test in line, calling the Rust vector scans for long skips. Coverage: Octane
      91.5%, source-map 100%, coffeescript 76%, Djot 100%.
   b. Item 2's closed `i` programs: Octane +8.5%, coffeescript +2.2%.
   c. Lookaheads (a frame record and the capture snapshot, as `LookFrame`), backreferences
      (inline unit compare; `i` through a helper), counted loops, modifier groups (flags fixed per
      instruction at compile time): coffeescript +21.4%.
   d. Unicode mode (surrogate pairs stepped as one element) and lookbehind: strings.js 100%.
      `v`-mode string sets (StringSet) stay on the matcher.
   Machine state: an entry `fn(*mut NativeMatch) -> u32` with today's statuses plus resource
   exhaustion. Callee-saved registers hold the subject, length, position, the context, the
   capture base and the backtrack stack's base, top and limit (AArch64 x19-x28; x86-64 rbx, rbp,
   r12-r15 and the frame). Captures and marks stay in the program's `MatchScratch` (3708989b).
   The backtrack stack is the scratch's storage taken as 16-byte native records (a resume or
   undo-stub address and an operand), grown by a Rust helper that enforces
   `MAX_BACKTRACK_STATE` (:5859) as the matcher does. A pop jumps to the record's address;
   undo stubs restore and pop again, as V8's undo code (regexp-compiler.cc:861-884). Polling: a
   counter in a register, decremented at each backtrack and candidate, loads RuntimeInterrupt's
   state word at zero; deadlines go through the Rust helper every 2^14 steps
   (`INTERRUPT_POLL_MASK`). Tier-up: after 64 executions as now, or at once for a subject of
   1,000 units or more (V8's rule); each width compiles on first use; one ExecutableBuffer per
   program and width (jit.rs:1564-1600), its code listed in the perf map as today. The one-byte
   tier (`OneByteNativeProgram`, both emitters, `find_terminal_one_byte_many`) goes once 3a
   covers its subset, which also retires the fault above; until then its declines are lifted
   only after the Crystal check.
   Gains beyond 1's: Octane 6.0-6.8% (with 3b; about a sixth of what W5a leaves), source-map
   1.4-1.5%, coffeescript 0.8-1.0%, with 3d strings.js 10.5-12%, Djot under 1% (W5c's
   single-element path took most of its matcher work; its RegExp cost now lies in W2's arrays).
   Risks: two code generators on two backends; every compiled program runs under the
   differential gate below, and the matcher remains the reference. Code memory: an mmap per
   program and width costs a page each, so Web Tooling's hundreds of patterns may need a shared
   arena. Polling must bound the time to an interrupt in every loop. AAPCS64's undefined flags
   across calls and unextended narrow arguments are the fault's lesson: compare results
   explicitly and extend every argument narrower than a register. Windows' x64 ABI stays on the
   matcher, as today's tier does. Garbage collection: matching allocates nothing and runs no
   JavaScript, and the caller keeps the subject rooted.
   Dumps and tests: the JIT's dumps do not change; `TRUST_JS_REGEXP_CODEDUMP=<source>` prints a

What V8 does (c8b709085e21):
- Sparkplug's call is a builtin call: `BaselineCompiler::BuildCall` (baseline-compiler.cc:1713-
  1729) calls `Call_ReceiverIs*_Baseline_Compact`, which loads the feedback vector from the
  caller's frame and runs `CollectCallFeedback` (ic-callable.tq:91-168: increment the call count,
  then return if the slot holds this target), then tail-calls `Call` and `CallFunction`
  (builtins-arm64.cc:2373-2450, 2944-3024) and `InvokeFunctionCode` (macro-assembler-arm64.cc:
  2884-2948), which pads missing arguments with undefined in place and jumps to the callee's
  dispatch-table entry. The callee pushes its frame (fp, lr, then in `BaselineOutOfLinePrologue`
  context, closure, argc, bytecode array, feedback cell and vector; builtins-arm64.cc:1147-1259)
  and makes one stack check against a limit that also signals interrupts (:1224-1233); the
  interrupt budget is charged at loop back-edges and returns, not at entry (baseline-compiler.cc:
  2638-2720, 2903-2911). new.target travels in x3, undefined for a call (macro-assembler-arm64.cc:
  2908); there is no frame stack beside the machine stack (frame-constants.h:744-785) and no
  ambient strictness. Maglev's `CallKnownJSFunction` skips `Call` and `CallFunction` altogether:
  it pads at the site and calls the dispatch entry (maglev-ir.cc:7434-7470).
- A function with context-allocated variables makes its own context: `CreateFunctionContext`
  (bytecode-generator.cc:8719-8744), in Sparkplug a call to `FastNewFunctionContextFunction`
  (constructor.tq:63-73): one new-space allocation of map, length, ScopeInfo, previous and the
  slots, filled with undefined (builtins-constructor-gen.cc:381-469); bytecode then copies the
  captured parameters (bytecode-generator.cc:8746-8770) and writes the TDZ hole at each
  declaration (:2139-2183). Slots are tagged words; modes and flags live in the ScopeInfo
  (scope-info.tq:101-108), which slot 0 of the context names (contexts.h:545-577).
- Builtins are machine code entered like JavaScript functions (TFJ/Torque): Map and WeakMap
  get/has/set, Array.isArray, Object.is, Reflect.get and has, String includes and substring,
  RegExp exec, parseInt and Number all are. Only C++ builtins (Reflect.set among these) pay a
  boundary: an adaptor and `CEntry`'s exit frame (builtins-internal-gen.cc:1337-1402,
  builtins-arm64.cc:4749-4926). WeakMap.get is one EphemeronHashTable probe by the key's stored
  identity hash, and a key without one returns undefined without creating it

Design (gains are shares of today's instructions; per-call counts are the census's):
1. A cheaper direct call (ARM64), from 257 instructions beyond the body to about 140:
   a. The static gates (compiled entry, frame size, the global-body need, a sloppy callee's
      object receiver) fold into one ready bit at fill, and the sequence counts the callee's runs
      itself, so the inline-attempt warm-up gate goes: 30 to ~10.
   b. new.target and the construct flag live in the callee's record, as V8 passes new.target in
      a register; an ordinary call stores Undefined there and the sequence stops saving, clearing
      and restoring `Interp::constructing`/`new_target`; natives that read new.target take it from
      the boundary (2): 31 to ~4.
   c. The callee frame: save only the callee-saved registers the chunk uses, read strictness from
      the running chunk instead of an ambient `Interp::strict` set and restored by every
      prologue and epilogue, and find running code by walking the live frame records when code is
      reclaimed instead of counting residency per activation; one entry check: 59 to ~30.
   d. The finish stub checks one dirty bit that the slow paths set (pending tail call,
      materialized activation, `FnFrame` extra, operands left), not five fields; the callee
      context reads the chunk's constants instead of copying them; the record pool pops and
      pushes by index: 86 to ~45.
   Gains (117 instructions a direct call): React 9.4%, chai 1.7%, Djot 1.5%, Vue 1.3%; on the
   call table, the direct, method and closure cases' instructions an iteration fall to 1.13,
   1.10 and 1.23 times Sparkplug's, recursion to 1.48. Risks: code reclamation must see every
   running chunk (records, Rust entries, borrowed frames: the collector already registers each
   active context); every reader of `Interp::strict` and `new_target` moves. Dumps: every ARM64
   chunk's prologue and epilogue, every call site's sequence, the finish stub.
2. Natives without the full boundary (both backends, the helper):
   a. Native classes recorded at registration, not pointer lists: pure (Array.isArray, Object.is,
      Number.isNaN-style predicates, Math, the collection methods), primitive-pure (no author
      code when the receiver and arguments are primitives: parseInt, parseFloat, Number, String
      and Boolean called as functions, String.prototype's slice, substring, indexOf, includes,
      startsWith, charAt, trim and case mapping; Array.prototype.indexOf and includes on arrays
      the element protector covers; RegExp exec and test while W5's protector, 753d3aa2, holds),
      and the rest. The helper runs pure and primitive-pure natives on the operand window as the
      operand-only path does now; only natives that read new.target keep that clear. A native
      that usually runs no author code but may (Reflect.get, set and has through a getter or a
      Proxy) runs its fast path first and enters the boundary only on the path that calls out.
      Gains: Vue 3.8% (Array.isArray, Object.is, parseInt and Number 2.6%, Reflect 1.2%), chai
      5.2% (slice 3.0%, Array indexOf 1.1%, Reflect 0.9%), Djot 1.7%.
   b. The intrinsic helper's fallback takes the same light path for its pure intrinsics: chai
      ~2.8% (25.3M entries), Djot ~2.5% (276,060), Vue 0.4%.
   c. Templates, after the IC's identity proof (non-speculative, unlike Maglev's reductions):
      Array.isArray and Object.is in line (Vue ~1%), Math.min and max with three or four
      arguments (chai 1.9%), String.prototype.slice with one argument beside the existing
      two-argument intrinsic (chai ~1%), codePointAt on two-byte strings with W7's S4 (Djot
      ~0.3%).

      (W2g's pattern; Vue 2.7%), Reflect.get, has and set sharing the property-get path (Vue

      PropKeys, d3c66d56), dense indexOf (W1's deferred bulk indexOf now has a workload: chai
      4.3%), the string searcher's setup (Djot 0.5%).
   Risk: a misclassified native skipping the boundary while it can run author code; debug builds
   assert that nothing on the light path reaches `Interp::call`. No dump change apart from 2c,
   whose stubs gain arms.
3. The closure entry: a callee that needs an environment builds it in its prologue, as V8's do:
   allocate the cell its ScopeDesc sizes (a lean helper first, W2e's inline allocation later),
   link the closure's environment as parent, copy captured parameters from the argument slots,
   fill vars with Undefined and lexicals with the empty word, and install it as the frame's
   environment. W2b's descriptors make that a copy of words. Bindings become 8-byte slots (TDZ as
   the empty word; mutability and strictness in the descriptor; deletable eval bindings and
   imports in private descriptors, as W2b planned), aiming at the 64-byte class for one binding.

Then the safepoint poll in V8's shape (d4c51376..d14387e3, 2026-10-28, an agent's; Decisions 11,
18 and 19; item 1c's one entry check):
- d4c51376: each interpreter has a poll word, an atomic other threads write: one bit the heap's
  (a collection due, the live-object ceiling included), one for host interrupts. A
  `RuntimeInterrupt` handle keeps weak references to the words it controls and writes each bit
  under its lock from the state at that moment, so a request racing a clear is never lost. One
  watchdog thread expires armed deadlines (Decision 18): the first deadline starts it, it serves
  those that follow and exits after 5 s with none armed; a burst's arm and clear costs 462 ns,
  where a thread per deadline measured 36-90 us. The Rust-side polls read the word too.
- ed9f6be9: every native safepoint loads the word and branches: the entry, loop and helper-end
  polls on ARM64 (12 instructions to 3) and x86-64 (10 to 3); the helper-free region guard tests
  the interrupt bit alone, and numeric loops keep their countdown. The allocator compares the
  live count with the ceiling as it counts (3 instructions an object allocation) and sets the
  heap's bit out of line.
- d14387e3: ShadowRealm code is interruptible by the host (Decision 19): its interpreter shares
  its creator's handle, and an interruption passes `evaluate` and wrapped functions in both
  directions, as V8's evaluate returns while execution terminates
  (builtins/builtins-shadow-realm.cc:182-186); ordinary throws still become TypeErrors.

### W3 item 3: the closure entry (census and design, 2026-10-28; decided, Decisions 20 and 21)

Item 3, as the stage's design has it: a callee that needs an environment builds it in its prologue,
as V8's do; bindings become 8-byte slots; such callees and `arguments.length`-only or
lazy-`arguments` bodies take the direct sequence. This note sizes that, and records the design
the owner decided on its questions (Decisions 20 and 21).

The code.
- `CALL_IC_NEEDS_ENV` (bytecode.rs:1012-1016) is set at fill for every chunk whose
  `jit_no_activation()` is false (interpreter.rs:15215, 15350; bytecode.rs:20839-20841): an
  activation (`makes_env`: captured bindings, a captured `this` or `arguments`) or an arguments
  slot (bytecode.rs:3632-3640); prepared entries are never cached (interpreter.rs:15343-15344).
  An entry with the bit clears bits 0-3, so the ARM64 sequence's first gate routes it to
  `jit_call_hit`, then `call_jit_env_committed` (interpreter.rs:13842) and `run_moved_env`
  (jit.rs:19201-19234): `make_run_env` (bytecode.rs:3654-3750) runs the chunk's `ActivationPlan`
  (bytecode_activation.rs:24-212), whose `instantiate` collects the plan's 24-byte bindings into a
  vector (164), allocates the cell, seeds parameters, records lexical names, makes hoisted
  closures and a captured `arguments` object, and publishes the layout id (210);
  `arguments_slot_value` (bytecode.rs:20573-20586) fills the arguments slot; `run_moved_inner`
  (jit.rs:19246) then enters on a pooled record as the sequence does. On x86-64 every call takes
  `H_CALL` (jit_x64.rs:1220-1224), and environment callees the same Rust entry.
- The prepared entry (bytecode.rs:2622-2625): `compile` (6816-6826) retries a body the lean
  compilation refuses (direct eval, `with`, Annex B or unanalyzable patterns in `CaptureScan`,
  7147-7166; sloppy `arguments` with non-simple parameters, 7131-7140; mapped arguments beyond
  `length`) as a chunk whose caller completes FunctionDeclarationInstantiation in Rust
  (interpreter.rs:15796-15840) and passes the instantiated record, which `make_run_env` returns
  as it is (bytecode.rs:3655-3657).
- Derived constructors compile against a record their caller makes (bytecode.rs:6828-6838;
  interpreter.rs:13439-13510). The construct record (above) lists them, classes with instance
  elements and constructors outside the sequence's gates (an activation among them) as the
  helper's cases.
- The representation (W2b): an environment is a `RefCell<Scope>` (interpreter.rs:2584-2608) in
  the 96-byte class (2669): a `VarMap` (1520-1528: a names word; `BindingValues`, the first
  binding in place and the rest in a storage block, 1962-1964; a generation and a layout id), the
  parent, a `with` object word, three flags and `lexical_names` (2677). Names live apart from
  values: a kept `ScopeDesc` (1586-1594), the record's own list (1705-1710) or one atom (1736). A
  `Binding` (2723-2744) is 24 bytes: the value, `mutable`, `initialized` (TDZ), `import_ref`,
  `imported`, `deletable`, `strict_immutable`.
- Readers: the callee's own captured bindings go through per-chunk cap caches (bytecode.rs:
  20346-20403: a layout-id mode that derives the slot, or a pinned pointer and its generation) and
  their templates (above); free names through `NameIc` (bytecode.rs:239-259) and the shared name
  stubs (jit.rs:12272-12420; deep chains, jit_names.rs:50-160), which check each record's `with`
  word and generation or layout id, the slot's bound, then the binding's `initialized` byte (for
  imports and stores also `imported` and `mutable`), at stride 24 (value.rs:1452-1464,
  1889-1890; x86-64 jit_x64_names.rs:57-62, 311-317). The tree-walker and the VM use `Binding`'s
  fields directly at about 400 sites (`Binding::data` 115, `initialized` 86, `vars.get` and
  `get_mut` 81, `vars.insert` 43, `import_ref` 32, `mutable` 31, `strict_immutable` 10,
  `deletable` 9).
- Tracing: `Scope::trace_fields` (interpreter.rs:2644-2664) reports the storage blocks, the
  lexical names, each binding's value and import, the parent and the `with` word. A record's
  `env_raw` is not traced (jit.rs:1912-1916): its owners are the entry's Rust frame, the callee
  object a direct call leaves on the caller's stack, or a `NativeActivation`, whose base is
  `env_raw` (bytecode.rs:21520-21536).
- Snapshots encode parser output only (snapshot.rs:8-11), and neither the embed API nor the

Three points carry over to TRust. Every engine makes the record in the callee, from a static
descriptor: Sparkplug and JSC's Baseline JIT by a call, SpiderMonkey's Baseline in line since 2023
(6f790d09: most of Speedometer's calls to the VM's InitFunctionEnvironmentObjects came from
Baseline code; a micro-benchmark went from 55 to 23 ms with `--no-ion`). So any caller reaches it
through its ordinary call. TDZ is a word no language value can be, never a flag. And no baseline
tier elides an arguments object beyond a lone `arguments.length` (SpiderMonkey and JSC; V8 not
even that): their optimizing tiers do the rest (TurboFan reads elements from the frame, JSC's FTL
eliminates the objects), and TRust JS has one native tier, so it does that work there (20e).

Design (Decisions 20 and 21)

The environment record. A binding is one 8-byte word in its record: its value, or `Value::Empty`
while a `let`, `const`, `class` or a derived constructor's `this` is uninitialized (the word local
slots already use for TDZ, bytecode.rs:16513). The static attributes (mutable, strict, lexical at
this level, deletable, import) live with the names: a kept descriptor's per-name byte, the
record's own list beside its atoms, or two spare alignment bits of the one-name word (immutable,
strict; a single deletable or imported binding takes an own list). An import keeps its
(environment, name) in its record's own list, its slot holding the empty word. A descriptor's
address is the layout identity name caches compare (kept for its heap's life, so never reused
under a cache), which retires `layout_id`; `lexical_names` goes, its use being the lexical
attribute. Every binding is in line, in a cell its descriptor sizes (20b), as V8's contexts,
SpiderMonkey's CallObjects and JSC's lexical environments are:

| bytes | field |
| --- | --- |
| 0-7 | the RefCell's borrow flag |
| 8-15 | names: a kept descriptor, the record's own list, or one name with its attributes (tagged) |
| 16-23 | parent |
| 24-31 | the `with` object word (empty unless a `with` record) |
| 32-39 | slot count and capacity (0: the slots are in line) |
| 40-47 | generation (own lists' structural changes), `under_with`, `var_boundary`, `catch_param` |
| 48- | the slots, one word each |

One or two bindings take the 64-byte class (96 bytes today), three to six the 96-byte class (today
96 bytes and a block of 24 bytes a binding), seven to ten 128 bytes, up to 506 the 4,096-byte
class. A record that outgrows its cell (a sloppy eval's `var`, a tree-walked record's later
insert) moves its slots into a storage block and leaves its in-line words unused, as `InlineVec`
does today (inline_vec.rs:3-7); the collector reads the count from the header. chai's five-binding
activations (111,475) take one 96-byte cell where they take 96 bytes and a 120-byte block today.

Steps, each landing and gated on its own (the lib suite, pacing, GC stress on the environment,
closure, arguments, eval and construct tests, the fixtures and difftest as the base's, Test262
identical, zombie's x86-64 lib suite and clippy; the dumps differ only as each says):

1. The callee makes its environment and the arguments it needs, on today's representation (20a,
   20d, 20e); `CALL_IC_NEEDS_ENV` retires.
   - The count. Every ARM64 call site passes the argument count in w1, one `movz` (20d). The
     arguments are the caller's top argc words under x20 until it pops them (jit.rs:8504-8507,
     8678-8681), and every prologue already saves the caller's x20 (4080), so a prologue that needs
     the arguments finds them from that word. Rust entries pass the count flagged (bit 31) and the
     arguments' address as the code's second and third arguments; on x86-64, whose calls all enter
     from Rust, the prologue takes both from its argument registers. A prologue that needs them
     keeps them in two new words of its frame record.
   - The environment. The prologue of a non-resumable chunk that makes an activation calls a lean
     helper after its entry poll (jit.rs:4112-4114, the frame's first safepoint), as Sparkplug's
     first bytecode calls FastNewFunctionContext. The helper runs the chunk's plan with the
     closure's environment (`env_raw`) as parent, captured parameters copied from the arguments
     (20c), `this` from `this_word`, hoisted closures over the new environment, then sets
     `env_parent_raw = env_raw` and `env_raw` to it. It reaches no safepoint and collects nothing,
     so every word is initialized before the next safepoint; the frame record's trace reports
     `env_raw`, which the record now owns.
   - `arguments` and rest (20e). Where a compile-time proof shows that every use of `arguments` or
     of a rest parameter is a `length` or element read (`lazy_arguments_rewrite`'s,
     bytecode.rs:8908-8941, extended to rest and to sloppy bodies with parameters: never stored,
     passed, called, captured, written or deleted, in a body that is not resumable), no object or
     Array exists at run time. `length` is the count (for rest, the count less the formals, at
     least 0). `arguments[k]`, k an integer index below the count, reads formal k's slot when k is
     a formal's index: in sloppy code that is the mapped alias (MakeArgGetter, spec.html:
     15130-15148), and in strict code it holds the argument while the body never assigns that
     formal (otherwise the k-th argument word). Past the formals it reads the k-th argument word;
     `rest[k]` reads argument word n_params + k. An index at or past the count is undefined while
     the no-elements protector holds (interpreter.rs:3658-3665: `Array.prototype` and
     `Object.prototype`, where the [[Get]] would go, have no index keys). Any other key, or a lapsed
     protector, materializes the exact object this body would have made into its slot, and every
     later read takes it. A sloppy body with parameters whose `arguments` the proof covers leaves
     the prepared entry. Elsewhere the prologue fills the slot as the Rust entries do today: a count
     body stores the count as a Number (three instructions); an object body (unmapped, or sloppy
     without parameters) and a rest parameter the proof does not cover get theirs from the helper,
     made from the arguments.
   - What goes. The Rust entries (`jit::run`, `run_moved_inner`, `run_moved_oversized`) stop
     building environments, rest Arrays and arguments values, and pass the count and arguments
     instead; `run_moved_env` and `call_jit_env_committed` go; `jit_direct_flags` stops refusing
     rest callees (bytecode.rs:20905). Prepared entries are never cached (interpreter.rs:
     15343-15344), so once activation and arguments-slot callees enter like any other nothing sets
     `CALL_IC_NEEDS_ENV`, and the bit goes. The ARM64 call and construct sequences admit these
     callees with no change but the count. The VM keeps building environments in Rust through the
     same plan, with its own access to the arguments; borrowed entries resume in a frame that has
     its environment. x86-64's prologue calls the same helper.
   Dumps: every ARM64 call site (the count), the prologues of chunks with an environment, an
   arguments mode or rest, the elided reads, the helper table, the frame record's two words.
2. Binding accessors. Every reader and writer of a binding's fields moves behind `VarMap` methods
   (value or TDZ, attributes, initialize, set), so that the representation changes in one place.
   No behaviour or dump changes.
3. Attributes with the names. `mutable`, `strict_immutable`, `deletable`, `imported` and the
   import's target leave `Binding` for the names, and `lexical_names` goes. Copy on write stays the
   rule: a sloppy eval's `var` (spec.html:30667) or a `delete` gives the record its own list,
   bumping the generation; a kept descriptor never changes. The name stubs check attributes when a
   cache fills (a store into an immutable binding, an import, keep the helper) and drop the
   `mutable` and `imported` loads from the hit path. Dumps: binding stride 16, the stubs' hit paths.
4. TDZ as the empty word, 8-byte bindings, the records above (20b). `initialized` goes: a read
   compares the word with the empty word (two or three instructions where a byte load and a test
   were); InitializeBinding stores the value; `typeof` of a binding in TDZ still throws. Records
   are allocated at their descriptor's size; the tree-walker's records, the VM's block records and
   module records take the same layout. Cached binding pointers (cap caches, `BindingGetterCache`,
   the name caches' pointer mode) become slot pointers, validated by generation, which a spill
   bumps. `trace_fields` reports the slots, in line or spilled, the own lists with their imports
   and the spill block. Dumps: the slot stride and offsets everywhere, the TDZ compare, the
   record's field offsets.
5. Fixed slots, generated stores, TDZ checks per basic block (20c, 20g). In a chunk without
   bridge-op state (`jit_needs_activation_state`, which block records, `with` or eval would need),
   the record's shape is fixed for the call: no direct eval can reach it (such bodies are prepared
   entries) and nested functions' evals hoist into their own records. So LoadCap, StoreCap,
   StoreCapInit (now with a template) and UpdateCap load and store at a fixed offset from
   `env_raw`, storing with the card mark (as `store_cap_ic` does, bytecode.rs:20437-20442), on both
   backends; the chunk's cap caches go. The helper only allocates and fills the header and template
   words, and the prologue's generated stores copy the captured parameters from their slots, as all
   three exemplars copy them. A read of the function's own captured lexical checks the empty word
   once in each basic block (SpiderMonkey's frontend/BytecodeEmitter.cpp:1603-1633); inner
   functions keep their checks. Dumps: the cap templates, the prologues.
6. Mapped arguments alias environment slots, and the side table goes (20f). A sloppy body with
   simple parameters whose `arguments` the proof does not cover, and since Decision 22 one it
   covers, keeps its parameters in its environment, and its arguments object holds that environment and, per mapped index, a slot
   number (V8's SloppyArgumentsElements, JSC's ScopedArguments): `arguments[i]` and the parameter
   share one word, as MakeArgGetter and MakeArgSetter alias them (spec.html:15130-15168), and a
   define or a delete unmaps the index (14960-14992, 15039). The map lives in the object (W2g's
   pattern): the address-keyed side table and its probe on the generic get and set paths
   (interpreter.rs:10146-10150, 10632-10652) go, and such bodies leave the prepared entry.
7. (W2e) In-line allocation of the record in the prologue: cursor take, header and template words,
   as SpiderMonkey's Baseline does.

Outside item 3. Derived constructors and instance elements become a series of their own, after
item 1b's full form puts new.target in the frame record (20h). The design drafted for them here
stands as its starting point: the derived record from a descriptor, `this` the empty word until
`super()` returns; the chunk as machine code (today it stays on the VM, interpreter.rs:
13483-13485); the construct sequence without allocating `this` (spec.html:14013-14014), its
finish per 14028-14033; `super(...)` through the construct sequence with the caller's new.target,
whose `prototype` the lean `this` allocation must read (19977-19982), then BindThisValue
(11277-11293) and InitializeInstanceElements (19988); a class's field definitions as an
initializer chunk called with the instance as `this`, as all three exemplars call an initializer
function. Captured names read by nested closures resolve statically, as (hops, slot) with guards
only under sloppy direct eval and `with`: a new item after the representation change
(Decision 21).

Risks

Semantic, with the clauses they touch (spec.html at e28783d5):
- FunctionDeclarationInstantiation (14247-14391): the prologue must make what it makes in the
  algorithm's order: parameter bindings (14302-14308), then the arguments object (14309-14321),
  then the parameters' values (14330; with duplicate names the last wins, as the plan's
  `slot(..., replace)` does), vars as undefined (14331-14341), lexicals uninitialized
  (14376-14383), hoisted functions last, closing over the new environment (14385-14388). A
  non-strict function's separate lexical record (14373-14374) is observable only through a direct
  eval's conflict walk (30558), which a compiled entry never runs; prepared entries keep the
  lexical attribute for it.
- TDZ (InitializeBinding 10828-10848, SetMutableBinding 10850-10886, GetBindingValue
  10887-10905): the empty word must never leave a slot as a value; every read path tests it (the
  stubs, the fixed slots, the tree-walker, `typeof`, reflection), and step 5's per-block elision
  holds only where the block's earlier check dominates the read; a derived constructor's `this` is
  the same word (BindThisValue 11277-11293).
- The elided objects (CreateUnmappedArgumentsObject 15059-15082, CreateMappedArgumentsObject
  15083-15168): the proof must see every use on the final operation stream; the argument words
  must stay unchanged for the call (the caller's operand stack under its top, the Rust entries'
  slices) and be read only while the frame runs, so a resumable body keeps its object; in strict
  code a formal the body assigns must read the argument, not its slot; an out-of-range read's
  undefined holds only under the protector; and a materialization must come before any author code
  (a getter on the prototype) can see the object, after which every read takes the object. Step 6
  must keep the map's aliasing exact through defineProperty, delete and freezing (14960-14992,
  15039-15058).
- Direct eval (PerformEval 30442-30535, EvalDeclarationInstantiation 30536-30671): bodies with
  direct eval stay prepared; their records take own lists with the deletable attribute; a deleted
  binding (DeleteBinding 10908) and SetMutableBinding's missing-binding step (10866-10870) must
  keep working once attributes leave `Binding`; a kept descriptor must never change in place, or
  every activation of the function would see another's eval.
- `with` (Object Environment Records, 10974-11040): unchanged; records under `with` keep the
  tree-walker, and the stubs keep testing each record's `with` word.
- OrdinaryCallBindThis (13887-13918) for a captured `this`: sloppy callees with non-object
  receivers keep the sequence's receiver gate (`CALL_IC_DIRECT_READY`).

Implementation:
- The collector: a prologue's environment is reachable only through the frame record's `env_raw`
  until a closure takes it, so the frame record's trace must report it (step 1), and the helper
  must reach no safepoint. Records sized by their descriptor (step 4): the trace and the marker
  read the count from the header, and a spill must set the count and capacity before the next
  safepoint.
- About 400 sites move in step 2; the tree-walker's records, module imports and the global
  declarative record are the cases with own lists.
- Cached binding pointers become slot pointers, which a spill moves: the generation must bump on
  every spill, as on every structural change today.
- Generators and async functions keep Rust-made records (their coroutine owns them); the prologue
  step is not emitted for resumable chunks.
- Every ARM64 call site grows by one instruction (20d).

Decided (Decision 20; the exemplars' answers kept)

Q1. The environment record keeps every binding in line, in a cell its descriptor sizes (20b), not
the draft's 64-byte record with two slots in place. [All three in line: V8's contexts,
SpiderMonkey's fixed slots (16, then dynamic), JSC's variables after a 32-byte header.]
Q2. Step 1 first, on today's representation; the representation change follows as its own series
(20a). [No exemplar bearing.]
Q3. The helper copies captured parameters during step 1, and generated stores take over as soon as
bindings are fixed slots: step 5, not W2e (20c). [All three copy in bytecode after creation;
SpiderMonkey removed its C++ copy loop in 2023 for that.]
Q4. `arguments` and rest arrays are elided where a compile-time proof shows every use is a length
or element read, with no run-time placeholder: a formal's index reads its parameter slot, an
out-of-range read goes through the prototype (20e, step 1). [Baselines elide only a lone
`arguments.length` (SpiderMonkey, JSC); TurboFan reads elements from the frame and JSC's FTL
eliminates Direct and Cloned arguments and CreateRest; SpiderMonkey removed run-time lazy arguments
in 2021. The exemplars leave this to their optimizing tiers; TRust JS has one native tier.]
Q5. Mapped arguments alias environment slots and the side table goes (20f, step 6). [V8 forces the
parameters into the context and maps context slots; JSC's ScopedArguments read the activation;
SpiderMonkey forwards captured formals to the CallObject.]
Q6. TDZ checks on a function's own captured lexicals are elided after the first in each basic
block; inner functions keep theirs (20g, step 5). [V8 elides per block by a bitmap; SpiderMonkey
checks once per basic block; JSC lifts the check after the declaration within the function and
keeps it in inner functions.]
Q7. Derived constructors and instance elements are a series of their own, after item 1b's full
form (20h). [All three: `this` is the TDZ word until `super()`, and fields run in an initializer
function.]
Q8. Captured names resolve statically, as (hops, slot) with guards only under sloppy direct eval and
`with`: a new item after the representation change (Decision 21). [All three resolve statically;
V8 falls back to `LdaLookupContextSlot` with extension checks, JSC to var-injection checks behind
a watchpoint, SpiderMonkey to dynamic name ops.]
Q9. Every ARM64 call site passes the argument count, one instruction (20d). [V8 passes it in a
register on every call; JSC and SpiderMonkey keep it in every frame.]

Step 1's record (afca0db6, b9241ae6, 2026-10-28, an agent's; Decisions 20a, 20d and 20e):
- afca0db6: a callee builds its activation, rest Array and arguments value in its prologue, as
  V8's CreateFunctionContext, SpiderMonkey's Baseline prologue and JSC's

### Immediates out of an instruction's range (design and record, 2026-10-29; Decision 23)

The ARM64 encoders check their immediates with `debug_assert!` only, so a template that misses
its range guard mis-encodes silently in release builds: the field overflows into the opcode bits
(`ldr_imm`, `str_imm`, `add_imm`, `cmp_imm_w`, the pairs) or wraps (`ldur`, `stur`, `ldur_d`,
`stur_d`, `ldurb` and the D pairs mask their field without even a debug check). Step 1's first
version stored `arguments.length` wrongly in a body with 5,000 formals. Decision 23: the encoders
accept any offset, as the exemplars' macro-assemblers do. The owner's question: does that require
a permanently reserved scratch register across every template?

Method. Exemplars: V8 at c8b709085e21 (target/p2/w3-design/v8-src, paths from its root;
register-arm64.h fetched at that commit), SpiderMonkey at mozilla-firefox/firefox 6bb811006a50
(paths under js/src; MacroAssembler-vixl.cpp from the copy fetched for this note, main on
2026-10-29), JavaScriptCore at WebKit/WebKit 260278048486 (paths under Source/JavaScriptCore;
MacroAssemblerARM64.h from the copy fetched for this note). Encodings checked with llvm-mc 23
(`llvm-mc -triple=aarch64 -show-encoding`). The census is of main a187b1f8.

How the exemplars do it

V8. `MacroAssembler::LoadStoreMacro` (src/codegen/arm64/macro-assembler-arm64.cc:936-959) emits
the scaled immediate form, else the unscaled one, else `LoadStoreMacroComplex` (961-989), which
takes a register from a `UseScratchRegisterScope`, moves the whole offset into it and uses the
register-offset form; out-of-range pre- and post-index forms move the base with an `add` before or
after the access. Pairs (`LoadStorePairMacro`, 991-1028) add the offset to a scratch register.
`AddSubMacro` (839-885) moves an unencodable immediate into a scratch (`MoveImmediateForShiftedOp`,
789-837, pre-shifting it where that saves an instruction). The pool is `DefaultTmpList()`, ip0 and
ip1, that is x16 and x17 (macro-assembler-arm64.cc:41; an FP pool beside it), and
`UseScratchRegisterScope` (macro-assembler-arm64.h:2564-2651) lends and returns them, nesting by
snapshot: `AcquireNextAvailable` is a release `CHECK` that the pool is not empty (2644-2650).
x16 and x17 are outside the register allocators' set (src/codegen/arm64/register-arm64.h:32-46,
`ALLOCATABLE_GENERAL_REGISTERS`), and hand-written code that names them takes them out of the
pool first (`temps.Exclude(x17)` around `Call(x17)`, src/builtins/arm64/builtins-arm64.cc:1994-1999;
the warning at macro-assembler-arm64.h:621-649). Sparkplug, V8's template-like baseline compiler,
wraps the same scope and adds x14, x15 and x19 to it for baseline code
(src/baseline/arm64/baseline-assembler-arm64-inl.h:18-41); the RegExp macro-assembler's register
map leaves x16/x17 to the assembler ("Very volatile", src/regexp/arm64/
regexp-macro-assembler-arm64.cc:45).

SpiderMonkey. vixl's `MacroAssembler::LoadStoreMacro` (jit/arm64/vixl/MacroAssembler-vixl.cpp:
1217-1305) takes a scratch from its `UseScratchRegisterScope` and prefers adding the offset's high
bits to the base and encoding the low bits in the access (1260-1270), which avoids materializing
the whole offset. When the pool is empty it recycles: it pushes two volatile registers that alias
neither the base nor the transfer register, lends them to the scope, adds 16 to an SP-based
offset, and pops them after the access (1241-1253, 1277-1280). Pairs add the offset to a scratch
(`LoadStorePairMacro`, 1316-1352), out-of-range pre- and post-index forms move the base, and
`AddSubMacro` (1069-1114) is V8's. The pool is ip0 and ip1 (MacroAssembler-vixl.cpp:36-40,
`tmp_list_(ip0, ip1)`, `fptmp_list_(d31)`), which `NonAllocatableMask` keeps from the register
allocator (jit/arm64/Architecture-arm64.h:196-201); `AcquireNextAvailable` is a `VIXL_CHECK`
(MacroAssembler-vixl.cpp:2082-2088).

JSC. `load64(Address, RegisterID)` (assembler/MacroAssemblerARM64.h:1849-1856) tries
`tryLoadWithOffset` (7949-7959: the unscaled form, then the scaled one), else sign-extends the
offset into `memoryTempRegister` and uses the register-offset form; stores are the same
(`store64`, 2383-2390), and `add64` with an unencodable immediate goes through
`dataTempRegister` (326-342). The two are x16 and x17 (56-57), reserved from the register
allocators (jit/GPRInfo.h:370-379, `reservedRegisters`); a region can forbid their use, and a
macro instruction that needs one there is a release assertion (`scratchRegister()` and the cached
temp getters, MacroAssemblerARM64.h:64-68 and 7635-7653). JSC caches memoryTempRegister's contents
to skip rematerializing an offset.

Why they do it, and whether the reason applies here. All three serve register allocators
(TurboFan, Maglev and Liftoff; Ion and Wasm's; DFG, FTL/B3 and the baseline JIT's register
assignment): any allocatable register may hold a live value at any instruction, so the only
register a macro instruction can always clobber is one the allocators never use. That is why the
scratch registers are reserved for good, and why hand-written code must take them through the
scope before naming them. TRust JS's ARM64 JIT has no allocator: templates name registers, and
every register has an owner somewhere. x0-x15 are temporaries and residents (the loop regions
allocate x0-x8 to resident values, `I_UNIVERSE`, jit.rs:16125); x16 and x17 are temporaries in
517 emitter calls in jit.rs and its siblings, the intra-procedure-call registers of the helper
calls (`ldr x16, [x21, #idx*8]; blr x16`), and the loop regions' first two receiver bases, live
across whole loop bodies of slot loads and stores (jit.rs:16655-16662); x19-x22 hold the context,
operand top, helper table and slot base; x23-x27 are the regions' pins and x28 their poll
countdown; x29/x30 the frame. No register is free for the encoders to own.

The answer to the owner's question

No. A permanently reserved register is what the exemplars need because an allocator may put a
live value in any other register; it is not what accepting any offset needs. Most out-of-range
forms need no scratch register at all:

- a load into a general register uses its destination as the address register, which the load
  overwrites anyway: `add x9, x22, #hi, lsl #12; ldr x9, [x9, #lo]` (SpiderMonkey's add-the-high-
  bits form, with the destination in the scratch's place);
- an add or subtract adds the high part shifted by 12 and then the low part, into its destination:
  `add x20, x20, #hi, lsl #12; add x20, x20, #lo`;
- a store, a SIMD&FP load or store, or a pair whose base is not SP and not a register it
  stores moves the base and moves it back: `add x22, x22, #hi, lsl #12; str x9, [x22, #lo];
  sub x22, x22, #hi, lsl #12` (V8 and SpiderMonkey move the base themselves in their out-of-range
  pre- and post-index forms; here the move is undone after the access);
- out-of-range pre- and post-index pairs move the base before or after the access, as V8's and
  SpiderMonkey's do.

What remains needs a register for a value with no destination to borrow: a compare (or flag-
setting add) whose immediate fits neither 12 bits nor 12 bits shifted, a store whose base is SP
or is the register it stores, and an add of 16 MB or more onto its own source. For those the
encoder recycles a register as SpiderMonkey's does when its pool is empty: it pushes x16 (or x17,
x15 or x14, the first the instruction does not name), uses it, and pops it, adding 16 to an
SP-based offset: `str x16, [sp, #-16]!; mov w16, #5000; cmp w1, w16; ldr x16, [sp], #16`.
The push and pop leave NZCV alone. It is safe everywhere the JIT emits code: every SP adjustment
in jit.rs and jit_regions.rs is a multiple of 16, so SP is always 16-byte aligned, and no
template keeps data below SP.

So no template's register convention changes, nothing is reserved, and no legalized form depends
on which registers a template holds: each is correct by construction, whatever is live. The cost
falls only on out-of-range operands, which ordinary code never has: every in-range operand
encodes exactly as today.

The design

Each encoder keeps its signature and, for an operand its own form encodes, its exact word, after
one mask test (`off & !(4095 * size) == 0` for a scaled access, a biased mask for imm7, one compare
for a 12-bit immediate), inlined at the call site, where it folds away for a constant operand; the
legalizing paths are out of line and cold. That keeps the compiler's own cost, which the fixture
counts include, to about 0.6 of an instruction per word emitted (see Measurement). Out of range, an
encoder legalizes by this ladder, taking the first rung that applies:

1. the instruction's own form (unchanged);
2. the other single-instruction form: scaled for an unscaled encoder whose offset is aligned and
   in the scaled range, unscaled (LDUR/STUR, -256..255) for a scaled encoder; for a compare or
   flag-setting add, the 12-bit immediate shifted by 12 when the low 12 bits are zero (identical
   flags);
3. no scratch: the destination as the address register (loads into a general register, LDP of
   general registers, ADDS/SUBS whose destination is not a source); the destination itself for
   ADD/SUB below 16 MB, through `#hi, lsl #12` then `#lo`; the base moved and restored (stores,
   SIMD&FP accesses and pairs whose base is not SP and not a stored register); the base moved
   before or after the access for pre- and post-index pairs;
4. a recycled register (push, use, pop), for what is left.

Offsets split as SpiderMonkey's do: the high part, a multiple of 4,096 below 16 MB, goes in an
`add` or `sub` with `lsl #12`, and the low part in the access's own field (scaled when aligned,
unscaled when the remainder is within -256..255); an offset that splits neither way is moved whole
into the address register and used through the register-offset form (into the recycled register
when the address register is the base itself).

Operands that are field widths, not offsets or values (shift amounts, bitfield positions, MOVZ and
MOVK's 16-bit lanes and their shifts, a logical immediate's prepared field), have no legal
meaning past their range: an out-of-range one is a template bug. Debug builds panic, as today;
release builds fail the compile instead of emitting a wrong word (the `ubfx` and
`orr_low_ones_x` encoders keep their release assertions and tests). A compare of SP with an
immediate past 12 bits and an add onto SP of 16 MB or more, which no template emits, fail the
compile in every build.

Failing a compile. The assembler records its first failure (`Asm::failed`); `checkpoint` and
`rewind` save and restore it, so a discarded optional region takes its failure with it. The
chunk compiler and the shared-stub assembler check it before finishing and return `None`, so the
function stays on the bytecode VM; `finish_with_offsets` asserts that nothing failed. The
conditional-branch fields checked after branch relaxation become a release assertion, like B's.

Fixed shapes. The JIT patches no code once installed. The sequences whose length other code
relies on are the prologue's first eight words and the epilogues' restore groups, which
`skip_unused_callee_saved_fp` rewrites in place; their operands are the frame constants, so
compile-time assertions pin them in range and no legalization can change their shape. The direct
call's position word follows branches only. The RegExp tier patches its branches, ADRs and literal
loads in `finish`, which already returns `None` when one does not reach.

The RegExp tier (regex_native_a64.rs, landed with W5b 3a). Its register map already reserves x16
and x17 as "the intra-procedure scratch", V8's convention, and its `add_any`, `cmp_any` and
`load_elem` legalize through x17. Its encoders are free functions returning a word; each field
past its range now returns UDF #0 (`UNENCODABLE`), which no instruction it emits ever is: `emit`
notes it and `finish` returns `None`, so the pattern stays on the matcher. Its slot loads and
stores (8 bytes a slot) legalize as the JIT's do, a load through its destination and a store
through x17 (no store's register or base is x17), and `retreat` goes through x17 past 12 bits, as
`advance` does through `add_any`. The single-bit operands (`orr_bit` and `tbnz` on LOGGED, below
64 when the plan is not wide) refuse the program past 63. Its program-level guard (MAX_SLOTS,
4,000, "AArch64's scaled 12-bit offsets reach 4,095") stays: it chooses the matcher for patterns
with that many captures, not a cheaper path, but lifting it changes which patterns run natively.
This design does not touch the code-size cap (MAX_CODE_UNITS: conditional branches without
veneers); the JIT's `relax_branches` is the shape to port when that is taken up.

Weighed and not chosen

- V8's scope over a small pool, with templates that use pool registers taking them through it.
  Reserving x16 and x17 means 517 emitter calls take them through scopes, and the loop regions'
  receiver pins (x16, x17 live across whole loop bodies) move to other registers or exclude the
  pool for the region. It is a permanent change to every template's register convention for a
  benefit the scratch-free forms give without it, and it would touch the cap templates the W3
  item 3 agent is changing. A template could also lend a register it knows is dead (V8's
  `Include`, Sparkplug's x14/x15/x19) to get two-instruction forms for stores; no template has an
  operand that reaches rung 3 in ordinary code, so nothing would use it today. When P3's
  allocating tier arrives, its allocator can exclude x16 and x17 and lend them to the encoders for
  its code: the ladder has a place for a lent register before rung 3.
- Forms with no scratch only, failing the compile where they do not apply. Simpler, but compares
  of variable immediates and SP-based stores would then fail where SpiderMonkey's recycling
  accepts them; recycling costs two instructions and two stack accesses only past the range.
- A debug checker that panics when an emitted instruction names a pool register the scope lent
  out, or one the template did not take. It turns the audit of 517 calls into a test-driven one,
  but it is the audit the pool creates: with no pool there is nothing to check, because no
  legalized form assumes anything about which registers are live. The tests check the legalized
  forms themselves instead: decoded words, and execution on Crystal.

  legalizing `ldur`, `stur` and `stur_d`;

  jit_operations.rs:792-859), the family whose missing guard surfaced the problem: past slot 510
  or 4,095 formals they took the helper only for the encoders' sake. Ordinary code is unchanged,
  and the thousands-of-formals tests now run their fast paths with legalized operands.
Lifting the other slot guards is a measured change of its own for later (it gives bodies past
about 510 slots native fast paths, which changes those bodies' code).

x86-64. jit_x64.rs states its rule (jit_x64.rs:414-416, "Always use a full disp32 addressing
form"): every variable memory operand is disp32, every branch rel32 with a checked conversion in
`finish`, every ALU immediate imm32. The narrow forms are constant byte sequences, plus
`add_sp(amount: i8)`, called only with +8 and -8, which would encode -128 as `sub r13, 0x80`, an
add of 128: it gets the one-byte form's full range. One silent range hazard of the same class
is real: `Op::New` passes `pc | argc << 16` to `jit_new`, which takes the pc as `packed & 0xFFFF`,
and x86-64 compiles chunks of up to u32::MAX operations (ARM64 stops at 65,535), so a `new` past
operation 65,535 would run another operation's site. Such a site takes the generic helper. The
RegExp tier's x86-64 encoders (regex_native_x64.rs) pick imm8 or imm32 by range, use disp32 and
rel32 (checked in `finish`), and take their counts below 2^31 from the compiler (regex_native.rs
filters loop bounds to `m < 1 << 31`); `bt`/`bts` take LOGGED's bit as an imm8 modulo 64, below 64
only while the plan is not wide, and `set_logged` truncated a mask past 32 bits: a bit from 64 on
now refuses the program, and a wide mask is moved whole.

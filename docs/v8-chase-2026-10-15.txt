Chasing V8: re-architecture program (2026-10-15)
================================================

Decisions (owner, 2026-10-15)
-----------------------------
1. Target: V8 is the reference embeddable engine; "credible" means
   chasing it. Acceptance surface: framework workloads (Vue/React/Djot
   fixtures, Speedometer 3.1) compared against Node/V8 on this ARM64
   machine. x64 (zombie) remains secondary.
2. Direction: GC-managed object model first, then a speculative
   optimizing tier (inlining, type speculation, deoptimization).
3. Continuity: a big-bang branch is allowed. This work lives on
   `rearch/v8-chase`; `main` stays shippable and keeps receiving the
   incremental pilot line. The branch may break embedding/tests while
   the new object model is under construction, but must return to full
   gates before any merge.

Why object model first when GC collection is ~1%?
-------------------------------------------------
Collection pauses really are ~1% (measured below); nobody should sell
this phase as "fixing GC time". The argument is the representation tax
plus sequencing:

- Every object today is Rc<RefCell<ObjData>> plus a separately
  allocated property Vec (Props entries). That is 2+ allocations per
  object, incref/decref traffic on every Value copy in the
  interpreter, bytecode VM, templates, and regions, RefCell borrow
  checks on hot paths, and pointer-chasing layout (RcBox -> ObjData
  -> Props -> entries Vec -> entry). None of that appears as "GC" in
  a profile; it is spread across every operation.
- Value/object layout is baked into every JIT template and region via
  JitLayout offsets. A speculative tier built first would hardcode
  RcBox layout, exact refcount maintenance at every deopt point, and
  allocation shapes that a GC heap would invalidate; the tier would
  be built twice. The removed Cranelift tier (4.5x kernels, ~0 on
  apps) is the standing warning about optimizing on this substrate.
- Escape analysis / allocation sinking / cross-call load elimination
  (the optimizations that actually close app-level gaps) require
  cheap bump allocation and freedom from per-copy refcount semantics.

perf stat, Vue whole process:
                task-clock  instructions  cache-misses  branch-misses
  trust-js        649ms       3.298e9        22.49e6        1.61e6
  node            168ms       0.737e9         2.72e6        2.98e6
We execute ~4.5x the instructions with ~8.3x the cache misses, and
fewer branch misses than V8. Read: too much generic code per
operation, and a cache-hostile object graph. That is exactly the
signature the object model + tier program targets; it is not a
"one hot function" profile.

Independent finding: Array.prototype.shift at ~343us/call on Vue is
an algorithmic/builtin problem (spec-ordered generic per-element
moves on large arrays, presumably) that no tier or GC change will
fix by itself. Such builtin work is branch-independent and may land
on main at any time; Phase 1 success metrics must not silently
depend on it.

Phases and gates
----------------
P0 (done): decisions + attribution above; branch created.
P1: GC heap + object model on this branch. Deliverables: tracing GC
  (mark-sweep first, generational later only if measured), handle/
  root discipline replacing Rc<RefCell<ObjData>>, single-allocation
  objects with inline property slots + out-of-line overflow, shapes
  carried over (incl. Pilot C descriptor-class encoding), string
  representation review. Design doc for P1 must be recorded and
  owner-approved before code. Exit gates to merge: full lib suite +
  Test262 parity with main; framework fixtures no slower than main
  beyond an explicitly accepted bound; Vue instructions and
  cache-misses measurably improved at equal or better elapsed;
  embed API restored.
P2: Baseline strengthening: call path (frame/argument costs),
  feedback completeness for the future tier, builtin algorithmics
  (shift class), RegExp.
P3: Speculative optimizing tier: inlining, type speculation with
  deopt, global load elimination, escape analysis/allocation
  sinking, range analysis. Reuse Pilot A-C/R1 guard infrastructure
  (class shapes, landing, region facts) as the proof layer.
P4: Long-tail parity: strings, JSON, collections, startup snapshots.

Expectation setting: P1 alone is expected to be roughly
performance-neutral-to-modestly-positive on elapsed time (its payoff
is enabling P3 and cutting instructions/cache misses); V8-class
ratios only become reachable after P3. If P1 measurements contradict
this (no instruction/cache movement), stop and re-plan before P2.

Status: P0 complete. Next action: P1 design record (heap/layout/
handle migration plan) for owner approval before code.

S0d rooting spike + scanning contract draft (2026-10-15)
--------------------------------------------------------
Spike code: crates/trust-js/src/gc_scan_spike.rs (test-only, cfg(test)).
Toolchain: rustc 1.99.0 (b940084d7 2026-09-28), aarch64, release opt.
All results below are this toolchain only.

Results (cargo test --release, 3 passed):
1. Recognized forms, with safepoint spill: raw pointer, tagged word
   (tag-masked), interior pointer (+3 words), struct-field pointer all
   found through a call boundary + volatile spill area.
2. Without spill, same-frame scan in optimized code found only
   {arena-base, struct-field} of {raw, tagged, interior, struct-field}:
   the compiler kept sole references in registers. The register-spill
   step at collection entry is therefore mandatory, exactly as Boehm
   warns; scanning is a contract, not a construction.
3. stacker segments are invisible to a main-stack scan and visible in
   their own range. Guessing bounds around a segment local segfaulted
   twice during the spike (guard pages both sides): segment bounds
   must come from a registry with exact ranges.
4. Scan cost: 100 scans of 1 MiB in 24ms with volatile reads
   (~0.24 ms/MiB, an upper bound; production plain reads are faster).
   At typical live stack depths (<=256 KiB scanned) this is tens of
   microseconds per collection — acceptable, will re-measure in S1.

Scanning contract (draft, for S1 to encode; owner-approved at go/no-go):
- Supported: rustc/LLVM as recorded above, aarch64 (+x64 re-validation
  on zombie at S6), shipped codegen settings. Re-run spike tests on
  every toolchain bump (they are compliance evidence, not proof).
- Recognized forms across any allocation point: raw cell pointer;
  tagged word (recognized after payload masking); interior pointer
  within cell bounds (page metadata). FORBIDDEN as sole reference:
  integer-cast addresses (as_ptr as usize round-trips — 68 sites
  inventoried), XOR/offset-obscured pointers, references reconstructable
  only from non-pointer data.
- Safepoint protocol: collection entered only via allocation slow
  path (a call); entry captures a register snapshot (S1 chooses asm
  capture vs setjmp-style buffer) and scans snapshot + stack ranges +
  registered root ranges. Rust-heap containers are traced/registered,
  never scanned.
- stacker: grown segments are no-GC regions (I9 pending-collect) until
  registered with exact bounds. S1's first task chooses: (a) wrapper
  deriving exact bounds, validated by a bounds-precision test, or
  (b) replace stacker::grow on GC-relevant paths with an engine-owned
  mmap grow with known bounds. Until then, collecting allocation
  inside an unregistered segment defers, never scans blindly.
- JIT frames comply via I7 (registers never hold sole references;
  canonical slots are stack-resident and scanned).

wasm32 decision: no stack scanning possible; no wasm toolchain exists
on this box (no rustup/wasm-pack/wasmtime; system rustc only), so the
prototype run is DEFERRED to S1 with tooling installation as its
prerequisite — recorded honestly rather than faked. Mechanism decided:
collection at (i) task boundaries, (ii) bytecode-VM loop safepoints
where state is canonical in CompactFrame slots (precisely rootable,
no Rust-local sole references at those points by VM design — S2 must
prove per-safepoint), (iii) native call entry/exit, never mid-native.
Long JS evaluations therefore stay bounded; a single long native
builtin allocating unboundedly is the residual risk, accepted for the
playground-scoped wasm crate and revisited if that changes. The S2
wasm32 sustained-allocation acceptance test remains mandatory.

S0e string accumulation decision (2026-10-15)
---------------------------------------------
Current mechanism: concat_owned(self) consumes the handle;
append_in_place only when strong==1 (lstr.rs:311-326);
append_prop_fast (interpreter.rs:8783) takes the slot value out,
drops the stack copy to manufacture uniqueness, grow-copies once if
aliased, then appends amortized. Oracle test added:
lstr::tests::accumulation_scaling_oracle_geometric_capacity_and_aliasing
(10k appends, capacity <= 4x len, alias at 1k unaffected) — passes.

Decision: builder-cell typestate. GC strings are immutable flat
cells. A distinct builder cell kind holds a geometric buffer and
exists ONLY inside the single slot being accumulated: first += on a
flat string converts it (one copy) to a builder in that slot;
subsequent += appends in place; ANY other read of the slot freezes
(builder -> flat copy handed out; builder may persist in the slot).
Builders never escape as Values, so uniqueness holds by construction
with no refcount and no sole-reference proof. Aliasing cost = one
freeze copy per aliasing read, matching today's grow-copy-once
behavior class. concat_owned maps directly (flat->builder convert or
builder append). Cons/rope rejected for P1: every string consumer
would need rope-aware reads; builder/freeze confines complexity to
the existing += fast paths (AppendProp, eval Add, builtins concat).

S1 review fixes (2026-10-15)
----------------------------
An outside review of 6b0b469c found defects in the S1 deliverables, each
reproduced against a byte-identical copy of gc_core.rs before fixing:
- Weak slots and ephemerons were registered globally and never pruned.
  A reused weak-holder cell had an ordinary word zeroed by the collector
  (memory corruption); a reused key cell next to a still-free value cell
  made mark_ephemerons spin forever (mark_cell ignored the free cell but
  `progress` was still set).
- collect() on a stacker segment scanned [segment SP, entry stack top)
  and crossed a guard page: SIGSEGV in debug and release, against the
  contract's "defer, never scan blindly"; nothing implemented "unregistered
  segments stay no-GC regions".
- The spike's adversarial tests exercise the spike's own scan(), not
  gc_core: the S1 suite passed with the register spill deleted.
- Five tests asserted deaths after same-thread conservative collects;
  sweep_hook_sees_liveness_for_side_tables failed at opt-level=1 and in a
  fat-LTO standalone build.
- Registrations were add-only safe fns over raw pointers; Heap had no
  Drop; the I9 debug assertions were missing; a fixed 1 MiB trigger,
  SipHash page lookups, a HashSet liveness set for sweep hooks, linear
  large-object lookup and O(released x pages) page release would have
  dominated the S2 GC-time and pause gates.

Fixes (crates/trust-js/src/gc_core.rs):
- Weak data is rediscovered every collection from reachable holders.
  LayoutDesc.weak reports in-cell weak slots and ephemeron entries; edge
  sources (Heap::add_edge_source) report side-table edges conditional on
  an owner cell and, for ephemerons, a key. A conditional edge fires at
  most once, when its conditions are marked (per-cell waiter bits), so
  marking stays linear and a condition that is never marked (a free
  cell) only leaves its edge unfired. Dead in-cell entries are zeroed;
  side tables prune through sweep hooks. add_ephemeron/add_weak_slot are
  gone. Unconditional trace roots are for true roots only: a side table
  traced as a root would keep every cycle through it alive.
- Native stack = per-thread chain of registered regions: the entry stack
  (enter_native_stack, RAII) and stacker segments entered through
  gc_core::grow. collect() defers when nothing is registered or SP is
  outside the innermost region; collect_at_safepoint() collects with
  registered roots only (wasm32 safepoints, task boundaries, tests).
- Contract option (a) chosen for stacker: grow() spills callee-saved
  registers into its own never-inlined frame, records that SP as the
  previous region's scan start, and derives the segment's exact bounds
  in the callback from stacker's limit (page-aligned base) and its
  sizing rule (max(1, ceil(size/page)) pages, stacker 0.1.25). A
  bounds-precision test compares the region with /proc/self/maps for
  64 KiB, 100,000 B and 1 MiB segments; a mismatch yields an empty
  region (collections inside defer) and panics in debug builds. Engine
  grow call sites switch to it at S2.
- Spill protocol encoded: Heap::mark_native_stack is #[inline(never)],
  spills x19-x30/d8-d15 (aarch64) into its own frame, reads SP with asm
  and scans [SP, top) per region. The x86_64 SysV spill/SP asm is written
  but NOT compiled here (rustc's and the system LLVM have only the
  AArch64 backend, `llc --version`): validate on zombie before x64
  authority.
- Registrations are RAII handles; a handle dropped from inside a
  collector callback is skipped for the rest of that pass and removed
  after it. Raw-pointer root ranges are unsafe fns and can be re-pointed
  after their container reallocates.
- Heap::drop finalizes the remaining cells and frees all memory (I5).
- I9: Heap::borrow_scope is the hook for S2's GcCell; a collection
  requested with a borrow outstanding panics in debug builds and defers
  in release; debug_assert_quiescent catches leaked guards; re-entrant
  collection asserts. Recorded deviation (see plan): a deferred
  collection runs at the next allocation or request after the outermost
  no-GC region exits, not at region exit (exit is not a safepoint).
- Heap growth: the next collection is due when allocated bytes exceed
  max(1 MiB, 2 x live) (set_heap_growth); allocation is charged at cell
  size. Pages: stable slots, FxHash map keyed by page number (page
  addresses would zero FxHash's low bits), per (descriptor, class)
  current page + avail list rebuilt each sweep, O(1) release. Large
  objects: BTreeMap by address plus span rejection. Sweep hooks read mark
  bits directly. deferred_collections counts pending requests, not
  allocations; deferred_native_stack added.

S2 ownership switch (started 2026-10-15; owner: proceed after S1)
-----------------------------------------------------------------
Baseline at 75e1b77d, default features (`cargo test -p trust-js --lib
--features embed`, debug): 2149 passed / 0 failed / 3 ignored, ~4.5 min
of test time.

Strategy. The GcCell payload is literally RefCell<Object>: Gc derefs to
RefCell<Object> in both builds, so the thousands of .borrow()/
.borrow_mut() sites, Ref/RefMut types and RefCell::as_ptr callers compile
unchanged. Rc-specific operations go through Gc associated functions
(as_ptr, ptr_eq, downgrade, strong_count, as_rc) that gc-heap
reimplements; each as_rc use marks a site that genuinely needs an Rc.
Planned I9 enforcement without a mutator-side borrow counter: the tracer
borrows each reachable object, and a mutably borrowed one aborts the
collection and defers it (debug builds assert, locating the site).

Step 1, seam (default build, no behavior change): Gc's Deref target
changed from Rc<RefCell<Object>> to RefCell<Object>. 755 call sites
(440 as_ptr, 123 ptr_eq, 108 downgrade, 84 strong_count) were rewritten
by a fixer driven by rustc's JSON diagnostics — only calls rustc flags,
never textually similar Rc<SymbolData>/Env calls — plus qualified paths
and ~15 hand fixes (weak upgrades in tests; jit_x64_property_tests,
found by inspection because this host cannot compile x86_64; a
trust-js-node test now compares identity through RefCell::as_ptr, since
Gc is not part of the embed API). Lib suite unchanged (2149/0/3);
workspace builds with tests; clippy clean with embed, embed+gc-heap and
for trust-js-node.

Step 2a, remaining Rc tricks behind the seam (default build, no behavior
change): WeakGc is a newtype whose upgrade() yields Gc (35 explicit
Weak<RefCell<Object>> types replaced); object refcount manipulation goes
through Gc::clone_from_raw (FnFrame::callee, old-collector marking) and
Gc::release (five consumed-callee fast paths in the bytecode VM);
jit_prepare_packed_numeric_mirror borrows the RefCell directly instead of
rebuilding an Rc; Gc::new_in(heap, ..) receives the owning Agent heap;
array_binding's destruction-observing strong-count tests became
Gc::outlives_release (always true on a tracing heap). Lib suite unchanged
(2149/0/3); clippy clean (embed, embed+gc-heap); workspace builds.

Step 2b, the gc-heap object model (collection still disabled): under
--features gc-heap, Gc is the Copy address of a gc_core cell holding the
RefCell<Object> (gc_handle.rs `cell`; the default `rc` implementation is
unchanged). GcState owns the cell heap (allocation never collects:
collect_on_alloc = false); the object finalizer is drop_in_place, so
Object::drop still runs at reclamation. WeakGc is a shared (address,
alive) cell tracked per thread and cleared by collections or heap
teardown. HeapRelease, the interpreter's LAST field, finalizes and frees
the Agent's cells after every other field has dropped. Tier::admitted()
clamps Jit to Bytecode (the JIT refuses admission in S2). Every
old-collector entry point routes to gc_collect_with_cause, a no-op under
gc-heap until step 3. Clippy allows clone/drop/forget on Copy handles
under gc-heap only (code is shared with the default build).
Default build: lib suite 2149/0/3 unchanged; clippy clean.
gc-heap: lib suite 1756 passed / 426 failed / 8 ignored. Failure
families: strong_count assertions in tests (no reference counts), ~150
JIT-tier tests (refused by design), reclamation and weak-clearing tests
(need collection: step 3), ownership-precision tests asserting

S2 design decisions from the step-3 survey (recorded in the plan before
acting):
- Collections run only at interpreter safepoints (gc_check, task
  boundaries, buffer pressure, explicit), as today; allocation never
  collects. The rooting obligation (I1) therefore applies at safepoints.
- Environment records must become heap cells in S2: Env is
  Rc<RefCell<Scope>> held in Rust locals throughout the tree-walker and
  VM, and the conservative scan can only discover handles that point into
  the GC heap. The same seam approach as Gc applies.
- Rust-heap Value containers live across a safepoint (spread and
  argument buffers, literal element vectors) need a rooted container
  (JavaScriptCore's MarkedArgumentBuffer is the analog), found and
  verified by stress collection at every safepoint with poisoning on.
- Roots: Interp::trace_gc_roots destructures Interp exhaustively, so a
  new field cannot compile until classified (Decision 2 enforcement);
  owner-keyed side tables become owner-conditional callbacks that trace
  an owner's side slots once it is marked.

Step 3a, environment seam (default build, no behavior change): Env is a
newtype (env_handle.rs) over Rc<RefCell<Scope>>, dereferencing to the
RefCell<Scope>; identity and ownership go through Env::as_ptr/ptr_eq/
downgrade/strong_count/from_raw/clone_from_raw and WeakEnv, as for Gc.
The four Scope constructions became Env::new(scope) (the scope already
names its heap). 173 calls rewritten by the same rustc-driven fixer
(generalized to pick the handle type from what rustc reports finding),
13 Weak<RefCell<Scope>> types became WeakEnv, and the bytecode VM's
raw-environment reborrows use Env::from_raw. Default suite 2149/0/3
unchanged; workspace builds; clippy clean on both feature sets; gc-heap
suite unchanged (1756/426/8).

Step 3b, environments as GC cells (gc-heap; collection still disabled):
Env is the Copy address of a gc_core cell holding RefCell<Scope>, with
its own descriptor (trace_scope_cell / finalize_scope_cell); WeakEnv and
WeakGc share one untyped WeakRef (address + alive flag). The cell
descriptors' trace functions are written: an object reports its own edges
(prototype, every property and internal slot, array-iterator target,
closure environment, bound/wrapped targets, native captures and retained
reporters), an environment its bindings, imports, parent and with-object.
Object, Callable, Exotic, Scope and Binding are destructured or matched
exhaustively (gc_trace.rs GcTrace), so a new field or variant does not
compile until classified. Default suite unchanged (2149/0/3); clippy clean
on both feature sets. gc-heap suite 1747/435/8: the 9 newly failing tests
assert refcount-timed environment releases (expected until collection).

Step 3c, collection at safepoints (gc-heap): the heap collects. Entry points
are the interpreter's safepoints — gc_check (live objects over the old
policy's gc_next threshold, the cell heap's byte budget of max(64 MiB,
2x live), a stress interval or a deferred request), task boundaries,
buffer pressure and explicit requests; allocation never collects.
- Marking (gc_collect.rs). Interp::trace_gc_roots destructures Interp
  exhaustively: each of the 169 fields is a root, an owner-conditional
  side slot, a Realm-group member, an ephemeron, weak, or value-free, and
  a new field does not compile until classified. The heap's MarkClient
  reports roots (interpreter fields; registered VM frames, running
  coroutines and rooted buffers; host roots and native-graph roots), side
  slots traced once their owner is marked (the 12 owner-keyed tables,
  generator continuations, native-graph JS owners, and Realm groups: a
  Realm is not a root, any marked member activates its whole group and
  its template cache), and ephemerons (WeakMap/WeakSet entries, symbol
  keys conservatively; the [[Realm]] edge of built-ins; host edges).
- Two-phase collection: mark, then the engine evicts the dead from its
  tables (the shared gc_sweep_dead_objects over dead_cells) while every
  cell is intact and new cells are allocated marked (gc_core: allocate
  black between the phases), weak handles are cleared (a dead cell a weak
  handle still names stays reserved, finalized, until the handle goes:
  inline-cache address compares stay ABA-safe), and finish frees.
- ShadowRealm interpreters share their parent's heap (one heap per Agent,
  I6: no edge crosses heaps). Only the root of the ShadowRealm tree
  collects, over the whole tree; a child never releases or detaches the
  shared heap.
- I1 rooting. drive_vm registers its frame state (slots, operand stack,
  references, class and disposal state, environments) for the call;
  Interp::call, construct, dispatch_native and the native fast path root
  their argument slices; a native invocation roots its captures. Rust-heap
  value containers live across a safepoint use rooting.rs: RootedVec
  (growable), root_slice (borrowed), Rooted<T> (any GcTrace state) and
  ValueRoots (values kept beside an opaque structure); all are plain
  buffers without gc-heap. Applied to argument evaluation, spread, rest,
  tail calls, groupBy, Iterator.zip/concat/toArray/chunks/windows, class
  definitions and decorators (both tiers), sort/toSorted/toReversed/with/
  toSpliced/flat, Set methods, Object.values/defineProperties, RegExp
  match/replace/split, Reflect.apply/construct, TypedArray.from, wrapped
  ShadowRealm calls, timers and Intl formatToParts. Found by GC stress
  (every lib test run in its own process with TRUST_JS_GC_STRESS=1:
  spread, Iterator.zip, toArray/chunks, and class decorators crashed or
  failed the heap verifier) and by a source audit of value buffers built
  across calls into JavaScript.
- Stack hygiene. Conservative false retention was dominated by stale cell
  addresses in reused stack memory, including the collector's own: its
  setup enumerated every Realm member and host value in frames the marker
  then reused, and its sweep handled dead addresses that later matched
  new cells. The client is built out of line and the stack scrubbed
  before marking; marking and sweeping are sibling calls; explicit
  collections and embedder entries (script evaluation, microtask
  checkpoints) scrub below themselves on entry and exit (1 MiB debug,
  128 KiB release). The scrub is inlined into its caller and zeroes from
  a frameless asm leaf: a scrubbing frame of its own left its unwritten
  slots stale, and the collector's next frame inherited a dead cell's
  address from one of them (six collectability tests failed once an
  unrelated edit moved the collector's frame layout). Retention diagnostics: TRUST_JS_GC_WHY=1 records why
  each cell was marked (root, stack word with its owning frame, cell,
  side slot, conditional edge).
- Stack growth on execution paths goes through gc_core::grow (registered
  segments); a thread registers its whole stack when it creates an
  interpreter.
- Test triage under gc-heap: JIT test modules are gated off (the JIT is
  refused until S5) and tier-looping tests assert JIT facts only for an
  admitted JIT; tests observing reference counts, refcount release timing,
  eager death notification, the refcount collector or its nursery,
  cross-Agent object edges, the HostGc omission fallback or handles that
  outlive their Agent are ignored with that reason; collectability tests
  keep strong handles and cell addresses out of the test frame
  (gc_test::in_frame / alive / HiddenAddress), since the stack scan
  retains whatever a frame still holds. Test builds also zero a thread's
  stack when it exits: libtest runs each test on a new thread, glibc
  hands it a cached stack with the previous test's words in slots not yet
  written, and a new heap whose pages land at the old heap's addresses
  took them for roots (an intermittent WeakSet collectability failure).
- GC stress over the suite: every lib test in its own process with
  TRUST_JS_GC_STRESS=1 (a collection at every safepoint; debug build, so
  the heap verifier and freed-cell poisoning run at each). Tests asserting
  when collections or cleanup jobs happen skip those assertions under
  stress (gc_test::stress_active). Tests of deep recursion, long chains
  and allocation loops exceed the 15-minute limit at interval 1 (each
  collection rescans the whole stack and heap) and run at interval 100,
  the three heaviest at 1000. Stress found one engine bug here: a stress
  or byte-budget collection reset the live-object threshold to the limit,
  so the handler of the limit's RangeError threw again at its first
  safepoint; only a threshold collection now enforces the limit or
  re-arms the threshold, and collections keep the handler's headroom.

Step 4 plan, function payloads (recorded before the work; gc-heap):

  through a weak handle, used only to set `constructor` when the
  prototype materializes. Each constructor's creation then allocates a
  weak cell and registers it, and a dead constructor's cell stays
  reserved (a zombie) until the collection after its death. A lazy word
  lives only in its function's properties (cloning one materializes it),

  The default build keeps the weak handle: a strong one would be a

Exit gate finding, fixed before the gate (pre-existing since S2):
- The per-test stress run failed one test,
  bytecode_fragment_cache::shared_syntax_never_shares_fragment_ic_state_
  between_engines (two engines on one thread run one parsed program,
  in two rounds). Under GC stress the heap verifier reported a
  function's `name` holding a cell outside its heap. Labeled tracing

Step 7b, polls (f61f10fb):
- The due word: under gc-heap the core keeps a word equal to
  collection_due() (gc_core::Heap::attach_due_word; the heap is its only
  writer). Heap::alloc adds one compare against a precomputed threshold
  (the byte trigger; under a stress interval the current total;
  usize::MAX once due) and recomputes out of line, so the allocation
  that spends the budget or reaches the interval sets it. A deferred
  request sets it; marking, the end of each sweep and the settings
  recompute it. It sits beside GcState's live-object count
  (value::LiveCount, repr(C), gc-heap only) and is attached when the
  heap is created. gc_check asserts in debug builds that it agrees with
  collection_due().
- Polls (ARM64, gc-heap): JitCtx::live_objects already holds the count's
  address, so entry and loop polls load count and word with one LDP and
  take the H_INTERRUPT slow path while the word is set (12 fast-path
  instructions; 11 in the default build, unchanged). A general region's
  backedge guard (11 to 12) bails to its canonical header the same way.
  A direct call's safepoint is its callee's entry poll: the comments
  that said the direct call checks a gc tick are corrected, and the
  callstat mirror gains the inline-retry gate it lacked and loses two
  gates the sequence never had.
- While collections are suppressed or deferred, and in a ShadowRealm's
  interpreter (its root collects), the word stays set and every poll
  calls the helper. A region then bails on each backedge after a whole
  iteration and re-enters at the header, so the loop progresses.
- The recorded deviation, as emitted code: in a chunk body's baseline
  code each call to an allocating helper ends in an explicit poll once
  the helper has returned with its results in canonical places (3
  instructions while the word is clear, else H_INTERRUPT). It is emitted
  after the call, not run in the Rust helpers, because region checked
  effects call the same helpers and must not poll; region code and

Step 9 plan, from a read-only survey at 08122116 (with sub-surveys of
the emitter sites, `this`, string constants and bindings, spot-checked
against the source):
- Under gc-heap a packed word owns nothing but a lazy prototype's
  Rc<LazyFunctionPrototype>: BigInt, String, Symbol and Object payloads
  are cell addresses. A lazy word is only ever the value of a function's
  "prototype" property (one creation site). Rust materializes it at
  every property-to-execution boundary; generated code keeps it out at
  3 emitter sites and 2 region read guards; execution storage never
  holds one.
- Generated code still routes ownership for nothing under gc-heap: the
  13-instruction owner guard at 30 sites whose word is never lazy, and
  14 BigInt-only and 4 never-lazy inline tag tests. Two traps: in
  emit_store_local the BigInt test before the slot release and the
  clone after it go together; the region materialize clone has no slow
  path and relies on the read guards before it.
- `this` is packed up to each JIT entry and widened there (JitCtx.
  this_val is a Value, reached through this_raw); a direct call decodes
  it (33 instructions). JitCtx is repr(C) and later fields are reached
  by offset_of!, so a packed this_val must be gc-heap only.
- String constants: the template loads the cell from the chunk's
  constant slot and tags it. An immediate is safe under gc-heap (the
  chunk's RootedVec roots the cell, cells don't move, chunks don't cross
  Agents) but must stay out of the process-wide stubs; the default
  build keeps its increment (in-place append needs a count of 1).
- A packed Binding.value would leave the environment cell in its
  128-byte class; the gains are in the binding load and store
  sequences.

Deviations from the plan's step 9, recorded before the work:
- "The execution word is Copy": not literally. PackedValue keeps its
  Cell<u64>, since shared slots are written through &self (mapped-
  argument aliases, SlotAccess, slots the VM lends to generated code)
  and a Copy type cannot contain a Cell. Under gc-heap it gets no Drop
  and a Clone that copies the bits (debug-asserting a non-lazy word),
  pinned by a !needs_drop assertion, so copies and drops are free.
  Literal Copy needs one Cell<Word> slot type, simpler once the counted
  build is gone: an S6 item. Value stays non-Copy under gc-heap; its
  drop glue is already empty (also S6).
- "Lazy prototypes kept out of execution" already holds. Step 9 also
  makes the lazy prototype a gc-heap payload cell (as S4 did for
  UserCallable), so that no word owns an Rc once Drop goes and property
  overwrites release nothing. If the cell measures badly, Property owns
  the Rc instead (recorded if taken).
- "`this` travels packed" covers JIT contexts, entries and direct
  calls; the VM's `this` (run, drive_vm, VmCoro) stays wide.

- Soundness, re-verified at HEAD:
  - The pool (consts) is a RootedVec, built once and only read
    afterwards. It roots its cells until the chunk drops. Chunk has no
    custom Drop, so no safepoint runs between the pool's drop and its
    code's.
  - The chunk owns its code (Chunk::jit and its OSR sidecar). Each
    compile commits into its own chunk's slot, and Chunk is not Clone.
  - Cells never move: the heap is a non-moving mark-sweep.
  - No code is shared between chunks or Agents. The fragment cache is
    per Interp, and a Plan owns its Rc<Chunk>. Static snapshots decode
    per Agent, with empty code cells. An inlined callee compiles into
    the caller's own pool. No thread-local holds a chunk or an AST.
  - GLOBAL_STUBS is process-wide, and SharedStub::emit takes no chunk.
  - Word 0 of a gc-heap string cell is the frontier, not a count. A
    constant is allocated at exact capacity (LStr::from), so any
    non-empty append copies.
  - So the immediate is as valid as the pool's own Value, which the
    VM's Op::Const pushes.

  default-only, as 9c made jit_add_strings'. gc-heap appends at the

S5 review fixes (outside review of 37a3e12f, 2026-10-18)
--------------------------------------------------------
- [P1] A proper tail call's argument list was unrooted in most of the
  trampolines that run it. Past the ordinary-call depth (Op::TailDeep)
  a tail call leaves pending_tail, which the collector traces, holding
  the callee, the receiver and a Vec<Value> of arguments. A trampoline
  takes it out, so the list sits in a Rust-heap buffer the stack scan
  cannot see. Interp::call rooted the list (root_slice) from the take
  through its GC check and the call. The six JIT trampolines did not:
  jit_direct_finish, call_jit_committed_packed, call_jit_env_committed_
  packed, call_native_committed, call_jit_fast and construct_jit_fast.
  Their GC check could collect the arguments, and so could a Proxy
  callee's `apply` getter, which runs before the trap's argument array
  exists.
  - Fix: every trampoline takes the call through one step,
    Interp::run_pending_tail. It roots the list from the take through
    the check (amortized or not, as each path checked before) and the
    call. Interp::call uses it too.
  - Reach in the default configuration: direct calls return to the
    committed path from depth 128 (MAX_DIRECT_CALL_DEPTH), and tail
    calls are staged only from depth 1024, so jit_direct_finish drains
    one only with TRUST_JS_TAIL_CALL_DEPTH below 128. The committed,
    env and fast paths drain them at any depth past 1024.
    construct_jit_fast never sees one: both construct paths refuse a
    body with tail calls. Only a test native leaves a pending call with
    arguments for call_native_committed.
  - A JavaScript getter can mask the gap in the JIT paths. The callee's
    frame record returns to the pool, the getter's activation pops it
    again, and an active record's words are scanned whole. Its stale
    operand words then hold the arguments.
  - Test jit::rooting_tests::tail_call_arguments_are_roots_in_the_
    trampoline (gc-heap, ARM64). At depth 1024, with direct calls let
    run that deep, strict compiled functions tail-call a Proxy with
    two fresh objects. A native `apply` getter collects, so no JIT
    record is active, and reports that roots marked both objects; the
    trap then reads them back.
    - The calls drain through Interp::call (a Rust entry and the JIT's
      generic call), call_jit_fast, call_jit_committed_packed, its env
      variant, and jit_direct_finish once the callees are settled.
    - Mutation runs, one at a time: with the root removed from the
      step, or any one of those five sites taking an unrooted copy of
      the step, the test dies with SIGSEGV when the trap reads a freed
      object.
    - Unrooting call_native_committed or construct_jit_fast changes
      nothing here (see reach above).
  - The tree-walker's try/finally also takes pending_tail, keeping it
    in a Box across its finalizer. HasCallInTailPosition leaves nothing
    to keep there: a try block runs with tco_ok false, and a catch
    block keeps it only when there is no finalizer.
- [P2] difftest: classify_crash convicted a compiled tier whenever the
  interp oracle's rerun "completed", and running out of budget (the
  wall clock, or the allocation cap's abort) counted as completing. A
  program the interpreter could not finish was therefore reported as a
  crash of the first compiled tier that died on it.
  - Fix: a rerun now ends Completed, Exhausted or Crashed (Run). Only a
    Completed oracle can convict a compiled tier, and only one that
    Crashed. An exhausted or crashed oracle leaves the program
    inconclusive, as does a compiled tier that only runs out of budget.
  - The decision is a pure function (crash_verdict) beside run_end, so
    tests cover it without children: an exhausted or crashed oracle
    gives Inconclusive whatever the compiled tiers did. The old
    decision fails the first test (it convicts bytecode under an
    exhausted oracle).

Owner decisions (2026-10-18):
- The plan's non-goal "generational collection" is lifted. With
  full-heap collection, lowering the budget floor for RSS means more
  full marks of the whole live heap, and raising it costs RSS. A
  nursery removes that trade. S0 measured high infant mortality: on
  Vue, 85k of 151k deaths within 16 allocations of birth.
- Order: flip and delete first, so a write barrier goes into one model
  only. Then two cheap levers, measured: the byte budget replaces the
  inherited 100k-object trigger, and marking finds a cell's page
  directly instead of hashing every edge. Then the nursery, as its own
  step.
- 64-bit targets only. wasm32 leaves P1's acceptance (its criterion
  retires), and trust-js-wasm's wasm32 build stops being a P1 target.
- zombie (ruby@zombie, x86-64 Linux) validates x86-64 natively. It
  also validates Windows: x86_64-pc-windows-msvc, cross-built there
  with cargo-xwin and run under Wine.

Interruption tests made deterministic (2026-10-18). tests::
interruption_aborts_a_running_microtask_checkpoint and tests::job_
callback_context_is_restored_on_host_interruption (step 3's open item)
armed a 20 ms deadline before evaluating a script that queues a
spinning job. Reproduced with an experiment test (not kept): a script
body interrupted after queuing a job leaves the job to the next
evaluation's checkpoint, at bytecode and at jit. In these tests that
job spins, and the test clears the deadline before evaluating again.
Their spinning jobs now arm the deadline themselves (armDeadline(), a
test native), so it can expire only while a job runs. Both tests pass
in both builds on aarch64, x86-64 and Windows under Wine. Open for
the owner: whether an interrupted script's queued jobs should survive
it (the checkpoint clears its queue on an interrupt; the script body's
path does not).

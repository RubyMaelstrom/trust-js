## Goal

The program defines P3 as "Speculative optimizing tier: inlining, type speculation with deopt,
global load elimination, escape analysis/allocation sinking, range analysis. Reuse Pilot A-C/R1
guard infrastructure (class shapes, landing, region facts) as the proof layer." This plan builds
that tier the way V8 built Maglev: a whole-function speculative compiler directly above the
template JIT, fast enough to compile on the main thread, that inlines, speculates from feedback,
deoptimizes eagerly and lazily, and removes redundant checks, loads and allocations while it
builds its graph. On this machine that tier, not TurboFan, is where V8's lead comes from (below).
The proof layer carries over: shapes as proofs (P2's W4 step 9) become the tier's shape checks and
dependencies, the regions' landing generalizes into the tier's exits, and region facts become the
known facts its builder keeps per value.

The passes the exemplars run only in their top tiers (function-wide value numbering with alias
analysis, loop-invariant code motion, range analysis with bounds-check elimination, general
allocation sinking) go to a top tier on the same front end, after this one (Decision 2): the
exemplars' mid tiers (Maglev, the DFG) leave them out for compile time, and pinned to one CPU Node's
top tier loses to its mid tier on the fixtures, Web Tooling and ARES-6.

Acceptance surface, unchanged (the program's Decision 1): the Vue, React and Djot fixtures and
TRust's Speedometer replays against Node on Crystal (ARM64), x64 on zombie secondary; the standing
comparisons are full Octane 2, Web Tooling, ARES-6 and the call microbenchmarks.

The yardstick is Node limited to Maglev (node-mg, `--max-opt=2`), V8's speculative mid tier,
measured in the same session; full Node and Node limited to Sparkplug alongside. Phase exit
(Decision 1): each fixture within 2x of node-mg in its measured pass and in steady
state, and Octane's geomean within 2x of node-mg.

### The code (survey of main 1ca9b3e1)

The full survey, every claim cited at 1ca9b3e1, is target/p3/survey/code-survey.txt (sections 1-9
and a table of the deliverables). What the tier is built on:

Tiers. A function starts on the tree-walker, which has no pcs and no feedback; after 8 calls or
128 tree-walked back edges (scaled by source size) it compiles to bytecode, and its first bytecode
run compiles its native first stage (compact templates outside loops, loop register regions), so
the VM runs almost none of an ordinary function. At about 100, 500, 2,100 and 8,500 native runs a
function may recompile once as a second stage: a new chunk compiled from the AST with up to four
callees a site spliced in behind closure-identity and Realm guards, with acyclic spans and regions
where their operations ran. C1 recompiles once more without property chains. Every compile is
synchronous on the calling thread. A call site finds its callee's code through its own call-cache
way; A2 sends entries into a superseded chunk to a helper that refills the way in place. Code is
discarded only by the code cache's CLOCK sweep (128 MiB budget), never because a speculation failed.

Speculation and its exits. Regions (ARM64 only) are register-allocated copies of loops and acyclic
spans inside the function's one code object. Their SSA (jit_ir.rs's RegionIr: block parameters for
every local and stack slot, a verifier, Rep tags nobody reads) serves planning; the emitter re-walks
the bytecode with an abstract operand stack. They speculate on Number-ness, on int32-ness for
bitwise operators, on receiver shapes from the live inline caches and on callee identity, never on
W4's records. A failed guard materializes the virtual operand stack and the numeric homes into the
canonical frame and branches to the baseline template of the same pc in the same code: that is all
the deoptimization the tree has. deopt.rs (CopySlot recipes, root maps) is metadata only tests use.
Nothing counts bails; no code is patched after it is mapped; there is no lazy deoptimization, and
running frames finish in the code they started in.

Feedback. W4's always-on records (value classes per arithmetic and comparison pc, element facts,
named ways with a generic mark, call targets with a megamorphic state) and its typed read API
(feedback_read.rs) exist for this tier: "The speculative tier is the API's consumer". The
dependency registry (dependency.rs: watchpoint sets for prototype shapes and the Array elements
protector, desired watchpoints checked at install) is attached to no code. Allocation sites have
images and templates but no counts or survival (W4 step 8, moved to P3).

Values, frames and the collector. Values are NaN-boxed words; a Number is its f64 bits, and there
is no int32 value representation (int32 exists only inside regions and chains). Locals and operands
live in pooled frame records on the Rust heap (the canonical frame: x19 the context, x20 the operand
top, x22 the slots), not on the native stack; native frames are found through activation records
(no frame-pointer chain, no unwind tables; helpers are extern "C", and release builds abort on
panic). The collector is non-moving mark-sweep with sticky marks and scans the native stack, the
callee-saved registers and the frame records conservatively, resolving interior pointers through
its page table, so generated code needs no stack maps and a raw pointer in a register or a spill
slot is a root. The write barrier is an unconditional card mark; in-line allocation takes cells
from bitmap cursors, without zeroing and with no barrier needed before the next safepoint. Code
polls at entry, at back edges and after allocating helpers.

Backends. ARM64: an encoder of 118 instructions with labels, relaxation and Decision 23's
legalizer for any offset; 41 helpers with a (ctx, pc, sp) ABI on the canonical frame; 22
process-wide shared stub families; direct JIT-to-JIT calls through call-cache ways. x86-64 is much
thinner: no regions, chains, in-line f64 arithmetic, shared stubs or direct calls, and every call
goes through Rust. Code memory is one W^X mapping per chunk, written once. Native code exists on
Linux, macOS and Windows.

What P3 has to build, against what it can reuse (survey section 8):

| P3 deliverable | exists | missing |
| --- | --- | --- |

| speculation, eager deopt | region guards that land in the same code | a separate optimized code object whose exits land in baseline code or the VM at any pc; run-time deopt metadata |
| lazy deopt | the dependency registry; activation records | any link from the registry to code; any validity check in running code |

| GVN, load elimination, LICM | local guard and load reuse in effect-free spans; loop-chain preambles | function-wide value numbering; a heap alias model |
| escape analysis | in-line allocation; literal images | virtual objects; materialization at deopt; allocation counts |
| range analysis | loop chains' crude integer ranges | a range lattice; bounds-check elimination; int32 arithmetic with overflow checks |
| OSR at loop headers | VM-to-native entry into borrowed frames | native-to-native OSR; back-edge counts in native code |
| register allocation | fixed homes in regions | liveness, spilling, edge moves, a whole-function allocator |

Three of their reasons decide most of the design for TRust:
- Compile time on short runs. V8 added Maglev for code that spends "a lot of time in functions that
  don't get hot enough to be optimized by TurboFan" (its Maglev post, on Speedometer), and JSC
  keeps the DFG because tuning it for long-running code "would hurt short-running programs where
  the DFG's compile time played a larger role in total run-time than the quality of the code".
  TRust's fixtures run 30-200 ms, and TRust compiles on the main thread.
- The heap. TRust's collector is JSC's design point (non-moving, sticky marks, conservative stack
  scanning), under which "compilers don't have to worry about how to report pointers to the
  collector" (JSC). V8's and SpiderMonkey's precise maps exist because their collectors move
  objects ("GC things cannot move" was SpiderMonkey's reason to leave conservative scanning).
- Write-once code. TRust's code memory is written once and then mapped read-execute, and its native
  frames keep no frame-pointer chain. JSC's linked DFG and SpiderMonkey patch code to reach frames
  of invalidated code, and V8 rewrites return addresses it finds by walking frames. JSC's unlinked
  DFG tests a validity byte at each invalidation point instead (`branchTest8` on
  JITData::offsetOfIsInvalidated, dfg/DFGSpeculativeJIT.cpp:609) and reaches its exits through a
  jump table of data (dfg/DFGJITCode.h:156-166); both work with write-once code.

## Design: the tier

1. Its place among the tiers. Functions keep starting on the tree-walker, and their first stage
   (the template JIT) still compiles at the first bytecode run after 8 calls, as V8 compiles
   Sparkplug at 8. The tier then compiles a hot function once, whole, with its inlined callees, in
   place of the second stage: a function the tier compiles gets no second stage, and a function it
   refuses (an operation it does not handle yet, a size limit) keeps today's second stage until
   the tier covers it. Whether second stages, their AST splicing and C1 are retired is decided at
   the phase's end on the measurements (Decision 3).

2. When it compiles. As V8 counts: a budget of executed work, not calls (V8's budget is invocations
   times bytecode length, drawn down at back edges and returns; TM:187-195 in the survey), so loops
   and long functions tier sooner per call; the first stage counts its back edges for it (tier 1's
   step (c)). At Maglev's threshold (400 invocation-equivalents), and only once the function's
   feedback has settled: V8 waits 500 invocations after any IC change
   (minimum_invocations_after_ic_update), JSC until 75% of its value profiles are live
   (CodeBlock.cpp:3020-3089). Compiled once; recompiled only after an invalidation or repeated
   exits (point 12). This replaces the four inline checkpoints, since no exemplar recompiles a tier
   on a schedule. Stage 1's note calibrates the numbers by measurement.

3. The front end. At compile start the tier reads every site of the function and of its inlining
   candidates through W4's read API into an immutable per-compile summary (V8's ProcessedFeedback,
   JSC's status objects, SpiderMonkey's WarpSnapshot); the builder then reads only that summary and
   the immutable bytecode (point 13). It builds from the function's first-stage chunk, so pcs,
   feedback sites and the exits' resume points coincide. One forward pass over the bytecode
   interprets the canonical frame (locals and operand stack) abstractly, as MaglevGraphBuilder
   interprets Ignition's registers and WarpBuilder the bytecode stack; loop phis come from a
   liveness and loop-assignment prepass (jit_ir.rs's Cfg, live_entry_locals). Each value carries
   known facts (possible shapes, representation, properties loaded under an effect epoch; Maglev's
   KnownNodeAspects), so the builder never emits a check or a load it has proven. A site with no
   feedback becomes an unconditional exit that ends its block (Maglev, Warp, the DFG), which gives
   the tier the regions' scope -- only code that ran is compiled -- without region boundaries.

4. The IR. A CFG of basic blocks of SSA values (all three engines; V8 left the sea of nodes over
   cache misses, compile time and hidden loops, reasons that are properties of the IR), on
   jit_ir's blocks, dominators and loops. Values have representations (the tagged word, f64,
   int32, bool, a cell pointer), and checks are explicit nodes (shape, Number, exact int32, bounds,
   callee identity or code). Each check carries the frame state of its eager exit, and each
   effectful node the frame state after it, at the next bytecode (SpiderMonkey's resume-point rule:
   nodes without side effects need no state). A frame state is the bytecode pc, the IR value of
   each live local and operand slot, the handler nesting at the pc and the parent state of an
   inlined frame. Each node declares the abstract heaps it reads and writes (JSC's clobberize over
   a small hierarchy: named properties by key, elements, array lengths, the frame, everything),
   which known facts, barrier elision and invalidation points all need. Numbers stay NaN-boxed f64
   words outside the tier (Decision 5): int32 is a representation inside it, checked on load with
   FJCVTZS where the CPU has FEAT_JSCVT (one instruction that converts with JavaScript's semantics
   and sets the Z flag when the result is exact) and boxed with SCVTF on the way out.

5. Speculation, per site (JSC's status model; V8's in substance). Named access: one shape gives a
   shape check and a direct load or store by slot; up to four shapes, an in-line shape dispatch;
   megamorphic or mostly slow, the generic path (the engine's stub cache); never run, an exit.
   Prototype-chain reads: the holder's shape through a dependency (point 7) where SpiderMonkey's
   test passes, a guard per level otherwise. Elements: the element record's facts as kind checks,
   with the bounds checks kept (a mid tier runs no range analysis). Arithmetic and comparisons: rule
   U's value classes choose int32 with overflow checks or f64. Calls: a monomorphic target's
   identity, or its code for closures of one function (point 8), with a direct call or inlining;
   natives by builtin id, as in-line operations or through their fast entries; megamorphic sites,
   the generic call. A site whose exit flag is set (point 12) does not speculate (JSC: "We typically
   use the presence of an exit flag as an excuse not to speculate at all for that bytecode").

6. Exits (eager deoptimization). A failed check is one instruction into a shared entry (V8's form: a
   `bl` to a shared label, the exit's index taken from the return address), which saves every
   register and calls the Rust deoptimizer. The recipe is representation-aware, as V8's
   translations are (a register or spill slot holding a tagged word, f64, int32 or bool; a
   constant; captured and duplicated objects for escape analysis, point 9), delta-coded or shared as
   V8 and SpiderMonkey do. The deoptimizer boxes values, materializes captured objects (a fresh box
   for each mutable number, as V8 does), records the exit in the exit profile and the failing
   value's class in the value record (JSC's exits write the profiles), and rebuilds one canonical
   frame per function, inlined ones included. The innermost frame resumes in its function's
   first-stage code at the exit's bytecode boundary through that code's per-pc table (JSC's target,
   through its jitCodeMap; TRust's region bails already land in baseline code at a pc), or in the VM
   when that function has no first-stage code (evicted, or never compiled; JSC's LLInt fallback).
   Outer frames resume after their call op with the inner frame's completion, a value or an
   exception (V8 resumes them at the next bytecode); each frame runs to its completion through a
   real call, as SpiderMonkey pushes its rebuilt frames, and the outermost completion returns from
   the optimized activation to its caller. SpiderMonkey's alternative, resuming in its interpreter,
   rests on its baseline code then needing no per-pc table; TRust's first stage keeps that table
   for its unwinder anyway, and resuming in compiled code keeps the rest of the activation fast.

7. Dependencies and lazy deoptimization. The builder records each fact it relies on without a check
   (stable prototype shapes, the Array elements protector, String.prototype's ObjectFuse, constant
   globals) as desired watchpoints (dependency.rs, attached to no code today); install re-validates
   them at the end of the compile (V8's commit, JSC's plan finalization) and attaches the code's
   dependencies. A firing marks the code invalid in a validity word of its own data, unlinks it for
   new calls (the function falls back to its first stage, as V8 resets the dispatch entry and JSC
   jettisons), and running frames exit at their next invalidation point. An invalidation point
   follows every node whose effects can fire a dependency: a load of the validity word and a branch
   to that point's exit, at the next bytecode boundary (JSC's unlinked DFG). The exemplars split
   here, and TRust's constraints decide: JSC's linked DFG patches a jump at each point and
   SpiderMonkey patches its post-call OSI points, which TRust's write-once code rules out; V8
   rewrites the return address of each frame of marked code, which here would need every call out of
   optimized code to record where its return address lies (as V8's exit frames do), a lazy exit per
   call site, and V8's rule against operations that can exit both eagerly and lazily, because such
   an exit lands mid-bytecode. Exiting at the next bytecode boundary is JSC's argument ("letting the
   remaining effects of the current bytecode instruction finish executing in optimized code and then
   triggering an OSR exit right before the start of the next bytecode instruction"); the price is a
   load and a branch per invalidation point, next to the call or effect it follows. SpiderMonkey's
   test decides which guards become dependencies: facts that are rarely popped and cheaply detected
   (doc/how-we-optimize.md:37). References from code to cells are weak, and code whose referenced
   cell dies is jettisoned (JSC; TRust's call pins are weak today); code an activation runs stays
   alive (running_code).

8. Inlining. In the builder, as all three do it: the callee's bytecode is built into the caller's
   graph with its own frame-state chain, so exits rebuild its frame. Maglev's policy: depth 1,
   callees up to 100 bytecode bytes with 920 cumulative, small callees (up to 27 bytes) to depth 10,
   call frequency at least 0.95 of the caller's invocations (which needs the per-site call count W3
   parked), no recursion; and Maglev's polymorphic loads whose arms call constant functions inline
   those. Closures by code, the direction decided in P2: the call cache gains a "same code, other
   closure" state, as V8's FeedbackCell, SpiderMonkey's GuardFunctionScript and JSC's despecified
   executable do, and the guard checks the callee's function literal, with the closure's environment
   a value. SpiderMonkey's per-call-site callee feedback (trial inlining) waits until spliced
   callees' shared caches are measured going polymorphic.

9. The mid tier's forms of the program's optimizations. Check and load elimination by known facts
   during the build (Maglev), cleared by the read/write sets and merged at joins; Maglev's CSE; phi
   untagging and truncation to int32 where every use truncates; escape analysis as Maglev runs it by
   default (maglev_escape_analysis): an allocation whose only uses are frame states and stores into
   other elided allocations is not made, and the exits materialize it (its shape and field sources;
   nested and duplicated objects by id), for which deopt.rs's CopySlot-only recipes gain that kind.
   Function-wide value numbering with alias analysis, LICM, range analysis and general allocation
   sinking are the top tier's (Decision 2).

10. Registers and code. Maglev's allocator: one forward pass over the scheduled blocks, with live
    ranges and next uses computed first, a value spilled at its definition (one slot), and the
    register with the farthest next use evicted. The collector scans the native stack and the
    callee-saved registers conservatively and resolves interior pointers, so spill slots and
    registers need no maps (JSC); the shared exit entry saves every register, so eager recipes may
    name registers, and the inputs of lazy exits are spilled at calls, as Maglev spills them. Code
    generation uses the ARM64 encoder and Decision 23's legalizer; operations the tier does not
    lower run as effects: the canonical frame written, the operation's baseline template emitted
    through jit_operations.rs, its results reloaded (corrected by stage 1's note: jit_operations.rs
    emits canonical-frame templates, not a register ABI).

11. Calls, exceptions, polls and the collector. Calls out use the direct-call path through
    call-cache ways and A2's pickup, natives the lean boundary and their fast entries. A throw
    inside optimized code exits to the first stage at the throwing bytecode with the exception
    pending, where the first stage's handlers run (SpiderMonkey compiles no catch blocks; JSC exits
    on exceptions); compiled handlers wait for a measured need. Entry and back edges poll as the
    baseline does. Write barriers are elided for cells allocated since the last point that can
    collect (JSC's epoch analysis, which needs the per-node "may collect" fact; TRust's in-line
    allocation already needs no barrier before the next safepoint) and are card marks otherwise.
    JSC's other obligations carry over: code on the stack stays alive, references from code are
    weak, interior pointers resolve, and stack hygiene keeps dead spill slots from retaining
    garbage. Shared stubs keep the rule that they build in no per-heap or per-thread address.

12. OSR and reoptimization. OSR entry as JSC's DFG enters: each loop header of the whole-function
    graph is an entry; the live values are read from the canonical frame and checked against the
    speculated types at entry, and entry is declined (the frame stays in the baseline) when they
    disagree; the first stage's back-edge counts (point 2) trigger it, from first-stage frames and
    from the VM's borrowed frames. Separate per-loop entries (V8, JSC's FTL) are a top tier's.
    Reoptimization as JSC's exit profile: exits counted per compiled function; past 100 x 2^R
    (5 x 2^R when the exited frame then loops hot) the code is discarded, each exit taken is
    recorded as a flag at its bytecode site and kind, the next compile declines those speculations,
    and the warm-up before it doubles. SpiderMonkey's cause tags mark guards an optimization
    invented, and their exits set a per-function "not again" flag. Optimization is never disabled
    for good (JSC, V8). The pieces of P2's parked branch p2-region-s3 (per-site counters on the bail
    path, the exit profile, discarded code kept until no activation runs it) carry into this.

13. Compiled on the main thread, built for threads. On one CPU background compilation cannot help
    (SpiderMonkey turns off-thread Ion off there: "Require cpuCount > 1", jit/Ion.cpp:2114-2115).
    The tier compiles synchronously from its immutable snapshot (point 3), records every assumption
    as a dependency and validates them at install (JSC's Desired* sets), so compiler threads can be
    added later under JSC's rules (plans as roots, compiler threads stopped during a collection)
    without rebuilding the front end, as SpiderMonkey had to when IonBuilder's reliance on global
    type data kept its building on the main thread.

14. Targets. The snapshot, builder, IR, passes, recipes and deoptimizer are target-neutral; the
    lowering, register file, exits and entry and resume stubs are per target. ARM64 first; x86-64
    follows (Decision 6).

## Gates

P2's rules hold (its Decision 8: tests are a diagnostic tool, run in full at a major phase's end or
after a large change to what they measure). An optimizing tier adds what the exemplars run their
own tiers under, because a speculation that never fails in the default configuration is an exit
path that never runs:
- The tier eager: every function the tier accepts compiled at its first opportunity, so Test262 and
  the lib suite run their code through it (V8's --stress-maglev, "a very low interrupt budget for
  maglev"; SpiderMonkey's eager Ion compilation, a warm-up threshold of 0,
  jit/JitOptions.cpp:448-451; JSC's forceEagerCompilation).
- Exits forced: a mode that fails a check every Nth time one is passed, so every exit's frame
  reconstruction and materialization runs (V8's --deopt-every-n-times, "deoptimize every n times a
  deopt point is passed"; SpiderMonkey's bailAfter counter, jit/JitRuntime.h:216-224).
- difftest across the tiers with the new tier in its matrix, and its corpus seeded with the
  speculation-heavy shapes (polymorphic sites, int32 overflow, holes, prototype changes during a
  loop, getters installed late, closures of one function).
- GC stress over the tier's suites when the tier or its contract with the collector changes (stack
  scanning, barriers, allocation in line).
Test262 in full at --tier=jit with the tier eager and with exits forced joins the phase-end list;
each stage's design note says which of these its steps run before landing.

## Decisions (the owner's, 2026-11-08)

The owner approved the plan as proposed ("Go ahead, this is approved, let's get started on P3."):
the seven decisions below stand as written, each with its recommended option.

1. The phase exit. Recommended: each fixture within 2x of node-mg in its measured pass and in steady
   state, and Octane's geomean over the 15 benchmarks Node runs within 2x of node-mg, in one
   session; Web Tooling, ARES-6, the calls, full Node, TRust's replays, peak RSS and compile time
   reported. From today that needs Vue 2.08x faster in its measured pass and 1.81x in steady state,
   React 1.25x and 1.72x, Djot 1.01x and 2.22x, and Octane 2.43x (2.24x without zlib, whose asm.js
   V8 runs as WebAssembly). The alternative, in P2's form: the fixtures' measured passes only. Stage
   notes propose their own exits for agreement, as in P2.
2. Scope. Recommended: P3 builds the mid tier and its forms of the program's optimizations (point
   9). The top tier (function-wide value numbering and load elimination with alias analysis,
   LICM, range analysis with bounds-check elimination, general allocation sinking, per-loop OSR
   compiles, polymorphic call inlining, a greedy register allocator) is planned at P3's exit, on
   the mid tier's front end and its measurements. The alternative: the top tier as P3's second
   half.
3. The second stage. The tier replaces it for the functions it compiles, second stages remain for
   functions it refuses, and at the phase's end they are retired or kept on the measurements. C3
   on A2 is not landed, since compiling once on settled feedback is the tier's own policy (point
   2); tier 1's step (c) becomes the tier's work budget and OSR trigger (points 2 and 12).
4. The design forks as the exemplar survey matches them: points 2-13. The standing approval ("as
   recommended as long as they aren't simply to make implementation simpler") covers them unless
   the owner says otherwise; none rests on ease. Point 7 is the one where the exemplars split and
   TRust's write-once code and frames decide: invalidation points that test a validity word (JSC's
   unlinked DFG) over V8's return-address rewriting, at a load and a branch per point.
5. Values. Numbers stay NaN-boxed f64 words, with int32 a representation inside the tier. All three
   exemplars have an int32 value tag (V8's Smis, SpiderMonkey's and JSC's int32 tags); one would
   change every tier, the object model and the embedding, so it is not proposed for P3, and the
   owner may want it considered on its own.
6. x86-64. Recommended: the tier's x86-64 lowering as P3's last tier stage, so the two backends do
   not diverge further (x86-64 has no regions, chains, direct calls or shared stubs today); the
   alternative is after P3. Until then x86-64 keeps passing its suites on zombie with the first and
   second stages.
7. Gates: the eager and forced-exit modes join the phase-end gate, with Test262 in full under both,
   and difftest's matrix gains the tier.

## Non-goals

The top tier (Decision 2); compiler threads (point 13 keeps the way open); an int32 value tag
(Decision 5); moving or compacting collection; concurrent marking; startup snapshots (P4);
Speedometer acceptance beyond the replays.

## Risks

- Exits: every exit must rebuild exact frames (handlers, environments, `this`, new.target, arguments
  objects, TDZ state); the forced-exit mode, difftest and Test262 with the tier eager guard them.
- Effects: getters, setters, Proxy traps, valueOf and toString and every other re-entry make most
  operations effectful; a wrong read/write set is a miscompile, and a missing invalidation point a
  stale speculation. The sets start conservative and narrow only with tests.
- The collector: optimized code keeps raw pointers in registers and spill slots, which the
  conservative scan covers, but barrier elision and incremental marking's invariants must hold
  across every allocation and safepoint; GC stress and TRUST_JS_GC_VERIFY run over the tier's
  suites.
- Compile time: the tier compiles on the main thread inside 30-200 ms fixtures. Maglev's speed is
  the reference (by V8's own figures 10-20x slower than Sparkplug and 10-100x faster than
  TurboFan), measured at each stage.
- Hardening: generated code runs outside Rust's checks. Bounds checks stay (no range analysis), and
  where a later proof removes one, a trap remains (V8's turbo_typer_hardening).
- Scale: this is the program's largest phase. The second stage remains the fallback until the tier
  covers its functions, and each stage lands on main as validated.

## Stage records

Each stage's design note, written before its code, then its gates and exit measurement.

### Stage 1: the tier's skeleton on ARM64 (design, 2026-11-08)

Inputs: stage 0's census (target/p3/census/census.txt: 30 workloads, 1,361 hot functions, operation
counts from a diagnostics build of 44676fc7, profiles of its engine code) and a study of the
contracts the tier must meet (target/p3/stage1/contracts.txt, every claim cited at 44676fc7). Both
change how stage 1 meets the design, not the design.

What the census found:
- Production time: generated code 42.5%, shared stubs 13.7%, helpers called from generated code
  33.9%; second stages, whose code holds their spliced callees, carry 62% of the generated-code
  time. Calls (CallWithThis 23.1% of the hot-function time, more than half of it in their helpers)
  and the four named loads (26%) hold the time; locals and branches the executions.
- The core set S1 (constants, locals, arithmetic, comparisons and branches, loops, named loads and
  stores, calls, returns) holds 90% of the executions, but S1 plus the free names (LoadName,
  LoadNameForCall) is what completes functions: 29.5% of the hot-function time lies in functions
  whose executed operations are all in it, against 10.4% for S1 alone; turning never-run sites
  into exits (Design 3) doubles that from 14.3%. The coverage order after it: elements, allocation,
  spread, strings, the iterator protocol, typeof/in/instanceof, the self-hosted built-ins'
  abstract operations, closures and captures, generators, try/catch/finally.
- Features in hot functions: for-of 9.0% of the time (21-22% on the fixtures), try/catch/finally
  2.8% with no throw executed, generators 3.0% (ARES-6 Basic only), spread 12.7%, proper tail call
  sites 15.2% with none executed, accessors at named sites 14.4%, Proxy receivers 2.0% (Vue); no
  super, classes, private names, `with` or direct eval.
- Outside the tier, for later stages: ARES-6 ML's derived-class constructor never reaches generated
  code (42% of ML's cycles in the tree-walker and the VM); 59% of Air's hot-function time is the
  exact-PC helper, on switch statements whose case labels are free names; 53% of RayTrace's is
  `new` through jit_new.

What the contracts study found, and what it changes:
- Optimized code can be entered by every existing caller unchanged if it keeps the first stage's
  entry contract: both argument conventions (bit 31 of the count), the entry poll the direct call
  relies on, the frame setup, the strictness save, w0 = 1 or 0 with ctx.ret or ctx.error, x19-x28,
  x29, sp and d8-d15 preserved (contracts 5.4).
- jit_operations.rs is not a register ABI, as the plan's point 10 assumed: it emits each operation's
  baseline template on the canonical frame (contracts 4.6). The tier's generic path is therefore
  the regions' "effect": the canonical frame written, the baseline template emitted, its results
  reloaded (below). Point 10 is corrected accordingly.
- An exit cannot yet continue in place in the first stage: 13 fusions consume pcs whose
  pc_offsets entry then starts the next operation, and the first stage records neither which pcs
  are enterable nor its frame size (64 or 128 bytes) nor its unwind and epilogue addresses
  (contracts 2.2, 1.3, 4.5). Stage 1 resumes every exit in the VM, which can run any pc (drive_vm
  already takes borrowed state and a pending throw, contracts 3); stage 2 makes the first stage
  record what point 6's in-place resume needs and adds it, the VM staying the fallback, as JSC's
  LLInt is.
- A2 redirects by chunk, and a second code object for one chunk has no way in (contracts 6.2): the
  tier's code needs a chunk of its own.
- No counter sees every entry or back edge (contracts 7): the work budget of point 2 needs one in
  the prologue and at every kind of back edge (header polls, region, loop-chain and linked-scan back
  edges), the change OSR's trigger needs, so both come in stage 5.

The tier's place in stage 1: the code generator of second-stage chunks. The second stage already
builds the chunk the tier should compile, its hot callees spliced in, seeded from the first stage,
with a record map that forwards its feedback (W4 step 7), and publishes it through A2. Under
TRUST_JS_OPT=1 the tier generates that chunk's native code in place of the template JIT whenever
it accepts the chunk, and the template JIT does as today otherwise. This keeps the second stage's
inlining while the tier's own (stage 3: built in the graph, with frame states, Maglev's policy and
closures by code) is made, so turning the tier on loses no inlining, and it keeps every exit inside
one frame, since a spliced callee has none. Stage 3 then replaces the splicing as the plan's point
8 describes, and the tier's input becomes the first-stage chunk and its callees' chunks.

When: at the second stage's checkpoints (about 100, 500, 2,100 and 8,500 native runs), with the
tier on, the second stage is built at the first checkpoint whose feedback fingerprint (named ways
and generic marks, call ways and megamorphic states, value and element records) equals the
previous checkpoint's, V8's settled-feedback rule (P2's probe5, TRUST_JS_TIERUP_STABLE, is the
precedent), or at the first checkpoint under TRUST_JS_OPT_EAGER=1. A function whose inline plan
is empty gets a chunk of its own all the same when the tier is on (compile_with_inlines with the
empty plan, seeded and record-mapped from the first stage), published only if the tier accepts it:
Maglev compiles a hot function whether or not it inlines, and the hottest leaf loops have nothing
to splice (2026-11-08). The last checkpoint compiles whatever its fingerprint (2026-11-09): neither
exemplar abandons a hot function's tier-up while its feedback changes. JSC optimizes after
maximumOptimizationDelay (5) delays whatever its value profiles say
(CodeBlock::shouldOptimizeNowFromBaseline); V8 pushes the budget out by
minimum_invocations_after_ic_update (500) at each IC change and never cancels
(TieringManager::NotifyICChanged). The four checkpoints are a bounded schedule like JSC's delays,
and the repeated-exit rule below bounds what compiling unsettled feedback costs. TRUST_JS_OPT_LOG
logs each wait.

The front end:
- Inputs, immutable during the compile: the chunk's operations (Chunk::jit_ops, the list its code
  is for), constants, names and flags; jit_ir's Cfg (blocks, settled depths, RPO, dominators,
  natural loops, handler roots); the snapshot, one feedback_read view per pc copied (the seeded
  caches of the chunk, and through its record map the first stage's value and element records).
- Evidence that code ran: named and call sites only. Their first execution fills a way or sets the
  generic mark (seeded from the first stage); value and element records are not evidence, since
  in-line hits record nothing (rule U). A block holding a named or call site none of which ran is
  an unconditional exit at its first pc; other blocks are compiled.
- The IR (point 4): a CFG of blocks of SSA nodes. Values: constants, the entry slots, slots
  reloaded from the frame after an effect, `this`, phis, effect results. Checks, each with its eager
  exit's frame state and reason: Number, exact int32 (not -0), object, shape (up to four), Boolean.
  Conversions (int32 and f64 to and from the tagged word, NaN canonicalized), int32 arithmetic with
  overflow exits, f64 arithmetic, comparisons, field loads and stores by the way's location and slot
  (a card mark for a reference store), slot flushes, effects with their result projections, and
  the terminators jump, branch, return and exit. A frame state is the pc, each live slot's source
  (the frame, or a node) and every live stack position.
- The builder: one forward pass in RPO interpreting the canonical frame (slots and operand stack)
  over SSA values; loop-header phis from a loop-assignment prepass; known facts per value (shapes,
  representation, loaded fields under an effect epoch), merged at joins.
- Native lowerings: S1 as listed, with InlineGuard (the callee and Realm compared) and ResetSlots.
  Named loads and stores lower natively on own data ways (one shape, or up to four by dispatch); the
  rest of S1's named forms, calls and `new`, the free names and every other non-control operation
  are effects in stage 1, the free names first in stage 2's order.
- Handlers: PushHandler, PushIterator and PopHandler emit no code; the handler nesting at each pc
  is static (Cfg's handler roots), and a throw in optimized code exits to the VM at the throwing pc
  with the throw pending and the handler records rebuilt, where the VM runs the catch or iterator
  pad (point 11). Returns inside an iterator region exit to the VM, which routes them.
- Refused in stage 1: resumable chunks (generators, async), PushFinally and its completions
  (AbruptJump, ResumeJump, the Resume and Dispose families), `with`, direct eval, prepared entries
  (mapped arguments, eval, closures that need them), loop fragments, derived constructors, chunks
  over the frame record's 256 words. A TailCall that runs exits to the VM.

The back end:
- Frame and entry: the first stage's prologue and epilogue emitters are factored out of
  compile_entry and shared, so the entry contract above holds by construction; the frame adds the
  saves of x23-x28 when used and the spill slots below the first stage's header.
- Registers: x19 the context, x21 the helper table and x22 the slots stay pinned, as effects need
  them; x20 is set to stack_base + 8 x depth(pc) before each effect and is free between them.
  Allocatable: x0-x8 and x10-x15 (caller-saved), x23-x28 (callee-saved, and no baseline template
  touches them), d0-d7 and d16-d31 (caller-saved), d8-d15 (callee-saved, and no baseline template
  writes them); x9, x16 and x17 are the tier's scratch and veneers, x18 unused. Maglev's single
  forward pass: live ranges and next uses first, a register at each definition, a spill at the
  definition when none is free, values live across an effect or a call in callee-saved registers or
  spill slots (all scanned conservatively), parallel moves on edges into merges.
- Effects (contracts 4): the dirty locals flushed to their slots, the operation's operands written
  to the canonical words below stack_base + 8 x depth(pc), x20 set there, the baseline template
  emitted through operations::emit (emit_exec where it declines) with the tier's unwind label;
  afterwards its results are loaded from below the returned x20, every slot counts as living in the
  frame again, and heap facts are dropped. Calls keep the first stage's probes, direct sequence and
  native fast entries this way.
- Exits: a failed check is one `bl` to the code's shared exit stub, the exit found from the return
  address (V8). The stub saves x0-x28 and d0-d31 and calls the Rust deoptimizer, which reads the
  exit's recipe (per live slot and stack position: a register or spill slot holding a tagged word,
  f64, int32 or Boolean, a constant, or the frame), writes the canonical frame, fills elided rest
  and `arguments` slots as run_inner would (contracts 3.2), rebuilds the handler records, and runs
  the chunk in the VM from the exit's pc to completion on that state (a new driver modeled on
  jit_vm_operation and run_inner, with VmTiering so that a loop can move to borrowed-frame code);
  the completion goes to ctx.ret or ctx.error, and the stub leaves through the matching epilogue.
  The code stays protected meanwhile: its record's code_base names it.
- A throw with no handler at its pc leaves through the throw epilogue (ctx.error is set by the
  helper); with one, it exits as above.
- Repeated exits: past 100 exits of one compiled code (point 12's JSC rule at R = 0), new entries
  stop using it and the chunk takes the template JIT's code, compiled then if it has none; running
  activations finish in the tier's code, which stays alive until none runs it. Stage 1 does not
  recompile: the exit profile and reoptimization are stage 2's. This keeps an exit loop from making
  the tier slower than the code it replaces. Milestone 2's runs (non-LTO, Octane at 5 runs and the
  three fixtures, 2026-11-09): 241 of 905 compiled codes fell back with the tier on (eager: 436 of
  1,345), 97 of GBEMU's 110 and 82 of TypeScript's 354. Their exits: a wrong shape 17,111 (GBEMU
  and TypeScript, mostly at pc 0), a wrong callee 4,717, a block that never ran 2,259. The shapes
  (2026-11-09, every exit's expected shapes being the ways seeded at the compile): GBEMU's are the
  program's, receivers the cache had not seen. Each Octane run builds a new emulator core, and from
  the second run its audio set-up fails, so the core lacks a property the first one added and takes
  another shape from key 288; V8's maps split there too. Of TypeScript's 5,844, 3,650 are the
  tier's, named loads on primitive strings and numbers (next point), and the 2,059 others examined
  the program's (AST nodes that gain a property later, node classes that reach a site later,
  subclass instances in another capacity class, which V8's per-constructor initial maps share
  likewise). pdfjs's and box2d's are the program's but for 300 on strings; no shape changed
  without a key change. The program's cases are stage 2's: the caches after the exits hold the new
  shapes, four ways or fewer.
- Primitive receivers (2026-11-09): a named access on a string, number or Boolean fills its way
  from the wrapper prototype (the way's receiver shape is String.prototype's), so the builder took

  feedback says what the receiver was: V8's maps are string and HeapNumber maps, which Maglev

  builder keeps such a site an effect: the baseline template handles primitives as the template
  JIT's code does. Maglev's lowering (a check of the primitive, the prototype's shape and a load
  from it) is a later stage's.
- Throws (2026-11-09): an exit for a throw (a thrown effect, a throwing poll, Op::Throw) counts

Step 1, ToInt32 in line. The bitwise operations (BitAnd, BitOr, BitXor, Shl, Shr, UShr, BitNot)
take their operands' ToInt32 (ECMA-262 7.1.6), which wraps modulo 2^32. Stage 1 converted each
operand exactly (CheckInt32, exiting with NotInt32 when the Number is no int32) and left an operand
held as an f64 to the effect path, so `(a * b) & m`, a `| 0` on an f64 sum and `h >> 14` on a
double went through the VM's operation helper: 38% of zlib's samples and 31% of Mandreel's with the
tier on. Maglev truncates: GetTruncatedInt32ForToNumber takes an Int32 as it is, adds
TruncateFloat64ToInt32 for a Float64 and TruncateCheckedNumberOrOddballToInt32 for a tagged value
(src/maglev/maglev-reducer-inl.h), and ARM64's truncation is FJCVTZS where FEAT_JSCVT is present
(TruncateDoubleToI, src/codegen/arm64/macro-assembler-arm64.cc:3014), else FCVTZS to 64 bits with
a saturation test and the DoubleToI builtin when it saturates. The tier does the same with a
TruncateToInt32 node (f64 to int32, no exit): FJCVTZS under jscvt_available(); otherwise FCVTZS to
a 64-bit register, whose low word is the result unless the conversion saturated, and on that cold
path the low word computed from the exponent and mantissa (zero from 2^84 up, and for the
infinities), in line where V8 calls its builtin. A tagged operand is checked a Number (CheckNumber,
NotNumber) and truncated, a proven int32 is used as it is, and a constant folds. A truncation is not
a form of its operand (forms hold one value), so it is cached per value beside the forms. UShr's
result is an int32 when its count is a constant with count & 31 non-zero, as in stage 1; any other
count (asm.js's `>>> 0` among them), which stage 1 left an effect, gives a uint32 that the tier
holds as an f64 (UCVTF), as Maglev's shift "returns a Uint32" (Int32ShiftRightLogical,
src/maglev/maglev-ir.h:3519-3525), used as a Float64 where it may exceed the int32 range.
Operands the feedback says are not Numbers keep the effect path, as stage 1's. Tests: the builder's
graph for each operand form (an int32, an f64 product, a tagged double, a constant); end-to-end
values under the tier eager and with exits forced, with and without TRUST_JS_JIT_NO_JSCVT (-0, NaN,
the infinities, 2^31, -2^31 - 1, 2^53, 2^63, 2^84, a product past 2^53).
